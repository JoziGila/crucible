# R12 feasibility review

Summary: Round 2 moved third-party Wasm components into an opaque-origin browser sandbox that cannot answer the synchronous `crucible:ops` imports the contract gives evaluation worlds, so the heaviest Wasm components cannot run in browsers as specified.
The swarm premise rests on about 430 protected oracles that phases 0 and 1 need, which only humans may write, with no schedule, staff line, runner classes or held-out data; the 1.5× factor is neither measured nor accounted.
Round 2 added an estimated 20 to 30 engineer-years to phases 0 and 1 without the approval contract 13.2 requires, phase 2 is sized below the backlog it inherits, and the critical path omits the UI and release chains that the phase 1 gate also needs.

### R12-01 · Critical · Targets: CONTRACT, PLT, ECO
**Section:** CONTRACT 7.4 Wasm execution; PLT Wasm component runtime (D-PLT-31, D-PLT-36); PLT The browser target
**Problem:** Contract 7.4 makes evaluation worlds synchronous and lets them import `crucible:ops`, and CCR-ECO-8 and CCR-PLT-5 (round 2) move every third-party Wasm component into an opaque-origin sandboxed iframe's worker that exchanges data with the engine by `postMessage` only. A synchronous import cannot be answered by a message that arrives on the caller's own blocked event loop, the sandbox cannot share a `SharedArrayBuffer` with the engine worker because it lives in another agent cluster, and PLT rules out JS Promise Integration. As specified, nesting, CAM strategies, slicers, placers and routers that call Anvil or Flux operations cannot run in a Tier 1 browser at all.
**Evidence:** Contract 7.4: "Evaluation worlds are synchronous and import no WASI; they may import `crucible:ops`." D-PLT-31: in browsers a third-party Wasm component "runs in a worker inside an opaque-origin sandboxed iframe without OPFS, cookies or keys, exchanging data by `postMessage`". PLT: "Relaxed SIMD, memory64, exception handling and JS Promise Integration are not used." HTML StructuredDeserialize for `SharedArrayBuffer`: "If targetRealm's corresponding agent cluster is not serialized.[[AgentCluster]], then throw a DataCloneError DOMException" (https://html.spec.whatwg.org/multipage/structured-data.html); an opaque origin is its own site, so its workers form a separate cluster. A relay through the iframe's own main thread would need the sandboxed iframe to be cross-origin isolated, which no tab specifies. PLT's overhead table covers determinizer cost only, not the out-of-process call cost that round 2 introduced. WASI 0.3.0 (11 June 2026) made "async ... native to WebAssembly Components" (https://github.com/WebAssembly/WASI/releases).
**Fix:**
1. Contract 7.4: replace "Evaluation worlds are synchronous" with "Evaluation worlds import no WASI and are deterministic. Their `crucible:ops` imports are Component Model async functions in the callback ABI (no stack switching), so a host may answer them across a process or agent-cluster boundary; results never depend on completion order or timing, and fuel never counts host time." ECO regenerates the `crucible:ops` bindings; the browser first-party runtime (D-PLT-36) implements the callback ABI; native hosts may still answer synchronously.
2. Until the bridge passes PLT-O-WASM-1 in browsers, browsers evaluate third-party evaluation-world Wasm components remotely on the team server or a cloud worker, which contract 9's parity rule allows ("whether computed locally or through remote evaluation"). This also takes the browser sandbox out of phase 1, where the only third-party components are a user's own unpublished ones.
3. PLT adds rows to its overhead table, labelled targets: one `crucible:ops` round trip at most 20 µs between native processes and at most 250 µs across browser agent clusters, plus argument transfer per MiB. New oracle PLT-O-WASM-7: a reference component making 10,000 `anvil::offset` calls through each executor gives identical results and meets the rows.

### R12-02 · Critical · Targets: CONTRACT, PLT, AGT, ANV, FLX, UIX
**Section:** CONTRACT 1 Mission, 3 principle 6, 13.2 Program plan; Oracles in every tab
**Problem:** The mission and the 1.5× factor rest on swarms "working against oracles", yet every oracle sits in a directory agents cannot write, so each one, with its corpus and executable pass criterion, must be written and reviewed by people before any swarm work on its capability can start. Phase 0 and 1 capability rows cite about 427 distinct oracle ids, many on corpora that do not exist yet, while "oracles, corpora and QA" grows from 2 to 5 people and no milestone says when any oracle must exist. The spec has no build-program section at all: no work-item format, eligibility rule, runner class or review path for swarm output, and contract 13.2 lists "test corpora" as swarm work although agents cannot write `oracles/`.
**Evidence:** Parsing every capability table (Capability · Contract · Failure · Oracle id · Phase) gives 760 distinct cited oracle ids, 427 of them on rows phased 0 or 1. PLT: "All PLT oracles live in `oracles/plt/`, readable but not writable by agents"; UIX: "Oracles live in `oracles/uix/`, protected from agent edits." Corpora still to build include the "ABC-derived 200-feature corpus" and "a named GP1-class benchmark" (contract 13.3), "the prismatic ABC corpus" (13.2) and FLX's calibration entries with "at least 300 held-out samples and zero undershoots" per estimator class. Several oracles have runners agents cannot drive: PLT-O-PERF-1 on the physical reference laptop, UIX's "photodiode latency each phase", PLT-O-TGT-1's device farm, UIX-O-A11Y-3's screen readers and UIX-O-KEY-1's "reference tables kept by daily users". The only "swarm" text in the spec (AGT's Orchestration of swarms) describes agents using Crucible, not agents building it.
**Fix:** Add a "Build program" paragraph to contract 13.2, owned by PLT, which already owns engineering capacity:
1. **Oracle first.** An implementation work item opens only when its oracle ids exist in `oracles/` as executable checks reviewed by a second engineer. Chain A and B oracles exist by month 9 and every phase 1 oracle by month 15; each gate reports oracle coverage per crate.
2. **Runner classes.** Every oracle declares one runner class: `cpu-ci`, `browser-ci`, `gpu-lab`, `device-farm`, `physical` or `human`. Only `cpu-ci` and `browser-ci` work is swarm-eligible.
3. **Corpora.** Swarm-built corpora and reference data enter `oracles/` only through a human-reviewed Proposal and must agree with an independent source (MPFR, Open CASCADE, lib3mf, MFEM or libCEED, CAx-IF data).
4. **Staff.** Oracles, corpora and QA grow 4 → 10 instead of 2 → 5, or each domain team's line in the staffing table carries 15% of its engineer-years for oracle authorship, stated explicitly.
5. **Work items.** A work item is `{ crate, capability row, oracle ids, held-out split, budget }`, run through AGT's Plan and Proposal machinery against Crucible's own repository, with the verifier role of D-AGT-12.

### R12-06 · Major · Targets: CONTRACT, PLT
**Section:** CONTRACT 13.3 (reference laptop); PLT Performance engineering (D-PLT-28, Measurement protocol)
**Problem:** The contract fixes a processor, not a laptop. The Core Ultra 7 258V runs between 8 W and 37 W at the manufacturer's discretion and mixes 4 performance cores with 4 low-power efficient cores, so sustained throughput depends on chassis, firmware and power mode. The measurement protocol fixes run counts and percentiles but no power source, OS power mode, thermal preconditioning, panel refresh rate, or Windows and Ubuntu builds. Beta-blocking rows measured on an unnamed chassis are not reproducible, and the 120 Hz input-to-photon row needs a 120 Hz panel that nothing guarantees.
**Evidence:** Intel's specification for the 258V: "Performance cores 4", "Low-power efficient cores 4", "Base power 17 W", "Peak turbo power 37 W", "Minimum assured power 8 W", "Instruction set extensions: SSE4.1, SSE4.2, AVX2" (https://www.intel.com/content/www/us/en/products/sku/240957/intel-core-ultra-7-processor-258v-12m-cache-up-to-4-80-ghz/specifications.html). PLT: "Rows run 30 times unless stated", with no other conditions. Contract 13.3: "Input to photon, p99: 50 ms at 60 Hz; 33 ms at 120 Hz".
**Fix:** In D-PLT-28 and contract 13.3, name the exact laptop model and SKU (chassis, panel and its refresh rate, BIOS version), buy three units (one per OS and a spare), and fix the conditions: AC power, one named OS power mode, sustained package power read and logged per run, 10 minutes of thermal soak, ambient 20 to 25 °C, and pinned Windows 11 build, Ubuntu release, kernel and GPU drivers. Before each benchmark session, a calibration workload must land within 3% of its recorded value, or the session is discarded. If the chosen chassis has a 60 Hz panel, the 120 Hz row is measured on the macOS mid machine and does not block beta.

### R12-07 · Major · Targets: CONTRACT, FLX, ANV, ING
**Section:** CONTRACT 7.5 Shared kernel IR; 13.2 Staffing and milestones
**Problem:** Kernel IR v0 must freeze at month 6, yet the three compiler engineers who build it are first hires in months 0 to 4. Its first real consumers, H¹ elements with CG (months 6 to 12) and Anvil's implicit tapes (phase 1), arrive only after the freeze. **Fix:** In contract 7.5, freeze IR v0 at the month-12 phase 0 gate, after one H¹ elasticity kernel with sum factorization, one constitutive function with forward-mode derivatives and one implicit tape have compiled through both CPU back ends and passed their oracles. From month 6 the IR is additive-only, except for defects those three consumers find. In 13.2, list the seed team of 20 by role, with an owner in seat at month 0 for every month-3 and month-6 milestone; any milestone without one moves by the owner's hiring lag.

### R12-12 · Major · Targets: CONTRACT, AGT

### R12-13 · Major · Targets: CONTRACT, PLT, UIX, FLX, KLN, ECO
**Section:** CONTRACT 3 principle 6; Oracles in every tab
**Problem:** Agents read every oracle's inputs and pass criteria, and only Anvil keeps held-out data outside the agent-readable tree. Code written against fixed visible inputs can pass by special-casing them, which is the standard failure of optimizing against a fixed test set. PLT's benchmark files, UIX's recorded scripts and reference images, and most corpora in other tabs are fixed and readable, so "oracle-covered" work is not yet evidence of correct behaviour.
**Evidence:** ANV: "Held-out ABC and Thingi10K subsets, chosen by a fixed hash rule, stay outside the agent-readable tree." PLT: oracles "readable but not writable by agents"; benchmark files "live in `oracles/plt/bench/`". UIX-O-SNAP-2: "Mean ꟻLIP at most 0.01 against references per backend"; UIX-O-ELX-1 replays "ELX's recorded routing and placement sessions". No other tab's Oracles section names a held-out split.
**Fix:** Contract principle 6 adds: "Every oracle that agent-built code is judged against has a held-out split outside the agent-readable tree, chosen by a fixed hash rule, or a property generator seeded at CI time and never shown to agents. A pass on visible inputs with a failure on held-out inputs fails the oracle." PLT adds held-out variants of each 13.3 benchmark (perturbed GP1 parameters, a second ABC sample); a visible-to-held-out performance gap above 10% fails PLT-O-PERF-1.

### R12-14 · Major · Targets: CONTRACT, PLT, UIX, ECO
**Section:** CONTRACT 7.4 Executors (iPadOS); PLT Tablets and phones (D-PLT-33); PLT Open questions 1 and 2; UIX Platform notes
**Problem:** The contract claims the iPadOS app "meets App Review guidelines ... 3.2.2(i) ... and 4.7" while registry packages are "never ... a browsable catalog". But guideline 4.7.4 requires "an index of software and metadata available in your app" with universal links, and 4.7.1 and 4.7.5 add reporting, blocking and age restriction, which no tab plans for. D-PLT-33's first form, a WKWebView worker beside native engine threads, also cannot answer the synchronous `crucible:ops` imports of Wasm running in WebKit (R12-01): it would need a relay from a separate WebKit process through a callback-based reply handler. UIX has already picked the second form, while PLT defers the choice to a phase 3 spike, so the tabs disagree.
**Evidence:** App Review Guidelines: 2.5.2 forbids apps to "download, install, or execute code which introduces or changes features or functionality of the app"; 4.7.4: "You must provide an index of software and metadata available in your app. It must include universal links that lead to all of the software offered in your app"; 3.2.2(i) bans an interface "similar to the App Store or as a general-interest collection" (https://developer.apple.com/app-store/review/guidelines/). Apple's `WKScriptMessageHandlerWithReply` answers JavaScript through a `replyHandler: (Any?, String?) -> Void` callback (https://developer.apple.com/tutorials/data/documentation/webkit/wkscriptmessagehandlerwithreply.json). UIX: "On iPadOS the web build runs in a thin WKWebView shell"; PLT open question 2: "A phase 3 spike ... picks one of D-PLT-33's two forms".
**Fix:** Answers PLT open questions 1 and 2.
1. iPadOS uses only the second form, the web build in a WKWebView shell, so it shares the browser runtime and the async `crucible:ops` bridge of R12-01.

### R12-19 · Major · Targets: PLT, KLN, FLX
**Section:** PLT The browser target (D-PLT-29, D-PLT-30)
**Problem:** D-PLT-29 makes the engine worker the owner of "every OPFS write handle (CAS packs, journal, ...)", while D-PLT-30's heavy worker "writes results to the OPFS CAS". Synchronous access handles lock per file, so the heavy worker cannot write those packs. The heavy worker also has no thread pool, because the wasm-bindgen-rayon compute workers share the engine module's memory, not the heavy worker's. **Evidence:** D-PLT-29: "The first tab's engine worker takes a Web Lock and owns every OPFS write handle"; PLT: a synchronous access handle "takes an exclusive lock on the file". The compute pool through wasm-bindgen-rayon" beside "Heavy worker | One disposable evaluation with its own memory".
**Fix:**
1. The heavy worker writes a new pack file under a name only it holds, then sends the pack's index to the engine worker, which adopts it. D-PLT-29 then reads "every OPFS write handle except heavy-worker packs in transfer".
2. The heavy worker starts its own pool of min(`hardwareConcurrency` − 2, 8) nested workers on its own shared memory, the engine pauses its pool while a heavy evaluation runs, and Kiln's cost model includes pool start-up.
3. PLT-O-WEB-3 adds a heavy evaluation at 1 and 8 threads with identical hashes and the expected speed-up.
