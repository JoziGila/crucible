# R4 practice review

Summary: (1) No tab forbids Crucible from starting machines, robots or printers remotely, and the contract, MFG, AGT and KLN disagree on who may transfer or start physical work and when the Act machinery exists (R4-01).
(2) Collision verification simulates the toolpath model, not the controller's motion semantics (rapid interpolation, rotary unwinding, reference returns, retract planes), so "verified" programs can still crash (R4-02).
(3) Circuit connectivity merges as a set union, so two clean branches can silently short two nets, and ELX's own merge target counts that as success (R4-03); the schematic and PCB editors also have no workable home in UIX (R4-04).

### R4-01 · Critical · Targets: CONTRACT, MFG, AGT, KLN
**Section:** CONTRACT §2 (Act); MFG Approval and machine safety, Printer profiles, 3MF and machine connectivity, Machine and MES connectivity, Platform notes; AGT Irreversible real-world actions, Phasing; KLN Hardware CI runner.
**Problem:** No tab separates moving data to a device from starting motion, heat or energy, and none forbids Crucible from starting a machine remotely. MFG ships printer "start" and OPC UA job writes as plain "`api` actions" in phases 1 to 3, while AGT's Act machinery for `send_to_machine` arrives only in phase 2 and lets the agent commit after a remote approval reached "through the review UI and Tier 2 notifications". KLN lets agent branches run `unattended_safe` rigs although MFG requires a person to approve every program, and the tabs disagree on who may transfer (MFG: never agents; AGT: agents prepare and commit) and on Act names (`transfer_program`, `start_build` against `send_to_machine`).
**Evidence:** MFG: "Printer connectivity | Send, start, pause, cancel, monitor through plugins (OctoPrint, Moonraker, PrusaLink, vendor APIs, MTConnect, OPC UA) as `api` actions | … | 1"; D-MFG-4 "agents can neither approve nor transfer programs"; OPC UA adapter "production jobs … are written only where allowed"; "Shop-floor approval requires a Tier 1 client or a Tier 2 client with an authenticated approval key". AGT: CAM programmer role holds `send_to_machine`; phase 1 has only the `release` Act. KLN: "Runs requested from agent branches use only rigs marked `unattended_safe`". OPC 10031-4 ISA-95 Job Control, which OPC 40001-3 Machinery Job Management (1.0.1, 2024-05-01) builds on, lists `Start`, `StoreAndStart`, `Resume` and `RevokeStart` methods on the job-order receiver (https://reference.opcfoundation.org/ISA95JOBCONTROL/v200/docs/6.3; https://reference.opcfoundation.org/Machinery/Jobs/v100/docs/). ISO 10218-1:2025 and ISO 10218-2:2025 replaced the 2011 robot safety editions (https://www.iso.org/standard/73933.html; https://www.iso.org/standard/73934.html).
**Fix:** Contract §2, Act row, append: "Acts with a physical effect are transfer Acts (send an NC program, print job or robot program to a device) or start Acts. Crucible never issues cycle start, resume, jog, `Start` or `StoreAndStart` to machine tools, robots, lasers, presses or furnaces; a person starts them at the device. `start_print` exists only for printers whose profile declares thermal-runaway protection and enclosure or smoke detection, and needs an Approval of the job digest plus an on-site confirmation that the build plate is clear, given on the printer or with a site-bound key at the gateway. A Tier 2 or remote approval never gives the on-site confirmation." MFG and AGT adopt one list: `send_to_machine`, `send_print_job`, `start_print`, `send_robot_program`, `store_machine_job` (OPC UA `Store` only); machine data collection is a Read. The OPC UA adapter's capability set excludes `Start`, `StoreAndStart`, `Resume` and `RevokeStart`. Rewrite D-MFG-4: "Agents may prepare transfer Acts; the server executes them only after a human Approval; no agent can give an on-site confirmation." KLN: `unattended_safe` is a signed site policy, never self-declared by a runner and never granted to machine tools, robots or lasers; agent-branch runs still need an Approval of the program digest. MFG robot offline programming: posted robot programs are proved first in the robot's manual reduced-speed mode and never alter the controller's safety configuration (safety-rated zones, speed limits); the robot safety data package cites the 2025 editions above. AGT moves `send_to_machine`, `send_print_job` and `start_print` to phase 1, because MFG and KLN ship those effects in phase 1.

### R4-02 · Critical · Targets: MFG
**Section:** Machine models; Controllers and post-processors; Material removal and machine collision simulation; Oracles.
**Problem:** Collision verification checks the toolpath, not how the control moves between programmed points. The `Controller` record has no fields for rapid traverse interpolation (straight line or each axis at its own rate), rotary rapid direction and unwinding, TCP state during rapids and tool changes, reference-return intermediate points, canned-cycle retract planes, or cutter-compensation entry and look-ahead. Those are where verified programs crash in practice, so the claim that rapids are checked "with the same rigor as cuts" is unsafe as specified.
**Evidence:** MFG: `controller: Controller, // dialect, options, capability flags`; "The model describes nominal kinematics only."; "Rapid-move safety | Rapids checked against stock and fixture with the same rigor as cuts | `Collision` | As above | 1". ISO 6983-1 defines program format and address words (https://www.iso.org/standard/34608.html); positioning (G00) fixes the end point, and the path between points is control-specific [unverified per control; a Fanuc parameter, for example, selects linear or non-linear positioning]. Nothing in the seeded crash corpus specification plants controller-semantics crashes.
**Fix:** Add `MotionSemantics` to `Controller`: `rapid: Linear | PerAxis { rates }`, `rotary_rapid: Shortest | Directional | Unwind`, `tcp_in_rapid: Bool`, `reference_return: ViaIntermediate`, `cycle_retract: { initial_plane, r_plane }`, `cutter_comp: { lookahead_blocks, entry_rule }`, `tool_change_envelope: Body`. Collision simulation and the independent re-interpreter both execute the posted NC text under these semantics, never the pre-post toolpath. Where a semantic is undeclared, the simulator sweeps a conservative envelope (for a rapid, the joint-space box between the endpoints) and reports `Unsupported` instead of passing. Posts get a rule: convert G0 to G1 at a declared rapid-equivalent feed wherever the conservative envelope comes closer to stock or fixture than the declared clearance. Add to the crash corpus: dog-leg rapids through clamps, rotary unwinding through the fixture, reference return through the part, wrong retract plane over a clamp, cutter-compensation entry gouge, tool change inside the work envelope. Gate: zero false negatives on that corpus for each controller family before its post ships.

### R4-03 · Critical · Targets: ELX, KLN
**Section:** ELX Writing a circuit; State of the art (connectivity capture); KLN Merge (D-KLN-21).
**Problem:** Because `connect` accumulates idempotently as a set union, two branches that each attach the same pin to a different net merge without textual conflict and silently short the two nets. None of KLN's five merge conditions catches it: the merged program compiles, Queries resolve, ERC passes unless pin types or voltage domains clash, and DRC follows the merged netlist, so the short becomes the design. ELX's merge target scores this case as a success.
**Evidence:** ELX: "`connect` statements accumulate into one value, and connecting the same pins twice is idempotent."; State of the art target "Scripted concurrent-edit branch pairs, target 100% merged without manual conflict when edits touch different nets". KLN D-KLN-21: merge succeeds when the design "compiles, resolves, passes every check that both parents passed, and shows no new geometric overlap or interference". Example: branch A adds `connect(u1.pin("PA5"), led_net)`, branch B adds `connect(u1.pin("PA5"), button_net)`; the merge joins both nets through PA5.
**Fix:** KLN adds a sixth merge condition: "Connectivity. The driver computes the net partition (pins per net) of base, both sides and merge. A merged net that unions nets that are distinct in the base and in each side is `Conflict::NetMerge`, naming the pins, both nets and both Changes. Net renames are matched by provenance, not by name." ELX adds an ERC rule that two named nets join only through an explicit `tie(...)` element (R4-22). Replace the ELX target with "100% of net-merging branch pairs reported as conflicts; 100% of non-overlapping pairs merged clean". Apply the condition to harness `Circuit`s and `std::systems` interface connections too.

### R4-04 · Critical · Targets: UIX, ELX
**Section:** UIX Modes; Extending the interface; Capability catalog; Migration from other CAD tools; ELX Interactive routing; What this tab requires (UIX row).
**Problem:** UIX hosts electronics only as Wasm panels that return element trees, may not draw pixels and get 2 ms of CPU per frame, yet ELX requires schematic and layout editors with push-and-shove routing at 16 ms per mouse move. A layered board canvas with net highlighting, ratsnest, DRC markers and a live router head cannot be built from stacks, grids and overlay glyphs inside 2 ms, and UIX has no Electronics mode, no electronics role and no Altium or KiCad key presets. As written, the board designer's daily tools have no owner.
**Evidence:** UIX: "Domain views from other tabs, such as the electronics board view …, use the same extension points as any third-party package."; panels "never draw pixels or ship shaders"; "Each panel gets 2 ms of CPU per frame."; modes are Design, Simulate, Manufacture and Review; presets "for SOLIDWORKS, Fusion, Onshape and Blender users". ELX: "Targets: under 16 ms per mouse-move update with up to 50 shoved items"; ELX requires "Schematic and layout editors writing `Schematic`, `Layout` and source edits; constraint manager view; waveform, Smith chart, eye diagram and timeline viewers".
**Fix:** UIX adds an Electronics mode (Schematic, Layout) and a public `crucible:ui/canvas2d` world any package may use, so principle 1 holds: a component submits retained 2D primitive buffers (lines, arcs, polygons, text, with layer ids and net ids) that the wgpu renderer draws with layer visibility, opacity, high-contrast and net-highlight modes, and hit-testing uses the same buffers. Tools that compute per pointer move (the router, placement drag with live DRC) run in the engine process on an interactive edit lane like Kiln's drag lane and stream head geometry each frame through `api`; the 2 ms budget applies to panel UI logic only. Specify the schematic canvas (symbols, wires, junctions, labels, sheet frames, cross-references), the layout canvas (layer stack, ratsnest, DRC markers, length-tuning meters) and the constraint-manager grid, with budgets equal to ELX's targets. Add Altium-like and KiCad-like presets and an electronics first-run role. Phase 3, with a UIX oracle that replays ELX's recorded routing sessions at 16 ms or less per update.

### R4-05 · Major · Targets: MFG, AGT
**Section:** MFG Approval and machine safety; Machine and MES connectivity (program transfer); Platform notes.
**Problem:** Approval binding ends where Crucible hands the file over. A control cannot verify a signature, operators routinely edit programs, offsets and feeds at the control, and the controller's actual tool lengths and work offsets decide whether the simulated program is the one that runs; none of this is captured. Large 3D and 5-axis programs on older controls also need drip-feed DNC, which arrives only in phase 3.
**Evidence:** MFG: "Program transfer | Released programs to controllers, bound to the approval hash: signed file export first, then DNC, OPC UA and vendor plugins | Hash mismatch blocks transfer | … | 1 (file export), 3 (DNC, OPC UA)"; "A wrong tool length in the machine or a mis-clamped part is outside what any software can see." MTConnect 2.5 Part 3 lists observation types `PROGRAM`, `PROGRAM_HEADER`, `PROGRAM_EDIT`, `PROGRAM_EDIT_NAME`, `ToolOffsets` and `WorkOffsets` (https://docs.mtconnect.org/MBSD_MTConnect_Part_3_2-5-0.pdf, contents).
**Fix:** (1) Posts write a header comment with item, program revision, release id and a short content hash; the gateway recomputes it on transfer and on read-back. (2) Pre-run verification: before enabling transfer, the gateway reads tool and work offset tables (MTConnect `ToolOffsets` and `WorkOffsets`, OPC UA, a vendor plugin, or operator entry against the setup sheet) and re-runs collision simulation with the actual gauge lengths and offsets; a mismatch beyond the setup-sheet tolerance blocks transfer with `MfgError::OffsetMismatch`. (3) Edit capture: the gateway watches `PROGRAM_EDIT` and the active program header, uploads edited programs (DNC receive) and opens a Proposal with the semantic NC diff against the release; parts made from an edited program get a deviation in the as-built record. (4) Move DNC transfer, including drip feed with XON/XOFF or RTS/CTS flow control, to phase 1 in the gateway. (5) Oracles: recorded edit sessions yield Proposals with exact diffs; a seeded offset-mismatch corpus is blocked 100%.

### R4-06 · Major · Targets: MFG, UIX
**Section:** MFG Tool libraries, Controllers and post-processors, What MFG provides; UIX Toolpath preview and playback, Modes.
**Problem:** Neither tab produces a setup sheet, the document every machinist runs from: tools with holder, stick-out, gauge length, T, H and D numbers and pocket; stock size and material; work offset location and probing instructions; clamping views; program names and cycle times. UIX shows toolpaths but no NC text, although MFG already keeps a `BlockMap` from blocks to toolpath points. A reference shop cannot run GP1 without these.
**Evidence:** 07-manufacturing.md contains no "setup sheet", "tool table" or "G54". UIX toolpath table covers toolpaths, tool and holder, stock, collisions and additive only. MFG: "Each `BlockMap` entry links a posted block to its workingstep, path parameter and content hash."
**Fix:** MFG adds `setup_sheet(program, template) -> Drawing` in phase 1, an Ingot drawing built from the `Program`, tool Assemblies and setup, so it diffs and releases with the program; templates are packages. Content: setup views with the WCS triad and dimensions from the work offset to datum features, fixture and clamp positions, stock definition, tool table (T, pocket, H, D, holder, stick-out, gauge length, flute length, expected life), workingstep list with tool, cycle time and Z extremes, and first-run notes (tool-length verification, reduced override) from MFG's safety text. UIX Manufacture mode adds an NC code panel with two-way highlighting through `BlockMap` (block, toolpath point, workingstep, design feature) and a setup-sheet preview. Oracle: every tool in the program appears once in the table, with gauge length equal to the tool Assembly's analytic stack-up.

### R4-07 · Major · Targets: MFG
**Section:** Core manufacturing types; Machine models; Fixture and jig design; Phasing.
**Problem:** A `Setup` holds one part Instance and one `datum: Transform`, and a `Program` holds one setup, so everyday setups cannot be expressed: two parts in a double vise, op 1 and op 2 in one vise and one program, a tombstone with eight work offsets, extended offsets, pallet changers. Fourth-axis indexing and rotary wrapping on vertical machining centers appear nowhere, and vises, modular fixtures, soft jaws and probing wait for phase 2 although GP1 needs workholding.
**Evidence:** MFG: `pub record Setup { machine, fixture, stock, part: Instance, datum: Transform }`; `pub record Program { setup: Setup, steps: [Workingstep] }`; "Modular fixtures … | 2", "Soft jaws and nests … | 2", "Probing … | 2"; "4-axis" appears only for wire EDM.
**Fix:** Replace with `Setup { machine, fixture: Assembly, stations: [Station] }`, `Station { part: Instance, stock: Body, wcs: WorkOffset }`, `WorkOffset { number: WcsId, frame: CoordSys }` (G54 to G59, extended and fixture offsets as the controller declares) and `Program { setups: [Setup], order: ByTool | ByStation }`. Add 4th-axis indexing (3+1) in phase 1 and rotary wrapping in phase 2, with A or B rotary kinematics in machine models. Move vise and modular-fixture catalog parts (jaw stroke, clamping force) and work-offset probing cycles to phase 1. Oracle: a tombstone corpus in which each station's toolpath is verified in its own WCS and posted offsets match the setup sheet.

### R4-08 · Major · Targets: MFG
**Section:** Controllers and post-processors.
**Problem:** Post tuning is the most frequent CAM customization in a shop, but logic that data cannot express needs Rust compiled to Wasm, which shop post editors will not write and which contradicts the contract's Ingot-first tier rule. There is no path from a shop's proven posts and programs (machine-builder M-codes, tool-change macros, safe-start blocks, probing macros) to Crucible posts.
**Evidence:** MFG: "Post extension hooks | Rust Wasm component hooks for logic that data cannot express | … | 2". Contract §4: "Use Ingot unless code needs more than about 10⁶ primitive steps per call, an existing codebase in another language, or a data structure Ingot cannot express efficiently".
**Fix:** Post hooks are Ingot functions over typed block events (`on_program_start`, `on_tool_change`, `on_wcs_change`, `on_rapid`, `on_cycle`, `on_program_end`) in phase 1; Rust Wasm hooks only for the contract's exceptions. Add post qualification against legacy output: the shop supplies a proven program from its current CAM for a reference part, and Crucible's semantic NC diff must show only differences on a declared list; the qualification record ships in the machine package. Machine packages carry machine-builder customizations (M-code map, tool-change macro, coolant variants, chip conveyor, spindle warm-up) as data. Oracle: per controller in the conformance corpus, the posted reference program equals the shop's proven program modulo the declared list.

### R4-09 · Major · Targets: MFG, ECO
**Section:** MFG Rust surface, Oracles; ECO Manufacturing and metrology, Migration from incumbent tools.
**Problem:** Shops hold thousands of proven NC programs from other CAM systems and from hand programming, and they need to verify them (backplot, material removal, machine collision) and keep them under revision control. MFG makes the NC interpreter oracle-only and offers no capability to simulate external NC, and ECO's migration lists no manufacturing data.
**Evidence:** MFG: `pub trait NcInterpreter { // independent implementation, used only by oracles`. ECO: G-code "W; R for verification"; "What can move" lists parts, assemblies, PMI, mates, metadata, drawings and PDM history only.
**Fix:** Add `verify_nc(nc: Asset, machine, setup, tools) -> (stock, collisions, gouges, cycle time, BlockMap)` in phase 1 on a product interpreter kept separate from the oracle interpreter, so the oracle stays independent. Legacy programs import as Items (kind `Program`, see R4-11) linked to part revision and machine, with the same approval and transfer path. ECO's migration table adds NC programs (verified, never converted to workingsteps), tool libraries (R4-10), post configurations (R4-08) and setup sheets as Assets. Oracle: hand-written and third-party-CAM programs with planted crashes, all detected.

### R4-10 · Major · Targets: MFG, ECO
**Section:** Tool libraries.
**Problem:** ISO 13399 import is necessary but is not how tool data reaches shops: vendors publish packaged catalogs (GTC packages built on ISO 13399, and DIN 4000 property lists [unverified]), shops keep libraries in their current CAM, and measured lengths come from presetters. Holders lack a full collision-body rule, there is no per-machine tool table, and tool-life tracking waits for phase 4.
**Evidence:** MFG: "ISO 13399 import | Vendor packages to Catalog parts … | 1"; "Shop library | A package of tool Assemblies with pocket numbers and measured lengths"; "Tool wear and life | … | 4". ISO 13399-1:2006 was last confirmed in 2021 (https://www.iso.org/standard/36757.html).
**Fix:** Phase 1 importers (tool context): ISO 13399 Part 21 data inside vendor catalog packages, DIN 4000 property mapping, and the documented tool-library formats of the most common incumbent CAM systems [unverified which are documented]; presetter readings (length, radius, runout) as signed External inputs keyed by tool-assembly serial. Holders and extensions are full collision Bodies. Per-machine tool tables map tool Assemblies to T number, pocket and H and D registers, and posts read them. Count-based tool life (minutes or parts per edge) moves to phase 1; model-based life stays in phase 4. Oracle: a vendor package round trip with geometry within 1 µm and properties unchanged; conflicting tool-table entries fail the build.

### R4-11 · Major · Targets: KLN, MFG
**Section:** KLN Items and item numbers, Change management; MFG Approval and machine safety, MBOM and routings.
**Problem:** Every NC program, routing or work-instruction change goes through the engineering release path, but shops change programs daily (feeds, step-downs, a better tool) without touching the part definition. Without a manufacturing change lane with its own revisions and approvers, either engineering change control drowns in shop edits or programmers bypass it.
**Evidence:** MFG: "The release is a signed tag in `repo`. Released programs are immutable artifacts in CAS."; KLN Item kinds are "`Part`, `Assembly`, `Document`, `Software`, `Purchased`"; KLN's change-order sequence has no manufacturing-only variant.
**Fix:** KLN adds a manufacturing change order (MCO) policy class: scope limited to MBOM, routings, programs, fixtures, work instructions and inspection plans; a check rejects any change to an EBOM Item definition; approvers are manufacturing roles; programs and routings carry their own revision sequence and effectivity by work order or lot, with states `Prototype` (first-article run under a deviation), `Proven` (after a passing first-article record) and `Released`. Add Item kind `Program`. MFG step 4 becomes "release through an MCO". Oracle: an MCO touching an EBOM definition is rejected; an ECO changing a part invalidates exactly the dependent programs.

### R4-12 · Major · Targets: KLN, MEC, MFG, UIX, AGT
**Section:** Phasing in each tab.
**Problem:** The GP1 chain is phased inconsistently. MEC title blocks read item and revision from `repo` and drawings carry BOM tables in phase 1, MFG rolls up BOM cost and releases programs in phase 1, and UIX's phase-1 gate approves GP1 through the UI; but KLN delivers Items, revisions and BOM views in phase 2, UIX delivers toolpath playback and the cost panel in phase 2, chamfer and deburr toolpaths (needed for edge breaks on any machined part) are phase 2, and AGT's CAM programmer role is phase 2 while MFG ships agent-proposed toolpaths in phase 1.
**Evidence:** KLN phasing: "2 Mechanical depth | … | … Items, revisions, change orders …; EBOM, MBOM and SBOM views". MEC: "Sheets and title blocks | … read item, revision and approvals from `repo` | 1"; "Tables | BOM … | 1 (BOM, holes), 2". MFG: "BOM roll-up | `repo` BOM query … | 1"; "Deburr and chamfer | … | 2"; agent-proposed toolpaths "Phase 1". UIX: "Toolpath playback | … | 2"; "Cost panel | … | 2". AGT role catalog: CAM programmer, phase 2.
**Fix:** KLN phase 1 adds a minimal lifecycle: item numbers, revision labels on release tags, `InWork` and `Released` states and the EBOM view; full change orders, effectivity and MBOM stay in phase 2. UIX moves toolpath playback, the NC view (R4-06) and the cost panel to phase 1. MFG moves 2D chamfer and edge-break toolpaths to phase 1. AGT moves the CAM programmer role to phase 1, or MFG moves agent proposals to phase 2; state the same choice in both tabs. KLN either delivers the interchangeability check with change orders in phase 2 or states that phase-2 change orders take a human verdict.

### R4-13 · Major · Targets: MFG
**Section:** Process categories; Printer profiles, 3MF and machine connectivity; Phasing.
**Problem:** The phase-1 wedge assumes Crucible's own FFF slicer drives printers through OctoPrint, Moonraker and PrusaLink. The slicers people use carry years of printer and filament profiles, and the most common professional desktop printers impose formats and access rules the spec ignores: Bambu Lab firmware routes third-party control through Bambu Connect, also in LAN mode, and Prusa's binary G-code has an AGPL reference library.
**Evidence:** MFG: "Material extrusion | FFF … | G-code (Marlin, Klipper, RepRapFirmware flavors)"; "Printer connectivity | Send, start, pause, cancel, monitor … | 1". Bambu Lab, 16 January 2025: Bambu Connect "removes slicing functions while enabling remote control and print initiation", and the restrictions apply in LAN mode (https://blog.bambulab.com/firmware-update-introducing-new-authorization-control-system-2/). libbgcode is AGPL-3.0 (https://github.com/prusa3d/libbgcode).
**Fix:** The phase-1 default for FFF is slicer hand-off: write a 3MF build with plates, per-object orientation, modifiers and settings in the metadata that OrcaSlicer, Bambu Studio and PrusaSlicer read [unverified per slicer], and open it in the user's slicer. Crucible's native slicer stays for what only it does (direct slicing of implicit lattices for GP2, Field-driven infill) and becomes the default only after matching the reference slicers on the stated thin-wall corpus and on print time. Write bgcode from the published format description, never linking libbgcode. Reach Bambu printers only through the vendor's sanctioned path and say so. Printer start follows R4-01.

### R4-14 · Major · Targets: MFG, MEC
**Section:** MFG Inspection planning and CMM programming, First-article inspection and PPAP; MEC Drawings.
**Problem:** MEC drawings have item balloons tied to BOM lines but no characteristic balloons, and D-MFG-18 rejects balloon numbers as identity without saying where printed balloon numbers come from, how they stay stable across revisions, and how Form 3 rows match them. Job shops, the GP1 audience, mostly inspect against customer PDF drawings with no Crucible model, and D-MFG-18 extracts characteristics only from native GD&T.
**Evidence:** MEC: "balloons tied to BOM items". MFG D-MFG-18: "*Rejected:* balloon numbers as identity"; "Characteristic extraction | Design -> characteristics … with balloons | … | 2". IAQG's summary of 9102 revision C adds definitions for "Ballooned Design Characteristic" and "Ballooned Document" (https://ma.iaqg.org/wp-content/uploads/2019/10/9102_Changes_07112023.pdf).
**Fix:** MEC adds a characteristic-balloon annotation kind bound to D-MFG-18 identities. Labels are allocated once per identity, never reused, kept for unchanged characteristics across revisions and renumbered only by explicit command; each release produces the ballooned PDF that Form 3, inspection plans and reports cite. MFG adds a foreign-drawing workflow in phase 2: import a customer PDF as a controlled document, place balloons by hand or through an agent extraction Proposal with page coordinates, and create typed characteristics (nominal, limits, feature type) linked to the customer STEP when present. Oracle: a revision that changes one dimension changes one balloon's content and no labels; Form 3 rows equal the balloon set.

### R4-15 · Major · Targets: MFG
**Section:** First-article inspection and PPAP; Statistical process control.
**Problem:** The PPAP row lists an unverified partial element set, omits submission levels and has no measurement system analysis, which PPAP requires and which method selection needs. PFMEA names no method, although automotive customers expect the AIAG and VDA approach.
**Evidence:** MFG: "PPAP | Submission package with process flow …, PFMEA and control plan links, MSA, dimensional results, capability studies, material results and the part submission warrant [unverified for element list]"; SPC covers control charts and capability only. AIAG lists PPAP 4th edition as current (https://www.aiag.org/training-and-resources/manuals/details/PPAP-4). The AIAG and VDA FMEA Handbook is in its first edition, second printing, with a 7-step PFMEA approach (https://www.aiag.org/training-and-resources/manuals/details/FMEAAV-1).
**Fix:** Model PPAP as a data package for the 4th edition: the element list (design records, engineering change documents, customer engineering approval, DFMEA, process flow, PFMEA, control plan, MSA studies, dimensional results, material and performance test records, initial process studies, qualified laboratory documentation, appearance approval report, sample parts, master sample, checking aids, customer-specific requirements, part submission warrant) and the level 1 to 5 retention matrix, with customer-specific overlays. Add MSA to SPC in phase 3: gauge R&R by average and range and by ANOVA, bias, linearity, stability and attribute agreement, with study records linked to gauges and characteristics; method selection reads the measured %GRR. PFMEA and DFMEA follow the handbook's 7-step structure with action priority, DFMEA linked to MEC checks. Customer special-characteristic symbols are data.

### R4-16 · Major · Targets: MEC, KLN, UIX
**Section:** MEC Drawings; KLN Revisions and lifecycle states; UIX Drawings and model-based definition.
**Problem:** Drawings get a revision table but no revision markers. Practitioners flag each changed item with a revision symbol or cloud and list the change by zone; Crucible has the semantic diff to generate them, but no tab specifies it. Tabulated drawings, the usual way to document dash-number families, are also missing.
**Evidence:** MEC: "Tables | … revisions (from `repo` releases and change orders) …"; no tab specifies revision clouds, revision symbols or tabulated drawings. ASME lists Y14.35-2025 as the current edition of the revision standard (https://www.asme.org/codes-standards/find-codes-standards/y14-35-revision-engineering-drawings-associated-documents).
**Fix:** MEC adds `revision_markers(drawing, from: Release, to: Release, style: Delta | Cloud)`: the annotation and view diff between two releases places a symbol beside each changed item, fills the revision block with change-order number, description and zone, and regenerates at release. Markers and revision text are late-bound release fields excluded from the definition digest (R4-17). Drafting packages carry Y14.35-2025 rules and the ISO practice. Add tabulated drawings driven by `family` rows. Released drawings are also written as PDF/A [unverified part] for archive. Oracle: a release changing two dimensions yields exactly two markers and one revision row.

### R4-17 · Major · Targets: KLN, MEC, ELX
**Section:** KLN Revisions and lifecycle states (D-KLN-26); Keys and behavior versions.
**Problem:** "Modified since release" compares evaluated `ItemDefinition`s, which include B-rep `ObjectId`s and controlled documents, so an engine or std upgrade that changes bits within tolerance, or a drafting-package update that re-renders PDFs, marks every released Item modified: the noise D-KLN-26 exists to remove. The rule is also circular wherever revision text is part of the content: title blocks, silkscreen revision marks and engraved part markings change when the revision is assigned.
**Evidence:** KLN: "The `ItemDefinition` record holds the canonical evaluated Part or Assembly `ObjectId`, …, the product manufacturing information (PMI), properties and controlled documents."; "Upgrading versions is an explicit Proposal that shows the geometric and metric diff". MEC title blocks "read item, revision and approvals from `repo`".

### R4-22 · Major · Targets: ELX, UIX
**Section:** ELX Writing a circuit (schematic module and editor behavior); Electrical rule checks.
**Problem:** The stored drawing models pin-to-pin wires only, so real schematics cannot be stored: wires meeting wires at junctions, power symbols, no-connect flags, bus entries, sheet symbols. Nothing stops the drawing from lying: a code edit can leave a drawn wire between pins that are no longer connected, and only removed pins are caught. Labels are drawing items, although in every schematic tool a label is connectivity, and net ties (an intended short at one point) have no representation although IPC-2581C carries intended net shorts.
**Evidence:** ELX: `wire w_3c1 [u1.pin("SW"), l1.a] path [(78mm, 40mm)]`; "A wire end that touches no pin is impossible: the editor snaps or refuses."; "Annotations that point at removed pins fail with `SchematicError::StaleAnnotation`"; ELX contains no schematic junction or "net tie". **Fix:** The `Schematic` module stores drawn topology: segments whose ends lie on pins, labels, power symbols, sheet pins or other segments (explicit junctions), plus no-connect flags and bus entries.
