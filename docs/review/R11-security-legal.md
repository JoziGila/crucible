# R11 security and legal review

Summary:
1. Labels cannot work as written: integrity flags sit in the confidentiality order, so every tainted edit is a "write-down" while one human's endorsement lowers a label, and an external host resets its context label with a second OAuth grant or a stdio relaunch (R11-01, R11-04).
2. Untrusted free text survives evaluation as plain `String` values and embossed geometry, so R5-02's injection channel reopens through the scene graph, BOMs, diagnostics and snapshots (R11-02).
3. Trusted builders and the registry's builders run third-party code with attestation authority, and two-builder agreement cannot stop a deterministic exploit, so R5-03's fix does not hold (R11-03).
4. Legally, Crucible's own CAD, CAM and PLM fall under EU and US Russia and Belarus software bans the spec never names, std ships ISO and ASME tables under Apache-2.0, and the registry ignores the Digital Services Act (R11-27, R11-30, R11-29).

### R11-01 · Critical · Targets: CONTRACT, AGT, KLN
**Section:** Contract 5 `Labels`, 7.1 `repo`, 7.6 "Context labels and write-down", 7.8; AGT "Labels and injection defence"; KLN "Labels and export control", "Encryption at rest", "Live documents"
**Problem:** Contract 5 puts `integrity` inside one product lattice whose join is "the union of each set", and 7.6 fails every write "to a destination with a lower label" unless two people, one an export officer, sign a declassification. Integrity flags therefore count as "higher": a `data_untrusted` context editing its own branch of a clean repository is a write-down, which contradicts AGT's Rule-of-Two table ("Edit own branch: Yes"). Conversely `propose.endorse_text` lowers a span's integrity with one human, while KLN says "Lowering a label needs a declassification record signed by two people, one an export officer". The same lattice keys encryption domains and live-replication units, so every combination of integrity flags becomes its own domain and its own Loro document, and the read rule ("a principal may read a value only if it satisfies every element") has no meaning for integrity.
**Evidence:** Contract 5: "The join takes the maximum level and the union of each set. A principal may read a value only if it satisfies every element." Contract 7.6: "A write to a destination with a lower label fails with `label.write_down` unless a declassification record signed by two people, one of them an export officer, names it." AGT "Taint and the Rule of Two" allows `data_untrusted` and `instruction_tainted` contexts to edit their own branch. Contract 7.8: "Encryption domains are keyed by tenant and canonical label set"; 7.1: "blocks labelled above a document's label live in a separate document". No tab separates integrity from these comparisons (grep of AGT and KLN for "confidentiality" finds nothing).
**Fix:** Amend contract 5: `Labels` has two parts. The confidentiality part `C = { level, controls, scopes, licences }` is a lattice with join, read rule, clearance and write-down. The integrity part `I = { instruction_tainted, data_untrusted }` joins through derivations but never blocks a read or a write; it is lowered only by endorsement (text spans, and Assets per R11-13), never by declassification. Amend 7.6: write-down compares `C` only; integrity sets risk classes and taint as AGT specifies. Amend 7.1 and 7.8: live-replication units and encryption domains key on the canonical `C` only; integrity travels as span provenance and as a per-object field. Endpoint, client and recipient clearances bound `C` only. Add to AGT-O-17: a tainted context's edit to a clean branch succeeds at R3, and an `endorse_text` changes integrity without a declassification record.

### R11-02 · Critical · Targets: ING, KLN, AGT, CONTRACT
**Section:** ING free-text spans (D-ING-24) and `String`; AGT "Structured scene graph", "Sections and descriptions", "Snapshots and Field overlays" (D-AGT-26), "Errors as guidance"; KLN "Storage, Git export and span provenance"; contract 7.6 "Free text is never endorsed by merging"
**Problem:** The handle rule covers source spans returned by `read.source`, `read.outline`, `read.docs` and `inspect.describe`, but a string literal written by a tainted agent becomes an ordinary runtime `String` once Kiln evaluates it: a part name, a BOM line description, a drawing note, a requirement statement, a check name, or text embossed into geometry. Those values reach clean sessions through `inspect.scene`, `read.bom`, `compare.diff`, CI reports, compiler diagnostics that quote source, and snapshots, all of which AGT declares non-tainting. Snapshots count as untrusted only when a Body "derives from an untrusted Asset", so an `emboss("…")` feature fed by an agent-written literal produces an instruction-capable image that every later vision call reads as trusted. This reopens R5-02's Critical channel one evaluation step later.
**Evidence:** ING: "`String`, `ExternalText` | Immutable NFC text; untrusted text from outside the design, written `external("…")` … never implicitly a `String`". Contract 6: `part(solid, name: "Bracket")`. AGT: "The scene graph, measurements and descriptions stay non-tainting, because they carry typed values and handles only." D-AGT-26: "A snapshot is untrusted and instruction-capable when the geometry or appearance of any visible Body derives from an untrusted Asset." KLN's node label is "the join of its inputs' labels"; span integrity is recorded in `repo` but no tab says it enters a Kiln label.
**Fix:** (1) ING: every value evaluated from a free-text span (string literal, description template, untrusted identifier) carries that span's integrity, and Kiln joins it into the integrity part of the node's label (R11-01). (2) AGT: every string-typed field in every method response (scene node names, item and BOM text, check and requirement names and statements, diagnostics quoting source, CI reports, diff text, description facts) whose producing node has untrusted integrity is returned as an `ExternalText` handle; state this in D-AGT-18 and in the method contracts. (3) Revise D-AGT-26: a snapshot or section SVG is instruction-capable when any visible Body, text, annotation or overlay derives from a node with untrusted integrity, from an Asset or from source. (4) Extend AGT-O-8 and ECO-O-18 with part names, BOM descriptions, drawing notes, diagnostics and embossed-text features written by a tainted context and merged by a human.

### R11-03 · Critical · Targets: CONTRACT, KLN, ECO, PLT
**Section:** Contract 7.8; KLN "Shared cache and remote evaluation" (D-KLN-9); ECO "Publishing and signing" (pipeline steps 2, 5 and 7); PLT "Tier 3 and servers", D-PLT-31
**Problem:** R5-03's fix trusts machines by what they run, but both trusted pools run third-party code. Tenant trusted builders evaluate merged revisions, which pull in third-party Wasm components and packages that no human reviewed when merging; PLT isolates those only as OS-sandboxed processes "one per (tenant, label set)" on hosts that may serve several tenants. The operator's registry builders run "std and public packages" (test vectors, acceptance checks) while holding "operator keys" and writing the global public domain. A sandbox escape is deterministic, so the same malicious package compromises every builder that runs it, and 2-of-n agreement then signs the poisoned value; two-builder agreement only defends against faults.
**Evidence:** KLN role table: "Operator registry builders | std and public packages | Operator keys | The global public domain, with 2-of-n agreement". ECO pipeline: "2. Rebuild hermetically … 5. Run domain acceptance checks contributed as data … 7. Run test vectors on every engine". PLT: "Trusted builders evaluate merged revisions of protected branches in one process per (tenant, label set)". Contract 7.8: "Release gates and every `SignOff` check accept a cached result only when two independent trusted builders produced the same `ObjectId`." D-ECO-26 justifies isolation by Wasmtime's 2026 escape-class advisories.
**Fix:** Amend contract 7.8: (1) Trusted builders and registry builders execute every Wasm component and package from outside std, `crucible::` and first-party translators only inside single-use microVMs, with the host computing output `ObjectId`s; OS-process sandboxes are not a trust boundary for attestation. (2) A node whose dependency closure contains third-party code is attested only into its tenant's domain, by builders dedicated to that tenant (no host shared across tenants). (3) The global public domain holds only results whose closure is first-party, produced by registry builders that never run third-party code; publish-time test vectors and acceptance checks for third-party packages run on untrusted-evaluation workers and never enter the global domain. (4) The hermetic builder for first-party packages, whose output runs inside the engine process, never builds third-party packages. (5) State that two-builder agreement protects against faults, not deterministic exploits. Add to KLN-O-TRUST-1 a planted package that escapes identically on every builder.

### R11-04 · Critical · Targets: CONTRACT, AGT
**Section:** Contract 7.6 "Context labels and write-down"; AGT "Context labels and write-down" (D-AGT-24), "Platform notes"; Open questions 10
**Problem:** For external hosts the model context is the OAuth token family, and "an external host gets a fresh label only through a fresh authorization grant". Crucible cannot see the host's conversation, so one conversation can hold two token families at once (two server entries for the same Crucible server) or re-authorize, and read under one label while writing under another, clean one. The most common desktop path, `crucible mcp` on stdio with the user's keychain credential, has no OAuth token family at all, so its context is undefined, and a relaunch of the stdio server is the natural candidate for a "fresh" context. Write-down and every integrity flag (and with them risk classes and auto-merge eligibility) can therefore be reset by the host.
**Evidence:** Contract 7.6: "for external MCP hosts it is the OAuth token family (client instance plus user), shared by every session that family opens." AGT: "An external host gets a fresh label only through a fresh authorization grant." AGT Platform notes: "`crucible mcp` runs on stdio with the user's keychain credential". AGT open question 10 asks whether "one family per workspace" is right.
**Fix:** Amend contract 7.6 and D-AGT-24: an external host's model context is (user, client identity), where client identity is the registered key of an attested client (D-AGT-19) and otherwise one shared "unattested" identity per user. Every token family, refresh, concurrent grant and stdio launch of that pair joins one monotone label, stored server-side. A label resets only through `session.reset_context`, which the human performs on the approval page with WebAuthn, attesting that the host conversation was cleared; the reset is audited and shown in provenance. Answer to AGT open question 10: one context per (user, client identity), not per workspace, because Crucible cannot observe host workspaces; the reset action is the escape hatch for accumulated flags. Add to AGT-O-17: two concurrent grants, a re-authorization and a stdio relaunch all keep the label.

### R11-05 · Major · Targets: UIX, AGT, PLT
**Section:** UIX "Approvals" (D-UIX-29); AGT "Acts and approvals" (D-AGT-20); PLT "OS services" (`Authenticator`)
**Problem:** The approval page is "rendered verbatim" by the desktop, web and tablet clients, but no tab isolates it from the rest of the client. In the web app it shares an origin with views that render untrusted content (imported names, SVG sections, Markdown descriptions, panel element trees), so a script injection there can fetch a pending approval challenge and start a WebAuthn ceremony under a pretext such as "confirm it's you"; the passkey prompt shows only the relying-party name, never the plan. On desktop, any UI code can call PLT's `Authenticator`.
**Evidence:** UIX D-UIX-29: "desktop, web and tablet clients render verbatim from the server's record". PLT: "`Authenticator` returns WebAuthn assertions with user verification for the approval page". No tab names an origin, relying-party id, content security policy or caller restriction for the approval ceremony.
**Fix:** Add to D-AGT-20 and D-UIX-29: the approval page is served from a dedicated origin (for example `approve.<deployment>`) with its own WebAuthn relying-party id, so credentials registered for the main app cannot approve; it renders only server-generated text under a strict CSP (`default-src 'none'`, scripts by hash); approval challenges are issued only to that origin (`SameSite=Strict` cookies, no CORS). The challenge is the hash of (plan digest, request id, approver id). Desktop and tablet clients open this origin in an isolated webview or the system browser; PLT's `Authenticator` is callable only from that view. Extend UIX-O-APPR-1 with a scripted main-origin page that tries to complete an approval.

### R11-06 · Major · Targets: CONTRACT, AGT, UIX, KLN
**Section:** Contract 7.6 "Act approvals", 9 Tier 2; AGT D-AGT-20; UIX "Approvals"; KLN "Electronic signatures"
**Problem:** "No Act of any risk class is approvable on a phone" has no enforcement mechanism: WebAuthn does not reveal the device class, user-agent strings are client-controlled, and synced passkeys created on a phone are usable on any device. Synced passkeys are also exportable keys, which NIST SP 800-63B-4 bars from AAL3, yet they would sign export-officer declassifications, R4 Act approvals and Part 11 signatures. UIX-O-APPR-1's "phones … are refused" is therefore not machine-checkable as specified.
**Evidence:** NIST SP 800-63B-4: "syncable authenticators SHALL NOT be used at AAL3" and AAL3 requires "a cryptographic authenticator with a non-exportable private key" (https://pages.nist.gov/800-63-4/sp800-63b.html). UIX: "phone: 'approve on a desktop or tablet'". KLN signs with "ECDSA P-256 keys in platform keystores or WebAuthn authenticators".
**Fix:** Replace the phone rule with an enrolment rule in contract 7.6: approvals and signatures need a device-bound (non-exportable) credential registered through an enrolment that records device class, from a Crucible desktop or tablet app (which reports its form factor through the platform API) or a roaming security key whose attested AAGUID is on an allowlist. Synced passkeys may sign in but never approve or sign. Export-officer actions, R4-class Acts and Part 11 signatures require AAL3. KLN's signature record stores `authenticatorData`, `clientDataJSON` (challenge = the signed `ObjectId`) and the credential's attestation, so the record verifies offline. UIX-O-APPR-1 then tests "credential not enrolled for approval" instead of "phone".

### R11-07 · Major · Targets: MFG, AGT, KLN
**Section:** MFG "Approval, transfer and physical safety" (D-MFG-24), "Factory connection and digital twin" (D-MFG-20); AGT D-AGT-31
**Problem:** The gateway checks a short content hash that the post writes into the program header, which detects corruption but not substitution: a compromised server, relay or account can send any program with a self-consistent header, and the gateway never verifies that an assigned human approved that program. The approval therefore ends at the server, not at the machine. No tab states OPC UA security mode or certificate trust for the gateway's sessions.
**Evidence:** D-MFG-24: "Posts write item, revision, release id and a short content hash into the program header, and the gateway recomputes the hash on transfer and on read-back." D-AGT-31 makes approval "of the exact plan" the safety control. MFG has no occurrence of an OPC UA security policy or IEC 62443.
**Fix:** Add to D-MFG-24: the gateway transfers only a program whose full SHA-256 appears in an `ActionPlan` carrying a valid Approval assertion from a principal in the gateway's locally pinned approver set (a signed directory plus a transparency-log checkpoint), verified on the gateway itself; the short header hash stays only for operator display. OPC UA sessions use `SignAndEncrypt` with application certificates in a trust list managed by the site, and the gateway sits in an OT zone with one outbound conduit. Extend MFG-O-SAFE tests with a forged plan from a compromised server.

### R11-08 · Major · Targets: CONTRACT, KLN, ELX, COV
**Section:** Contract 2 External Op, 7.3, 7.8; KLN "Determinism policy"; ELX D-ELX-12, D-ELX-25
**Problem:** External Ops run only on untrusted-evaluation workers, but 7.8 lets release gates and `SignOff` checks accept a result only from two trusted builders, otherwise "they recompute", which for an External Op means another untrusted run. A `SignOff` check over an IBIS-AMI eye, an ngspice vendor-model run (ELX's default) or a GPL solver is therefore either never acceptable or silently exempt, and nothing binds the pinned result to the run that produced it: the guest computes its own outputs and no receipt is signed.
**Evidence:** Contract 7.8: "Release gates and every `SignOff` check accept a cached result only when two independent trusted builders produced the same `ObjectId` … otherwise they recompute." Contract 2: External Ops run "only on untrusted-evaluation workers". D-ELX-25: "Imported vendor models run by default in ngspice as an External Op". KLN: "External Op results | The host's class or `Unverified` | Only as `ObjectId`s the release pins".
**Fix:** Add an External Op rule to contract 7.8: a release gate or `SignOff` check accepts an External Op result when two single-use runs on different untrusted hosts produce the same output `ObjectId`, computed by each host outside the microVM and recorded in an execution receipt signed by a receipt key that never signs shared-cache attestations. Nondeterministic External Ops yield `Unverified` evidence that meets a gate only under a policy allowance, like a conditional `Pass`. KLN-O-TRUST-1 adds a forged guest output.

### R11-09 · Major · Targets: CONTRACT, PLT, KLN, ECO, ELX
**Section:** Contract 7.8; PLT "Tier 3 and servers", "The compute runtime" (stdio MCP sandbox); ECO "Where translators run", "Tiers and contexts"; ELX "Engine choice"
**Problem:** Every native-code path receives labelled design data, and none states a network policy: External Op microVMs (vendor AMI libraries, emulators, vendor SPICE engines), the licensed-translator host, processes spawned through `crucible:tool/process`, and stdio MCP servers. Vendor engines also need licence servers, so egress cannot simply be absent. Untrusted native code with labelled inputs and an open socket is a direct exfiltration path that bypasses `release_data`.
**Evidence:** Contract 7.8 says untrusted workers "hold no attestation key and write only to a per-Proposal namespace", with no network rule. PLT: stdio MCP servers run "with only their pipes and user-granted folders". ECO's tool context imports `crucible:tool/process`. D-ELX-25 runs encrypted models "in their vendor's engine … where the user holds a licence".
**Fix:** Add to contract 7.8: every External Op host, translator host, spawned tool process and stdio MCP server runs with network egress denied by default; a manifest may declare named egress endpoints (a licence server, an MCP server's API host), which an administrator grants per organization and which the sandbox enforces by address, never by DNS name alone. A host with any egress grant may receive only inputs whose confidentiality label is at most `internal` and carries no `controls`, unless a two-person grant (D-AGT-27) names that host and label. PLT-O-WASM-6 and ECO-O-8 add a native guest that tries DNS, TCP, UDP and HTTP egress.

### R11-10 · Major · Targets: KLN, PLT, CONTRACT
**Section:** KLN "Shared cache and remote evaluation", "Audit and encryption", "Phasing" (phase 1); contract 13.2 phase 1 scope
**Problem:** Phase 1's single-node team server is the only trusted builder and also runs microVM Proposal CI "on its host", while it holds the release-tag key, the signed audit log and the attestation role. Contract 7.8's separation of pools collapses onto one machine for the whole wedge, so one microVM escape reaches every key, exactly R5-03's failure. Firecracker also needs KVM, which a team server inside a cloud VM may lack.
**Evidence:** KLN: "In phase 1 the single-node team server is the only trusted builder, so release gates and `SignOff` checks recompute, and Proposal CI runs in microVMs on its host." KLN phase 1 includes "the release Act over approval subjects" and "a signed append-only audit log".
**Fix:** Add a phase 1 deployment rule to KLN: signing keys (release tags, audit log, attestation) live in a TPM, HSM or OS keystore whose signing service accepts requests only from the trusted-builder process over an authenticated local channel, never from the CI coordinator; Proposal CI uses Firecracker where KVM is present and gVisor otherwise, chosen and reported by the preflight check; External Ops are not offered on a single-node server; and every release on a single-node server records "single host" in its provenance. KLN-O-DEPLOY-2 adds a microVM-escape tabletop test showing which keys remain unreachable.

### R11-11 · Major · Targets: ECO, PLT
**Section:** ECO "Isolation and platforms" (D-ECO-10); PLT "Isolation of third-party Wasm components" (D-PLT-31), "Isolation and sign-in"
**Problem:** The browser sandbox for third-party Wasm components is "an opaque-origin sandboxed worker with no OPFS, cookies or credentials", but an opaque origin can still `fetch` any URL and send data in the request, since CORS restricts reading responses, not sending. The sandbox exists for the case where the Wasm sandbox fails, and in that case the worker holds the call's labelled inputs and an open network. The mechanism is also unspecified: workers have no `sandbox` attribute, so it must be a sandboxed iframe, which needs its own cross-origin-isolation headers to use threads.
**Evidence:** D-ECO-10: "Third-party Wasm components run in a separate opaque-origin sandboxed worker with no OPFS, cookies or credentials, exchanging data by `postMessage`". D-PLT-31: "a worker inside an opaque-origin sandboxed iframe without OPFS, cookies or keys". Neither mentions network.
**Fix:** Amend D-PLT-31 and D-ECO-10: the sandbox is an `<iframe sandbox="allow-scripts">` loaded from a dedicated sandbox site (a different registrable domain, so browsers place it in a separate process), whose document and worker scripts are served with `Content-Security-Policy: default-src 'none'; script-src 'self' 'wasm-unsafe-eval'` (which blocks `fetch`, WebSocket and `importScripts`), `Cross-Origin-Embedder-Policy: require-corp` and `Cross-Origin-Resource-Policy`. Data cross by transferable `ArrayBuffer`s. ECO-O-8 adds a red-team component that, given JavaScript execution in the worker, tries `fetch`, WebSocket, `importScripts` and navigation.

### R11-12 · Major · Targets: AGT
**Section:** "Risk classification" (D-AGT-16), "Auto-merge" (D-AGT-17), "Independent verifier", "Quarantined extraction and external hosts" (D-AGT-25)
**Problem:** R1 and auto-merge require "every authoring context clean", but for an external host Crucible sees only what it returned itself; the host's model may have read a poisoned web page, a local file or another MCP server's output before calling Crucible. "Clean" therefore means "clean as far as Crucible saw", which the tab presents as a property of the context. The same blind spot makes phase 1 verifier independence a claim about server session lineage only: one host conversation can run both the author and the "fresh" verifier under two agent principals of the same human. `allow_raw_external` "records the host's tool inventory", which the host self-reports.
**Evidence:** AGT risk table, R1: "every authoring context clean". D-AGT-17: auto-merge "only to R0 and R1 Proposals whose authoring contexts were all free of `instruction_tainted` and `data_untrusted`". "In phase 1 it runs in any MCP host under its own principal, and the server checks the lineage."
**Fix:** Revise D-AGT-16 and D-AGT-17: a context whose endpoint is `Declared` (any external host outside the model gateway) starts with `data_untrusted` set, so its Proposals are at least R2 and never auto-merge; only hosted-crew and gateway-attested contexts can be clean. A verifier review counts toward merge only when the verifier's delegating human differs from the author's, or the verifier runs in the hosted crew. D-AGT-25 records the host's declared tool inventory as `Declared`. Extend AGT-O-14 with an external-host Proposal that must classify as R2.

### R11-13 · Major · Targets: AGT, ECO, KLN, CONTRACT
**Section:** ECO "Untrusted content in imported files"; AGT "Context labels and write-down", "Risk classification"; contract 7.6 "Free text is never endorsed by merging"
**Problem:** ECO's readers attach `data_untrusted` to every output of an imported Asset and Kiln joins it into everything derived, so any assembly containing one supplier STEP file taints every mass property, interference check and BOM line computed from it, forever. Contract 7.6 says a human merge endorses typed values, but that endorsement never reaches an Asset's label, so there is no way to say "this supplier geometry was reviewed". In practice every agent context working on a real assembly is `data_untrusted`, every Proposal is at least R2, and the risk classes stop discriminating.
**Evidence:** ECO: "Readers attach the Asset's `data_untrusted` integrity label to every output, and Kiln joins it into everything derived." AGT D-AGT-16: "any content from a `data_untrusted` context is at least R2". Contract 7.6: "A human merge endorses structure and typed values, never free text".
**Fix:** Add an Asset endorsement record to KLN and contract 7.6: a human who reviews an import Proposal (translation report, geometry overlay, `import_map`) signs an endorsement of the Asset's hash; from then on the Asset's typed outputs (geometry, structure, units, numbers) carry trusted integrity, while its text stays `ExternalText` and its renders follow R11-02. A new Asset revision starts untrusted again. AGT-O-14 adds a corpus case: an R1-shaped change on an assembly with an endorsed supplier part classifies as R1.

### R11-14 · Major · Targets: KLN, ECO, AGT
**Section:** KLN "Storage, Git export and span provenance", "Proposals and merge", "Sync, scale and recovery"; ECO "Exit surfaces"; AGT `edit.import_archive`
**Problem:** Span integrity is recorded "trusted when a person typed it", but content also enters a repository from outside the witnessing server: text edited in an exported Git repository and re-imported, a repository archive from another organization, a federated branch and an air-gapped bundle. None of these paths says what integrity the incoming spans get, and an archive or bundle carries the other side's own claims of "typed by a person". An agent-written injection can thus round-trip through Git or a partner's archive and return marked trusted.
**Evidence:** KLN: "Each source span records the integrity of the context that wrote it: trusted when a person typed it or the compiler produced it". KLN merge: "blocks match by block id, or by GumTree for files edited outside Crucible". KLN: "federation joins two organizations' servers through signed packages and shared branches"; `crucible bundle import` "verifies signatures, closure, labels and log consistency". AGT: `edit.import_archive` "ECO repository archive → a new design repository".
**Fix:** Add to KLN: integrity is asserted only by the server that witnessed the write. Spans arriving through Git import, archive import or federation get `data_untrusted`, and free-text spans among them `instruction_tainted`, unless the Change is signed by a device key of a principal in this organization; air-gapped bundles between sites of one organization keep integrity only when the signing site's key is in the receiving domain's trust list. KLN-O-SPAN-1 adds Git, archive and federation round trips of a planted comment.

### R11-15 · Major · Targets: AGT, KLN
**Section:** AGT "Write sets, protected paths and two-person rules" (D-AGT-27); KLN "Identity and authorization" (D-KLN-41)
**Problem:** Break-glass access "exists" with review afterwards, but neither tab bounds what it grants, who invokes it or for how long. If one administrator can break glass and then declassify, clear an endpoint or change a recipient, the two-person rule that fixed R5-15 is one click from void; if break-glass cannot do those things, the tabs do not say so.
**Evidence:** D-AGT-27: "break-glass access exists with a mandatory review afterwards and an alert to every administrator". D-KLN-41: "break-glass access alerts every administrator and requires review afterwards."
**Fix:** Specify break-glass in D-KLN-41: it is invoked by one administrator with an AAL3 credential (R11-06), lasts at most 4 hours, and grants only read access, agent freeze, ref revert, lock release and session termination. It can never declassify, clear an endpoint, client or recipient, change Cedar policy, purge, approve an Act or sign. Every action under it is audited with the break-glass id, and the review is a Proposal that a second administrator must close within 72 hours. KLN-O-POLICY-1 adds each forbidden action under break-glass.

### R11-16 · Major · Targets: AGT, KLN
**Section:** AGT "Audit and personal data"; KLN "Audit and encryption" (D-KLN-30)
**Problem:** AGT stores "full content only for Act plans, approvals and policy changes" in audit entries, while KLN says audit entries are "never labelled content". Act plans hold labelled file lists, recipient data and agent-written purposes. The entries live in per-tenant tlog-tiles logs whose data tiles are fetched by every verifying client and checkpoints are cosigned by customer witnesses, so labelled content in an entry reaches everyone who verifies the log.
**Evidence:** AGT: audit schema "with full content only for Act plans, approvals and policy changes". KLN: audit entries carry identifiers "never labelled content". D-KLN-30: logs "served in the C2SP tlog-tiles format, with checkpoints … optionally cosigned by customer witnesses."
**Fix:** One rule in KLN, cited by AGT: a log entry holds only identifiers, digests and the pseudonymous principal; the full Act plan, approval and policy text is a CAS record in the encryption domain of its label, and the entry commits to its `ObjectId`. Log readers who lack the label verify inclusion without reading content. KLN-O-AUDIT-1 adds a check that no tile holds labelled bytes.

### R11-17 · Major · Targets: CONTRACT, KLN, ELX
**Section:** Contract 5 `ApprovalSubject`; KLN "Revisions and lifecycle states" (D-KLN-26), "Change orders" (D-KLN-28)
**Problem:** The approval subject is built from `ItemDefinition` `GeometryId`s with PMI, the check-verdict digest, effectivity and evidence ids. A `Software` item (firmware, bitstream) has no geometry, and neither the contract nor KLN says its binary digest is part of its definition. Because approvals deliberately ignore the `ChangeId`, a rebase that swaps a firmware binary while keeping geometry and check verdicts keeps every approval.
**Evidence:** Contract 5: `ApprovalSubject` is "{ base revisions, ItemDefinition GeometryIds with PMI attached by canonical entity number, check-verdict digest …, effectivity, evidence record ids }". ### R11-23 · Major · Targets: ECO

### R11-25 · Major · Targets: CONTRACT, KLN, PLT, ECO
**Section:** Contract 7.8; KLN "Electronic signatures" (D-KLN-42); PLT "Signed updates" (D-PLT-37); ECO "Publishing and signing"
**Problem:** The contract offers LMS "for release signing" beside ML-DSA-87 without the state-management rules a stateful scheme needs. ### R11-39 · Minor · Targets: ECO, KLN
**Section:** ECO "Events and webhooks" (D-ECO-12); KLN "Encryption at rest"
**Problem:** SSRF protection checks that a URL "must not resolve to" private ranges, which DNS rebinding defeats unless the address is checked at connect time, and redirects are not addressed. Thin payloads carry "hashes", yet KLN promises that "plaintext `ObjectId`s never leave the domain's principals"; the `ObjectId` of a small record (a parameter file, a lockfile entry) lets a receiver confirm a guessed value.
**Evidence:** ECO: "URLs must use HTTPS and must not resolve to loopback, link-local or private ranges". The Standard Webhooks specification recommends "a filtering proxy" that blocks internal addresses and treats any 3xx response as a failed delivery (https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md). KLN: "plaintext `ObjectId`s never leave the domain's principals".
**Fix:** Deliveries go through an egress proxy that checks each resolved address at connect time against loopback, private, link-local, CGNAT (100.64.0.0/10), IPv6 unique-local and IPv4-mapped ranges, and 3xx responses count as failures. For labels above `internal`, payloads carry per-subscription opaque ids (HMAC of the `ObjectId` under the subscription's key) instead of `ObjectId`s or file hashes.

### R11-46 · Minor · Targets: ECO
**Section:** "Stewardship and decisions" (D-ECO-22); Open questions 5
**Problem:** "The trademarks are assigned in escrow to an independent party" while the company keeps using them. US law lets a mark be assigned only with its goodwill, and a mark whose owner exercises no control over its use risks losing significance as a mark; an escrow agent that owns the mark but controls nothing invites both problems.
**Evidence:** 15 U.S.C. 1060(a)(1): a registered mark is assignable "with the good will of the business" (https://www.law.cornell.edu/uscode/text/15/1060); 15 U.S.C. 1127 treats as abandoned a mark whose owner's course of conduct, "including acts of omission", causes it to lose its significance (https://www.law.cornell.edu/uscode/text/15/1127).
**Fix:** Replace escrow with an irrevocable, recorded option for the foundation to take assignment with goodwill at the trigger, secured by the steward's board and the keyholders of D-ECO-22, while the company keeps ownership and quality control until then. Answer to open question 5: join an existing open-source foundation that already holds trademarks and operates infrastructure for hosted projects, rather than create one, so that trademark holding, the CRA open-source steward role (Article 24) and registry operation have staff on day one.
