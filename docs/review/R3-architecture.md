# R3 architecture review

Summary:
1. Every identity hashes entity names, which hash `OpSite`s built from CRDT node ids. Cross-design cache sharing cannot work, and a geometry-neutral refactor changes every downstream `ObjectId`, voiding releases and approvals (R3-01, R3-05, R3-06, R3-16).
2. Labels leak. Backdating and cache hits launder them, one `DataClass` string cannot hold a join, and per-package Loro replicas ship labelled blocks to uncleared participants (R3-02).
3. The Ingot–Kiln contract has determinism and termination holes: `try` catches environmental failures whose fallbacks Kiln caches, and feature recursion is unbounded (R3-03, R3-04).

### R3-01 · Critical · Targets: CONTRACT, ANV, KLN, FLX
**Section:** CONTRACT 7.2 (two-stage caching); ANV "EntityId", "Persistence and versioning"; KLN "Keys and behavior versions", "Revisions and lifecycle states" (D-KLN-26); FLX "Fields and errors (`flux-field`)"
**Problem:** Every identity that caching, early cutoff, revisions and approvals use hashes entity names, and names hash upstream `OpSite`s transitively through "generating entity ids". The "site-free geometric stage" is keyed by its inputs' `ObjectId`s, which contain those names. So it can be shared across designs only for an operation whose inputs carry no names, and a refactor that changes no geometry (the language service's "extract feature" or "inline binding", which change feature instance paths) changes every downstream Body and Field `ObjectId`. Contract 7.2's cross-design sharing, D-KLN-26's promise and early cutoff after refactors therefore cannot hold as specified.
**Evidence:** ANV: the Body encoding's sections hold "`EntityId`s, tolerances, attributes, lineage summary"; rows are ordered by Morton code "then `EntityId`", and "a row ends a leaf when a hash of its EntityId has its low 8 bits zero". EntityId `inputs` are "The EntityIds of the generating entities". KLN keys every Op by "Ordered `ObjectId`s of every input value". FLX: `pub domain: DomainRef, // Body content hash plus EntityIds`. D-KLN-26: an edit that leaves the definition unchanged ("a refactor, a comment, a change elsewhere in the repository") "never invalidates a release".
**Fix:** Give every Body two identities in `base`. `GeometryId` hashes the canonical encoding with names, lineage and name-keyed attributes removed, rows ordered by spatial key only and entities numbered in that order; `ObjectId` hashes the full named encoding. Amend 7.2: "The geometric stage of an entity-naming Op is keyed by its inputs' `GeometryId`s. It numbers new entities canonically and refers to input entities by canonical number. The relabeling stage is keyed by the geometric output's id, the `OpSite` and the inputs' name maps, and it assigns `EntityId`s." Flux results key on `GeometryId` plus the canonical numbers of the entities their conditions reference. D-KLN-26's `ItemDefinition` and approval digests use `GeometryId` plus PMI attached by canonical entity number. New ANV oracle: two designs that build the same geometry at different sites share every geometric-stage entry along a 20-operation chain.

### R3-02 · Critical · Targets: CONTRACT, KLN, AGT
**Section:** CONTRACT 5 (`Labels`); KLN "Memoization, verification and backdating", "Distributed and remote evaluation", "CRDT over the syntax tree", "Export control", Rust API (`Label`, `DataClass`)
**Problem:** Kiln is said to "join" labels, but three mechanisms lose or leak them. Backdating keeps `changed_at` when bytes are unchanged, so an input relabelled from confidential to ITAR with identical bytes never reaches its dependents. `DataClass` is one string, so the join of two incomparable classes (two export regimes, two customer scopes) cannot be represented. And a live document is one Loro replica per package, so a participant who "does not satisfy a label" still receives every CRDT operation of the labelled blocks.
**Evidence:** Contract 5: "`DataClass` (public, internal, confidential, export-controlled with regime and classification) ... Joined through every derivation by Kiln". KLN: "If the new value equals the old one, keep `changed_at` (backdating)"; `pub struct DataClass(SmolStr)`; "Organizations add classes such as `cui` or `customer:<name>`"; D-KLN-22 "one document per package"; "a participant who does not satisfy a label sees neither the labelled content nor its geometry". A replica must hold every causally prior operation to converge, so a relay cannot filter operations per recipient inside one document.
**Fix:** (1) Contract 5: `Labels` is a product lattice: `level` (public < internal < confidential), `controls: Set<(Regime, Classification)>`, `scopes: Set<Scope>`, `integrity`, `licences: Set<DataLicence>`. The join takes the maximum level and the union of each set, and a principal may read only if it satisfies every element. (2) KLN: a node's label is a separate memo output with its own `changed_at`. Verification re-joins labels from current inputs even when the value backdates, and a shared-cache hit returns only the value, with the label recomputed locally. (3) An encryption domain is keyed by tenant and canonical label set. (4) The unit of live replication is (package, label set). Blocks labelled above a document's label live in a separate document that only cleared participants receive, and the relay refuses moves into a lower-labelled document. (5) Extend `repo/labels`: relabelling an input with unchanged bytes updates every dependent label with zero re-execution, and an uncleared participant receives zero operations of a labelled document.

### R3-03 · Critical · Targets: ING, KLN
**Section:** ING "Strict, ordered, and failure-aware" (D-ING-11), "Resource limits"; KLN "Errors as values" (D-KLN-6)
**Problem:** `try` and wildcard `err(e)` arms catch any `Failure`, and nothing excludes environmental failures (out of memory, device loss, cancellation, a budget exhausted mid-run). Nor does anything exclude a `DependencyFailed` whose upstream was environmental. A feature can therefore take its fallback branch because a worker ran out of memory, and Kiln caches the fallback geometry as a deterministic value. This breaks principle 4 and can poison the shared cache.
**Evidence:** ING: "`Failure` is an extensible union ... a match over `Failure` needs a wildcard arm"; "`try e` turns propagation into a value of type `Result<T, Failure>`"; "When the host cannot supply memory ... evaluation fails with an environmental `ResourceExhausted`, which Kiln never caches". KLN: "A node that needs a failed value fails with `DependencyFailed { upstream }`"; "Exhausting a budget mid-run is an environmental failure and is never cached".
**Fix:** Contract 7.2 and ING define two disjoint classes. A deterministic `Failure` is catchable and cached. An environmental `Abort` covers cancellation, `ResourceExhausted`, device loss, budget exhaustion, worker loss, an unavailable retired version and the limits of R3-04. `Abort` is not a `Failure`: `try` cannot observe it, it propagates to every transitive dependent, and no node that observed one writes a memo entry, CAS object or attestation. `DependencyFailed` wraps only deterministic failures. New oracle `kiln/abort`: inject environmental faults at random Ops in 10,000 runs; every value that reaches the memo or shared cache equals the fault-free run's value.

### R3-04 · Critical · Targets: ING, KLN
**Section:** ING "Resource limits", "Strict, ordered, and failure-aware"; KLN "Scheduling and parallelism"
**Problem:** Ingot's claim that every evaluation ends in a value or a typed failure is false. Every limit applies per feature call, and each feature call is a separate Kiln node with fresh limits. A feature that calls itself with a new argument (`f(n) = f(n + 1)`) therefore builds an unbounded chain of nodes, and Kiln detects only a node that reappears on its own stack. Total work is also unbounded: 10⁹ steps per call times any fan-out times depth.
**Evidence:** ING: "Limits apply per feature call ... Feature calls and `#[memo]` function calls are Kiln nodes with their own limits ... Termination still holds, because every call is bounded and call depth is bounded"; the 2,048-frame depth limit is a "Default per feature call". KLN: "When a node demands a node already on its own active stack, Kiln returns `EvalError::Cycle`".
**Fix:** Kiln enforces two evaluation-wide limits as environmental `Abort`s (R3-03), so they never change a cached value. One is a demand-depth limit on nested node demands (default 10,000); the other is an aggregate fuel governor per Evaluation, taken from the request's budget. Restate ING's guarantee: "every node terminates with a value or a typed failure; every Evaluation terminates or aborts". New oracle ING-O-24: `f(n) = f(n + 1)` aborts with `DemandDepthExhausted` on every Tier 1 target and leaves no memo entry.

### R3-05 · Major · Targets: KLN, CONTRACT, ING
**Section:** KLN "Graph model" (Feature key); CONTRACT 7.2; ING "The incremental contract with Kiln"
**Problem:** KLN keys a feature node without its `OpSite`, yet the feature's result carries `EntityId`s that hash the feature instance path. Two `bracket()` calls with equal arguments at different sites then share one cached result with identical `EntityId`s. `left + (right |> move(x: 100mm))` then fails with `Internal::EntityIdCollision`, and `created_by: right` selects nothing. Contract 7.2 covers only entity-naming Ops and says nothing about feature nodes.
**Evidence:** KLN graph model: "Feature | feature identity, package closure hash, argument `ObjectId`s". ING: "A feature call is a node keyed by the feature's code hash, its `OpSite`, ... the `OpSite` is needed because entity names depend on it". ANV: `site` is "the feature instance path plus a call-site key"; "Within one Body, a duplicate EntityId fails the operation with `Internal::EntityIdCollision`".
**Fix:** Add to contract 7.2: "Every node whose value carries `EntityId`s (feature calls, entity-naming Ops, query resolutions) includes its `OpSite` in its key; cross-site sharing happens only in the site-free geometric stage of Ops (R3-01)." KLN's Feature key gains `OpSite`. New oracle `kiln/sites`: two equal-argument calls at different sites yield distinct `EntityId`s, and their union succeeds.

### R3-06 · Major · Targets: ING, KLN, ANV, ECO, CONTRACT
**Section:** ING "Entities and call sites"; KLN "CRDT over the syntax tree", "Storage format"; ECO "Package registry"; CONTRACT 5 (`EntityId`)
**Problem:** `OpSite`, and so every entity name, depends on Loro node ids that cannot be derived from source text. The same text can get different names after a Git round trip, after re-typing a statement, and in a registry package. ECO publishes packages without block maps, so ING's ordinal fallback applies to them. Inserting one statement into a std feature then renames entities in every dependent design on upgrade.
**Evidence:** ING: statement identity is "The `BlockId` of the enclosing statement block in the live document"; "A file outside any repository ... gets `BlockId`s derived from item paths and statement ordinals"; an outside edit "matches blocks by GumTree, so most `BlockId`s survive". KLN: "Block identities are Loro tree node ids"; "`crucible export git` writes Ingot text and lockfiles". ECO never mentions `BlockId`s or block maps.
**Fix:** Define statement identity from text in ING and contract 5. A `let` statement's identity is (item path, arm path, binding name), which ING1102 already makes unique per block. An unnamed statement's identity is (item path, arm path, nearest preceding binding name, ordinal after it). Renaming a binding is a refactor that writes `#[was(old_name)]`, which preserves the identity until the next edition. Loro node ids map onto these identities for collaboration only and never enter `OpSite`. New oracle (ING-O-10 and ANV): export to Git, re-import and rebuild; every `EntityId` is unchanged.

### R3-07 · Major · Targets: ING, FLX, KLN, AGT, CONTRACT
**Section:** ING "`Approx<T>` and `Truth`", "`require` and checks", worked example 3; FLX "Fidelity modes", "The error budget"; KLN "Progressive results"; AGT "Method catalog"; CONTRACT 5 (`CheckOutcome`)
**Problem:** Four tabs give four rules for deciding a check. ING decides on disjoint enclosures and makes any `Indicator` bound `Undecided`. FLX reports interactive bounds as `Indicator` and adds a consumer-side margin of three times the estimate; KLN adds a `Provisional` status. AGT's `CheckOutcome` has no `Undecided`, while ING adds `Error` and `Skipped`, so read literally every interactive Flux check is `Undecided(UnknownError)`.
**Evidence:** ING: "`Undecided(UnknownError)` | Any bound is `Indicator` or `Unknown`"; example 3 calls 112 ± 20 MPa against a 165.6 MPa limit `Undecided` because "FLX's interactive margin rule needs a margin of three times the estimate", though the enclosures are disjoint. FLX: discretization estimator "`Indicator` (residual)"; "`Pass` or `Fail` only with a margin of at least 3× the estimate". KLN: "Checks evaluated on `Preview` or `Interactive` results are reported as `Provisional`". AGT: `pub status: CheckStatus, // Pass | Fail | Error | Skipped`. Section 14 lists no `Undecided` edit for AGT.
**Fix:** One decision rule, owned by ING and applied to `if`, `require` and query `where:` alike: disjoint enclosures decide, subject to the check's `evidence`. Producers own their bounds. FLX reports interactive bounds already multiplied by the calibrated factor, labels them `Estimated { calibration }`, and drops the 3× rule. Contract 5 defines one `CheckOutcome { verdict: Pass | Fail | Undecided { reason, needed } | Error(Failure) | Skipped { reason }, fidelity, evidence, value, limit, margin, severity, source }`. "Provisional" becomes the derived predicate "fidelity below the declared one", not a variant. Add AGT to section 14's `Undecided` edit.

### R3-08 · Major · Targets: CONTRACT, FLX, COV, ING, ANV
**Section:** CONTRACT 5 (`ErrorBound`, `ErrorBudget`, `Approx<T>`); FLX "Fields and errors"; COV "Error budget"; ING "`Approx<T>` and `Truth`"
**Problem:** `ErrorBudget` has three incompatible shapes, and the ruling that `Approx<T>` carries one cannot be implemented as written. FLX's struct cannot express "not quantified" and has no model-form component. COV's struct has four components and is generic, and the contract lists seven. `ErrorBound.value` is a bare `f64`, and `total(norm)` combines components measured in different norms, which means nothing for a scalar.
**Evidence:** FLX: `pub discretization: ErrorBound, pub algebraic: ErrorBound, ...`; `pub fn total(&self, norm: Norm) -> ErrorBound`. COV: `pub struct ErrorBudget<D> { discretization, solver, input, model_form }`. Contract 5: "named components (discretization, solver, geometry conversion, input and tolerance, model form, surrogate, interpolation) ... A not-quantified component is never treated as zero". ING: `bound: ErrorBound`; "reducing a Field yields an `Approx` whose bound is the budget's total". Ruling ING-2 "carries an `ErrorBudget`" has no matching ING edit in section 14.
**Fix:** One definition in `base`. `ErrorBound<Q> { value: Q, norm, kind }`; `enum Component<Q> { Quantified(ErrorBound<Q>), NotQuantified { reason } }`; `ErrorBudget<Q> { parts: BTreeMap<ErrorSource, Component<Q>>, total: Component<Q> }`. `ErrorSource` is the contract's list plus temporal, quadrature, floating point and statistical. The total is `NotQuantified` if any part is, and its kind is the weakest part's. `Approx<T>` carries `ErrorBudget<T::Delta>` restricted to `Pointwise` and `Goal` norms. A Field reduction is `Quantified` only when Flux estimated that functional, otherwise `NotQuantified`, so comparisons on it are `Undecided`. Add the ING edit to section 14.

### R3-09 · Major · Targets: CONTRACT, FLX, ING, AGT, UIX
**Section:** CONTRACT 6 (canonical example); FLX "Honest reporting of singular quantities", "Solve plans"; ING worked example 3; AGT "Text descriptions"; UIX "Running and exploring results"
**Problem:** The canonical check takes a peak stress next to a clamped face, and linear elasticity makes stress singular where a clamped face meets a free face. By Flux's own rule such a check can only report `Undecided`, yet AGT and UIX show it passing with margins. ING example 3 claims a `Guaranteed` ± 1.5 MPa bound on a peak stress, which no FLX estimator provides. The first example every author copies teaches a check that cannot pass.
**Evidence:** Contract 6: `peak_stress(p, load, fixed: base.face(role: start_cap))`. FLX: "Point loads, point supports, re-entrant edges and corners ... make exact stresses infinite ... A check on a flagged peak returns `Undecided`"; guaranteed bounds hold "For energy norms" on fitted simplicial meshes, and immersed results are `Estimated`. AGT: "worst margin `peak_stress` 31%"; UIX: "peak_stress < 0.6 × yield: margin 18% ± 4%". Reasoning: where a clamped face meets a free face at a right angle, the linear-elastic stress field is singular, so the peak grows under refinement and FLX's own detector ("a local estimate that fails to decrease under refinement") flags it. Dual-weighted residual estimation needs a differentiable goal, and a maximum is not differentiable.
**Fix:** Rewrite the canonical check over a region that excludes the clamp: `let stress = study.von_mises.max(over: p.body.away_from(base.face(role: start_cap), 2 * thickness))`, then `p.require(stress < 0.6 * p.material.yield_strength(at: 20degC))` with default evidence. FLX defines `peak_stress` as a regularized goal (a p-norm or local average over a stated region, with the regularization error in the budget) and states that a raw maximum is never a goal. ING example 3's sign-off row becomes `Estimated`. AGT and UIX reuse the new check.

### R3-10 · Major · Targets: FLX, ING, KLN
**Section:** FLX "Solve plans" (D-FLX-5); ING "`require` and checks" (D-ING-12)
**Problem:** FLX derives adaptivity goals from "the checks that read a result", so adding or editing a check changes the pinned `SolvePlan`, the solve's key and every result read from it. A consumer then alters its producer, which reverses the evaluation graph. It also contradicts D-FLX-5 and D-ING-12.
**Evidence:** FLX: "Goals come from the checks that read a result. When a check depends on `peak_stress(part, load)`, that functional becomes an adaptivity goal automatically." D-FLX-5: "A consumer's accuracy demand never triggers an automatic re-solve of the producer". D-ING-12: checks stay out of the dataflow "so that adding a check never changes a design".
**Fix:** Goals are explicit study inputs written in source (`study(..., goals: [...])`). The language service offers a fix, "add this check's functional to the study's goals", that edits source visibly. Delete FLX's sentence. New ING oracle: adding or removing any `require` leaves the key of every non-check node unchanged.

### R3-11 · Major · Targets: CONTRACT, KLN
**Section:** CONTRACT 7.2; KLN "Keys and behavior versions", "Progressive results", Rust API (`OpCx::rng`)
**Problem:** The contract's `OpKey` omits fidelity, which KLN's key includes, and neither says how one exact geometry node serves both `Interactive` and `SignOff`. Item 4 ("or it ran in a class other than `CpuCanonical`") can be read to key a `Certified` result by the GPU that assisted it, which defeats that grade. Random streams are keyed by the full `OpKey`, which contains the class, so CPU and GPU runs draw different samples and differ statistically, not just by rounding.
**Evidence:** Contract 7.2 lists five items, none of them fidelity. KLN: "`fidelity` | `Preview`, `Interactive` or `SignOff`"; "Anvil's `Exact` fidelity serves both `Interactive` and `SignOff`, so exact geometry is one shared node"; `pub fn rng(&self, stream: u64) -> Philox4x32; // keyed by the OpKey`. Principle 4 requires cross-class agreement within declared tolerance.
**Fix:** Contract 7.2 adds "6. the effective fidelity, which each operation version maps from the requested fidelity; an operation that ignores fidelity maps all three to one value". Item 4 becomes "the platform class of the result, which is `CpuCanonical` for `Portable` and `Certified` results". `OpImpl` gains `fn effective_fidelity(Fidelity) -> Fidelity`. KLN keys random streams by the class-independent part of the key.

### R3-12 · Major · Targets: ING, KLN
**Section:** ING "Resource limits", "Manifest"
**Problem:** A feature's fuel limit is clamped by "the organization ceiling", which is policy, not source or lockfile. Two organizations evaluating the same key can get `ING6301 FuelExhausted` in one and a value in the other. That deterministic failure is cached and shared.
**Evidence:** ING: "10⁹ steps; `#[fuel(…)]` raises it up to the manifest maximum and the organization ceiling"; manifest comment "per feature call; within the organization ceiling". Contract 7.2: "Deterministic errors are cached".
**Fix:** The effective limit is a function of source and manifest only, and it enters the node key. An organization ceiling below a requested limit is checked at admission. It refuses the Evaluation with an environmental `FuelCeilingExceeded` (R3-03), never a cached `FuelExhausted`. Apply the same rule to the memory and operation-count limits.

### R3-13 · Major · Targets: ING, KLN
**Section:** ING "The incremental contract with Kiln"; KLN "Memoization, verification and backdating" (D-KLN-5)
**Problem:** A feature node's value includes "accumulators and recorded fuel", and backdating compares whole values. Any edit that changes fuel but not geometry (a new `let`, a refactor, a faster loop) marks the feature changed and re-executes every dependent. That defeats early cutoff for the commonest code edits.
**Evidence:** ING: "Its value is the result or failure, plus accumulators and recorded fuel." KLN: "If the new value equals the old one, keep `changed_at` (backdating)".
**Fix:** A node has separate outputs: the result, one per accumulator kind (checks, notes, tolerance sites, PMI) and metadata (fuel, cost). Each output has its own `changed_at`, and dependents record which outputs they read. Metadata is never compared for backdating. Extend `kiln/minimality` with fuel-only edits, after which no dependent re-executes.

### R3-14 · Major · Targets: ING, KLN, FLX
**Section:** ING "Previews, drags and incomplete code", "`require` and checks"; KLN "Progressive results"
**Problem:** A feature that branches on a Flux result fails whenever the observed bound cannot decide, which under today's `Indicator` labelling (R3-07) means every interactive update. When a branch does decide at a lower fidelity, its geometry can differ from what sign-off would build. ING lets a release evaluate "sign-off checks even when geometry ran interactively", so released checks can read geometry that sign-off would not produce.
**Evidence:** ING: "a branch on them may stop with `UndecidedBranch` where the exact build would decide ... a release evaluates sign-off checks even when geometry ran interactively". KLN: "Kiln schedules `Preview` first for every demanded target, then `Interactive`, then `SignOff` when the ceiling allows".
**Fix:** Each node's result records the fidelity of the bounds it observed. An `if`, `match` or `where:` on `Undecided` below the subscription's ceiling yields `ResultStatus::Pending` and waits for the next fidelity's node. That node is already demanded, so D-FLX-5 holds. The construct fails with `ING6401` only at the ceiling. A release demands every node at `SignOff`, not only the checks; replace ING's sentence accordingly.

### R3-15 · Major · Targets: CONTRACT, KLN
**Section:** CONTRACT 7.1 (`repo`, clean merge); KLN "Merge" (D-KLN-21)
**Problem:** The clean-merge rule tests only checks that "both parents passed". A check added or edited on one side, which the other side's change breaks, therefore merges cleanly and silently. Defining geometric conflict as overlapping changed regions is so coarse that the commonest pair of concurrent edits conflicts (one side edits a dimension, the other adds a feature). "Distance below the merge clearance (default 0 mm)" can never be true.
**Evidence:** KLN: "Every check that passes on both parents passes on the merge"; "the region as the symmetric difference of base and side Bodies ... two regions conflict when their distance is below the merge clearance (default 0 mm)". ING's default check `name` is "Derived from the predicate's source", so editing a predicate creates a check that exists on one side only. Offline rejoin and unprotected branches rely on this driver alone.
**Fix:** Contract 7.1 wording: "a merge is clean only when the result compiles and resolves, no check's outcome on the merge is worse than its outcome on each parent that defines it (`Pass` > `Undecided` > `Fail` > `Error`), and no interference appears that neither parent has." A geometric conflict becomes provenance-level: both sides modify, split or delete the same base entity, or one side's new entity intersects the other side's modified region. Symmetric-difference regions appear in review but do not block. Write "at or below the merge clearance". Add held-out merges with one-sided checks to `repo/merge`.

### R3-16 · Major · Targets: KLN, AGT, MFG, CONTRACT
**Section:** KLN "Change management" (D-KLN-28), Rust API (`ChangeOrder`)
**Problem:** Approvals sign a record that names the head `ChangeId` and the CI report's `ObjectId`. A rebase changes the `ChangeId`, and a CI re-run changes the report (timings, workers, costs), so either voids approvals of identical content. That contradicts KLN's own rule that a rebase resets approvals "only if its evaluated content changes". With R3-01, a refactor voids them too.
**Evidence:** KLN: "A signature signs the order record, which names the head `ChangeId`, the evaluated `ItemDefinition`s and the CI report `ObjectId`"; `pub head: ChangeId, // the exact content approvals sign`; "the second must rebase onto the first, which resets its approvals only if its evaluated content changes".
**Fix:** Contract 5 defines `ApprovalSubject { base revisions, ItemDefinition GeometryIds with PMI, check-verdict digest (check id, verdict, fidelity, class, value, limit), effectivity, evidence record ids }`. Approvals sign its `ObjectId`; the `ChangeId` and the full CI report are unsigned provenance. A rebase or CI re-run keeps approvals exactly when the subject is unchanged. MFG's program approvals and AGT's Act plans keep their own subjects.

### R3-17 · Major · Targets: CONTRACT, KLN, MFG
**Section:** CONTRACT 2 (External input), 7.1 (Hardware CI); KLN "Hardware CI runner" (D-KLN-35)
**Problem:** The contract makes a physical measurement an External input "pinned in `ingot.lock`", but hardware CI produces measurements automatically and keys them by the inputs they tested. Neither text says which measurement a check reads. A check's outcome for a fixed Change therefore depends on when it is evaluated, and a release cannot reproduce it.
**Evidence:** Contract 2: an External input includes "a machine reading, a physical measurement ... pinned in `ingot.lock`". KLN: "A measurement record is keyed by the check, the `ObjectId`s of the design inputs it tested, the rig and the run".
**Fix:** Contract 2 defines two pin modes. Lockfile pins cover translations, offers, catalog data and regulation packages, refreshed explicitly. Evidence pins cover measurement records, addressed by check id and the tested inputs' `GeometryId`s (R3-01). An evaluation reads the newest valid evidence record and stores its `ObjectId` in the `CheckOutcome`. Releases and approvals pin the evidence ids they cite, as 7.3 does for External Op results.

### R3-18 · Major · Targets: CONTRACT, ING, KLN, ELX
**Section:** CONTRACT 6 and 14 (variant ruling); KLN "Variants and the 150% BOM" (D-KLN-27); ELX "Variants" (D-ELX-4)
**Problem:** The ruling removed `options` and `when`, but the 150% BOM needs a static account of which Instances exist under which option values, and no tab now provides it. With plain `if` and `match`, an Instance's existence can depend on computed geometry. ELX's "every declared variant builds" enumerates configurations, which KLN rejects as exponential.
**Evidence:** KLN: "The Ingot compiler enforces that whether an Instance exists depends only on options and constants ... Kiln can then evaluate assembly structure with options as symbolic values". Contract 6: "variants are enum or record parameters selected with `if` and `match`". ING's Interfaces provide no such analysis.
**Fix:** ING adds an attribute, not a keyword: `#[configuration]` on enum or record parameters of an assembly feature. The compiler marks γ-regions whose conditions depend only on configuration parameters and constants as variant regions; Instances created inside them carry the region's condition. Creating an Instance under a condition that depends on computed values is a compile error. Kiln computes the 150% BOM by abstract interpretation of the IIR with configuration parameters symbolic, and SAT checks replace enumeration. ELX's CI builds only the configurations its policy lists.

### R3-19 · Major · Targets: KLN, CONTRACT, FLX, ING
**Section:** CONTRACT 7.1 (Kiln: reverse traversal, `Differentiable`, step checkpoints); KLN (whole tab); FLX "Adjoints for steady and transient problems"
**Problem:** The contract gives Kiln reverse traversal for adjoints, a `Differentiable` registration extension and step-keyed checkpoints, and ING and FLX depend on them. KLN specifies none of them, and section 14 lists no KLN edit. `OpImpl` has no tangent or adjoint methods while FLX writes its own over `OpCtx`, and the CAS has no retention class for checkpoints, which FLX requires.
**Evidence:** KLN contains no "Differentiable", "reverse traversal" or "retention class". Contract 7.1: "Reverse traversal for adjoints, a `Differentiable` registration extension and checkpoints keyed by step". ING: "`grad` over many parameters uses Kiln's reverse traversal of the Op graph". FLX: `fn tangent(..., ctx: &mut OpCtx)` and `fn adjoint(...)`; FLX requires "retention classes for checkpoints, intermediates and results".
**Fix:** KLN adds a "Derivatives" section. It defines `trait Differentiable: OpImpl { fn tangent(...); fn adjoint(...); }` in `base`, reverse traversal of the recorded dependency graph from a scalar goal, and checkpoints keyed by (`OpKey`, step) in a `Checkpoint` retention class that eviction drops first. Its oracle is a Taylor test of a three-Op chain. Add the edit to section 14.

### R3-20 · Major · Targets: CONTRACT, KLN
**Section:** CONTRACT 7.1 (trusted builders); KLN "Distributed and remote evaluation" (D-KLN-9)
**Problem:** "Only trusted builders write the shared cache" trusts the machine, not the code it ran. CI runners evaluate untrusted agent Proposals and third-party Wasm, so a sandbox escape there produces a valid attestation for any key. Spot re-execution of 1% of hits rarely catches a targeted poisoning, and the global public domain that all tenants share has no named writer.

### R3-29 · Major · Targets: CONTRACT, ING, MEC, ELX, FLX
