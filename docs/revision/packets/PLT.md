### R1-09 · Major · Targets: FLX, PLT, CONTRACT
**Section:** FLX D-FLX-8, determinism mechanism 1, platform notes; PLT "GPU compute" item 5; contract §7.3 ("no implicit FMA contraction anywhere").
**Problem:** WGSL lets implementations reassociate, fuse when "at least as accurate", implement `fma` unfused, flush subnormals and assume that overflow, infinities and NaNs never occur, in which case results become indeterminate values. Emitting no FMA therefore cannot make WGSL kernels share bits with CPU kernels, explicit flushing does not control what the driver flushes or fuses, and in-kernel NaN and infinity checks may be removed, so a diverging `f32` solve can return finite garbage. PLT's per-device double-float self-test cannot show that other pipelines compile without reassociation.
**Evidence:** WGSL specification source, https://github.com/gpuweb/gpuweb (wgsl/index.bs, cloned 2026-10-11), section "Reassociation and Fusion": "An implementation may reassociate operations." and "An implementation may fuse operations if the transformed expression is at least as accurate as the original formulation." The `fma` accuracy is "Inherited from `x * y + z`", with a note that it "allows an implementation which performs an ordinary multiply ... followed by an ordinary addition". The spec also says "Implementations may assume that overflow, infinities, and NaNs are not present during shader execution" and "Any inputs or outputs of operations listed in [floating-point accuracy] may be flushed to zero"; it defines no `f64` type. FLX D-FLX-8 claims "native, browser and user-form kernels share bits" with "no ... FMA for CPU or WGSL targets".
**Fix:** In contract §7.3, restrict "no implicit FMA contraction" to CPU classes and define GPU classes by the compiled pipeline, keyed by the driver and shader-compiler build plus the pipeline hash. In FLX, drop the shared-bits claim for WGSL; detect non-finite values on the CPU after readback by integer inspection of exponent bits; keep kernels in range by nondimensionalization and argument clamping; use integer arithmetic only for anything that must be exact on GPUs, as D-FLX-18 already does for reductions. In PLT, replace the per-device self-test with a known-answer test for each compiled pipeline, run at creation and after any driver or OS update, with CPU fallback on failure.

### R1-10 · Major · Targets: FLX, PLT, MEC, ELX, CONTRACT
**Section:** Contract §7.1 ("faer for CPU linear algebra"); FLX "Linear algebra layer"; PLT "Third-party numerical libraries"; MEC solver method; ELX D-ELX-13.
**Problem:** faer's dense kernels come from the `gemm` crate, which sizes the reduction block `kc` from cache size and associativity detected at run time and uses FMA microkernels where available. Any product whose inner dimension exceeds that block (at least 512), such as Gram matrices VᵀV in reduced-order modelling and LOBPCG, therefore sums in a machine-dependent order, and FMA and non-FMA microkernels differ across ISA levels. faer as shipped breaks the canonical class, even within one ISA level, for every `Portable` operation that calls it.
**Evidence:** `gemm-common/src/cache.rs`, cloned from https://github.com/sarah-quinones/gemm: `kernel_params` reads `CACHE_INFO`, filled from /sys or CPUID, and computes `auto_kc` from `l1_n_sets` and `l1_assoc`. `gemm-common/src/gemm.rs` defines `v3_fma` with `f64::mul_add`. https://docs.rs/faer/latest/faer/ shows faer 0.24.4 with "cpu feature detection at runtime" and rayon "global parallelism by default", and says nothing on determinism. PLT itself marks faer's behaviour "[unverified]".
**Fix:** Make a canonical linear-algebra crate (or a pinned faer and gemm fork) a phase 0 deliverable owned by PLT and FLX, with fixed machine-independent block sizes, canonical 512-bit lanes, no FMA, sequential or combinator-partitioned updates, and pivot ties broken by index. Unmodified faer runs only in `CpuIsa` mode, and only with `CACHE_INFO` pinned. MEC's constraint solver, ELX's circuit LU and COV's calibration fits use the canonical crate for `Portable` results. Add a determinism-suite case that runs the same factorization under two different `CACHE_INFO` values.

### R1-12 · Major · Targets: FLX, PLT
**Section:** FLX "Determinism" (cross-class tolerance); PLT "Measuring cross-class agreement".
**Problem:** FLX's agreement tolerance, "the larger of the final residual bound and 100 ulp per value", is wrong three ways: a small residual bounds the forward error only through the condition number (with κ = 10⁶, solutions with relative residual 10⁻¹⁰ can differ by 10⁻⁴), adaptive runs refine different cells in different classes, and ulp tolerances mean nothing near zero. The oracle will fail correct runs and pass wrong ones, and FLX and PLT use different rules.
**Evidence:** FLX: "results agree within a declared tolerance that is the larger of the final residual bound and 100 ulp per value". PLT uses "relative residual of each result in the other class's discretization".
**Fix:** Use one rule in both tabs: classes A and B agree when |q_A − q_B| ≤ E_A + E_B for every checked quantity q, where E is the budget total in q's norm (algebraic, discretization, floating point) plus an absolute floor scaled by the Field norm. Report the ratio |q_A − q_B| / (E_A + E_B); a ratio above 1 also fails the effectivity oracle.

### R1-13 · Major · Targets: CONTRACT, FLX, PLT
**Section:** Contract principle 4 and the CCR-FLX-7 ruling; FLX "Limits of the machinery".
**Problem:** At bifurcations (buckling, snap-through, symmetric contact, symmetry-breaking flow, electrostatic pull-in) and where several solutions exist (Newton converging to different roots, path-dependent plasticity), rounding differences select different branches. Cross-class agreement then fails by more than any tolerance even without chaos, but the ruling covers only chaotic problems.
**Evidence:** Contract principle 4: "cross-class results agree within declared tolerance (or, for chaotic problems, in declared statistics)". A perfect column has two post-buckling branches of opposite sign, and rounding decides which one Newton follows.
**Fix:** Add to principle 4: "Problems with bifurcations or multiple solutions declare branch selection explicitly (an imperfection or symmetry-breaking load in the input) or declare agreement on branch-invariant quantities (critical loads, mode sets, load–displacement magnitude)." Flux's Newton and arc-length solvers detect bifurcation points (a sign change of the tangent determinant or a zero eigenvalue) and return `Bifurcation { load, modes }` instead of silently picking a branch.

### R2-24 · Major · Targets: MFG, ANV, PLT
**Section:** MFG Stock models (D-MFG-6); Material removal and machine collision simulation
**Problem:** Gouge and leftover checks read the narrow-band grid stock, so their accuracy is the grid spacing, yet the gouge oracle requires every planted gouge to be found. For golden product 1 at a 5 µm spacing, a 100 × 100 × 30 mm part has about 1.3 × 10⁹ surface cells and about 8 × 10⁹ band cells (roughly 60 GB of f64), against a 1 GiB memory target; at a spacing the laptop can hold (20 µm or more), shallower gouges go undetected.
**Evidence:** D-MFG-6 "In-process stock is an `Implicit` Body backed by a sparse narrow-band distance grid at a declared resolution"; "Gouge and leftover | Signed distance from simulated stock to the exact design B-rep ... Seeded gouge corpus: every planted gouge detected"; PLT "Memory with golden product 1 open | Under 1 GiB in total". Arithmetic: surface area about 0.032 m² divided by (5 µm)², times a band of ±3 cells.
**Fix:** Detect gouges independently of the stock: for every cutting move, compute the certified minimum distance between the tool's exact swept envelope and the design B-rep (`anvil::distance` against `anvil::swept_volume` per move, or `tool_contact` along it), which is exact and needs no stock. Use the stock only for leftover, rest machining and display, with adaptive refinement near the design surface and a stated `ErrorBound` per setup. Add tri-dexel stock with exact dexel endpoints as a candidate in the phase 1 benchmark.

### R3-21 · Major · Targets: KLN, PLT, CONTRACT
**Section:** KLN "Cancellation", "Sources of nondeterminism and their controls", "Requirements on the Platform tab"
**Problem:** KLN contradicts contract 7.4 and D-PLT-22 in three places: it cancels Wasm components with epoch interruption, it inserts NaN canonicalization at load time in browsers, and it relies on Cranelift's NaN switch natively, which D-PLT-22 rejects. ### R3-33 · Major · Targets: ING, PLT, KLN
**Section:** ING "The deterministic Wasm subset" (Memory), "Values and memory", "Resource limits"; KLN "Memory management and eviction"
**Problem:** Each feature call runs in its own instance whose module "declares its maximum memory, and the host reserves it"; the default per-call limit is 1 GiB, and KLN's browser budget is 2 GiB. Suspended parent calls stay alive while their children run, so as specified a browser holds about two live feature calls. A std feature that calls a std feature that calls a third would then abort.
**Evidence:** ING: "Memory | Semantic bytes ... | 1 GiB"; "The module declares its maximum memory, and the host reserves it in its memory budget before instantiation"; "Each feature call runs in a fresh instance drawn from a pool". KLN: "2 GiB in browsers".
**Fix:** Reserve semantic memory as it is used, not the declared maximum. Run suspended feature calls as state machines in one instance per worker, each with its own allocator region and fuel and depth counters. Isolation then comes from the compiler (no mutable globals) and the allocator. Add a browser benchmark: 500 concurrently suspended feature calls fit within 2 GiB.

### R5-09 · Major · Targets: ECO, PLT, KLN
**Section:** ECO Running on every platform; PLT Wasmtime configuration, Open questions (6); KLN Distributed and remote evaluation
**Problem:** Third-party evaluation components from verified publishers run inside the engine process. That process holds every open repository and the user's tokens and can use the device signing key, so Wasmtime is the only boundary. Wasmtime's 2026 advisories include an out-of-bounds write in Component Model string transcoding and data leakage between pooling-allocator instances, and PLT uses the pooling allocator. On servers, no tab requires separate worker processes per tenant or per label scope.
**Evidence:** ECO: "Evaluation-context Wasm components from verified publishers run in process for speed". PLT: "Pooling allocator sized from the memory budget". PLT open question 6 leaves engine sandboxing undecided. **Fix:** (1) Only first-party, hermetically built components run in the engine process. (2) On servers, run one worker process per (tenant, label scope). `export_controlled` scopes get dedicated VMs, and pooling slots are never reused across tenants or scopes. (3) Apply Wasmtime security releases within 7 days on every supported line (D-PLT-21), gated by O-ECO-6.

### R5-12 · Major · Targets: ECO, PLT
**Section:** ECO Running on every platform (D-ECO-10); PLT Formats per target, In the browser
**Problem:** In the browser, every component ships with registry-generated JavaScript glue that runs in the engine worker's origin, where it can reach OPFS (every local repository), authenticated `fetch` and WebCrypto keys; the glue, not Wasm, is the real boundary. The web app is served with HTTPS and SRI on an entry script that the same server controls. A compromised CDN or deployment can therefore serve arbitrary code to every browser user, including the approval page. Linux apt and dnf metadata is signed with OpenPGP but has no stated freshness bound.
**Evidence:** ECO D-ECO-10: the registry transpiles each component "into ES modules", as jco does. PLT: "Content-hashed static assets plus a service worker | HTTPS; Subresource Integrity on the entry script"; Linux: "Repository metadata signed with OpenPGP". TUF lists indefinite freeze and rollback among the attacks it addresses (https://theupdateframework.github.io/specification/latest/).
**Fix:** (1) Ship one first-party, generic component runtime (fixed JavaScript inside the app) that instantiates core modules from data, so the registry ships no per-component JavaScript. (2) Run third-party components in a separate cross-origin sandboxed worker or iframe with no OPFS or credentials, exchanging data by `postMessage`. (3) Publish each web release's asset manifest to a transparency log. The service worker verifies new versions against TUF targets before activating them, and enterprise mode serves assets from the verified offline bundle. (4) Give apt and dnf metadata a short expiry and have the updater enforce it.
