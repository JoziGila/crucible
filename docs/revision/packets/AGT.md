### R8-02 · Critical · Targets: CONTRACT, ANV, ING, AGT
**Section:** Contract 5 `Query`; ANV Query resolution, EntityId (discriminators); ING The query language (rank selectors); AGT D-AGT-8; oracles ANV-O-NAME-2, AGT-O-18
**Problem:** The guarantee "Never silently picks another entity" rests on `Note::RankSwap`, emitted by `anvil::resolve` when "a winner whose lineage changes inside the declared parameter ranges". `anvil::resolve` is a pure Op over one Body and one `QueryPlan`; its key holds neither the design's parameter ranges nor any other evaluation, so it cannot know whether the winner changes elsewhere in the range. Even as a separate analysis, "full declared range of every parameter, endpoints included" has no sampling design (n parameters have 2ⁿ corners) and swaps between samples go unseen. A second silent path is the `Ordinal(k)` discriminator, ordered by canonical geometric order (box minimum first): any dimension edit that reorders two boxes swaps the ids, and only `Note::FragileAnchor` is raised.
**Evidence:** Contract 5: "success may carry Notes (`Merged`, `FragileAnchor`, `RankSwap`) that checks may forbid ... Never silently picks another entity." ANV: "a winner whose lineage changes inside the declared parameter ranges is reported as `Note::RankSwap { at }`"; "`Ordinal(k)`, which marks the id fragile (`Note::FragileAnchor`)"; canonical order is "kind, box minimum, box maximum, type and defining parameters". Contract 7.2: an `OpKey` holds the operation, arguments, input identities, class and fidelity, so a range-dependent note would be uncacheable.
**Fix:** (1) `anvil::resolve` reports only what it can compute locally: `Note::NearTie { runner_up, margin }` when the winner's certified margin in the ranked measure is below a declared relative band (default 5%). (2) Add an on-demand node `anvil::query_stability(query, ranges)` that evaluates a fixed, label-free design: each declared parameter at both endpoints one at a time, the current point ±10%, and 64 scrambled Sobol points over the declared box seeded from argument values; it reports `RankSwap { at }` with the sample, and its evidence is labelled `Sampled`, never a guarantee. Protected-branch CI runs it on every query that ends in a rank selector or reaches an `Ordinal` id. (3) Extent-use parameters fail with `ResolveError::Fragile { reason }` on a rank selector without `on_fragile: Accept`, and on an `Ordinal` id. (4) Replace the box-minimum ordinal with an order along the splitting tool's own role order where one exists. (5) Reword contract 5: "Never silently picks another entity at the evaluated configuration; stability across declared ranges is sampled evidence."

### R9-01 · Critical · Targets: CONTRACT, KLN, AGT, ELX, MFG
**Section:** CONTRACT 5 (`ApprovalSubject`); KLN "Revisions and lifecycle states" (D-KLN-26), "Change orders" (D-KLN-28); AGT "Acts and approvals" (D-AGT-20); ELX "Software and firmware as BOM items"
**Problem:** The binding `ApprovalSubject` covers only geometry and PMI, so an approved release does not bind the firmware, material, properties, documents or programs it ships. The release plan's digest deliberately excludes the `ChangeId`, so after approval anyone who can push may rebase onto a Change with the same subject but a different Software item binary or Material, and the approval stays valid. KLN's `ItemDefinition` is richer than the contract's subject but is defined only for Parts and Assemblies, and the contract wins where they differ.
**Evidence:** Contract 5: "`ApprovalSubject` [KLN]: `{ base revisions, ItemDefinition GeometryIds with PMI attached by canonical entity number, check-verdict digest …, effectivity, evidence record ids }`". KLN l.490: "A revision's `ItemDefinition` holds the `GeometryId`s of the Part or Assembly with PMI …, the `Material` version, properties, the BOM by value and documents by semantic content" (no rule for Software, Document, `Program` or `Purchased` Items). AGT l.889: "A release plan's digest covers the `ApprovalSubject`'s `ObjectId`, the tag and the effectivity, never the `ChangeId`". ELX l.798: a Software item "records its item number, version, binary hashes, source repository and Change, toolchain". A firmware or material swap changes no `GeometryId` and no PMI, and changes a check-verdict entry only if some check happens to read it.
**Fix:** Contract 5 replaces the second element: "`ItemDefinition` digests of every affected Item (KLN), for every Item kind". KLN defines `ItemDefinition` per kind in one table: Part and Assembly (name-free identity per R9-12, PMI by canonical entity number, `Material` `ObjectId`, properties, BOM by value); Document (semantic content); Software item (binary hashes, software bill of materials digest, `load` bindings, toolchain digest); `Program` (posted text digest and its simulation evidence ids); `Purchased` (approved-manufacturer list entries). Late-bound fields stay placeholders. AGT's release plan digest keeps excluding the `ChangeId`, and `act.commit` refuses a tag target whose recomputed subject differs from the approved one. New oracle KLN-O-CHG-2: swapping a Software item binary, a Material version or a document after approval voids the approval, while a rename with `#[was]` does not.

### R9-04 · Major · Targets: CONTRACT, KLN, AGT
**Section:** CONTRACT 5 (`Labels`), 7.6 (context labels, free text); KLN "Labels and export control"; AGT "Context labels and write-down", "Instruction authority and untrusted content", "Risk classification", "Auto-merge" (D-AGT-16, D-AGT-17, D-AGT-24)
**Problem:** `integrity` is part of the label lattice that Kiln joins through every derivation, and catalog content, imported files and all third-party package data are untrusted origins. A real product contains catalog parts and imported STEP, so nearly every derived value carries `data_untrusted`, every agent context that reads one is flagged, every agent Proposal is at least R2, and auto-merge never applies. The contract says a human merge endorses typed values, but no rule says how endorsement changes the integrity label of the inputs Kiln joins, so either the flag saturates or it contradicts endorsement.
**Evidence:** Contract 5: "The join takes the maximum level and the union of each set … Labels are joined through every derivation by Kiln". AGT l.750: "Untrusted origins include imported files, supplier, catalog and web content, all third-party package text". AGT l.653 (D-AGT-16): "any content from a `data_untrusted` context is at least R2"; D-AGT-17: auto-merge only for contexts "free of `instruction_tainted` and `data_untrusted`". Contract 7.6: "A human merge endorses structure and typed values, never free text".
**Fix:** Contract 5 states the integrity rule once: integrity attaches to input cells by provenance, and a human merge of the Change that introduced a typed input (a lockfile pin, an Asset, a source span) clears `data_untrusted` on that input's typed values; free text still needs per-span endorsement. Kiln joins integrity from input cells' current endorsement state, so values derived from a merged catalog pin are trusted data, while unmerged supplier submissions, extraction output and `read.value` handles stay `data_untrusted`. KLN-O-LABEL-1 adds two cases: a merged catalog pin yields trusted derived values; the same pin on an unmerged branch does not.

3. Robot programs transfer only as program files into the controller's program store, never through script or dashboard interfaces (transport per vendor [unverified]).

D-AGT-12 requires a verifier on every agent Proposal, and protected branches require human review.
**Fix:** State in contract 13.2 that the engineer-year figures are human effort with no swarm credit. Measure the factor in phase 0 on three oracle-covered work streams: `detmath` Rust ports against the C build, STEP entity codecs from the EXPRESS generator, and toolkit widgets against UIX-O-INT-1. Measure accepted Proposals per reviewer-hour, defect escape rate, and agent compute cost. From the phase 0 gate, credit capacity at the measured factor, capped at 1.5, only to work items that meet R12-02's eligibility rule. Budget reviewer time explicitly, as a stated number of reviewer-hours per accepted agent Proposal.

### R12-15 · Major · Targets: PLT, UIX, AGT
**Section:** PLT OS services (`Authenticator`), capability "WebAuthn"; UIX Approvals (D-UIX-29); AGT D-AGT-20
**Problem:** Every Act approval needs WebAuthn user verification, which PLT's `Authenticator` provides natively on each desktop. On Apple platforms an app can use passkeys only for relying parties listed as its associated domains, so the native macOS app cannot approve against a customer's self-hosted team server, the only server in phase 1. PLT names no Linux mechanism. Approvals on a general-availability Tier 1 target therefore fail for the phase 1 deployment model.
**Evidence:** Apple, Supporting passkeys: "You need to have an associated domain with the `webcredentials` service type when making a registration or assertion request; otherwise, the request returns an error"; "Your app can't use passkeys to authenticate for services that you haven't configured as the app's associated domains" (https://developer.apple.com/tutorials/data/documentation/authenticationservices/supporting-passkeys.json). PLT: "`Authenticator` returns WebAuthn assertions with user verification for the approval page"; capability "WebAuthn | `Authenticator` assertions with user verification | ... | 1". KLN phase 1: "a single-node team server".
**Fix:** Native desktop and tablet clients open the approval page in a browser session: `ASWebAuthenticationSession` on macOS and iPadOS, and the default browser on Windows and Linux, bound to the request id and returned to the app by a `crucible://` callback. The browser, not the app, performs WebAuthn, for any relying-party domain. `Authenticator` is used natively only where the relying party is an associated domain of the shipped app (Crucible's own cloud). PLT-O-OS-4 adds an approval against a self-hosted domain on every desktop OS.

### R12-16 · Major · Targets: AGT, KLN, MFG, UIX, CONTRACT
**Section:** AGT Acts and approvals (D-AGT-20, D-AGT-30); KLN Phasing (`release_data` for STEP and 3MF exports); MFG D-MFG-25
**Problem:** Every byte that leaves a tenant goes through the `release_data` Act family, and every Act needs an assigned Approval on the server's page with WebAuthn. KLN applies this to STEP and 3MF exports in phase 1, and no tab says where the tenant boundary lies for a local file. So the phase 1 wedge user, who hands a 3MF to their own slicer (D-MFG-25) or saves a STEP file for a shop, needs a team server, an inbox, a passkey and a recipient record for each export. The spec does not define whether a desktop install without a server can export at all.
**Evidence:** D-AGT-30: "Every byte that leaves a tenant goes through one Act family, `release_data` ... restricted-party screening ... audit". D-AGT-20: "`act.commit` creates an approval request that Cedar policy assigns to named approvers ... after phishing-resistant WebAuthn user verification". KLN phase 1: "`release_data` for STEP and 3MF exports". D-MFG-25: Crucible "writes a 3MF build ... and opens it there". Contract 13.1 names phase 1 the "Wedge: code-CAD and 3D printing".
**Fix:** In D-AGT-30 and KLN, define the tenant boundary for local files. A human principal writing an export to a local folder or a local application is an audited local write, not an Act, when the payload's label is `public` or `internal`, carries no export control, and is not addressed to a recipient record. Agent-prepared exports, labelled or controlled payloads, and every transfer to another organization stay `release_data` Acts. State in contract 13.2 whether phase 1 supports a desktop install without a team server, and what it can do.

### R12-26 · Minor · Targets: AGT
**Section:** AGT Phasing, phase 1
**Problem:** AGT's phase 1 gate contribution includes "pass^1 ≥ 80% and pass^4 ≥ 60% on the best qualified endpoint", measured through external MCP hosts and third-party models. Whether a phase gate passes should not depend on a vendor's model release.
**Evidence:** AGT Phasing, phase 1: "Golden tasks on GP1 and GP2 reach pass^1 ≥ 80% and pass^4 ≥ 60% on the best qualified endpoint (targets)".
**Fix:** The phase 1 gate contribution becomes "the golden-task harness, injection suite and qualification run on at least two endpoints and report pass^1 and pass^4". The thresholds govern which endpoints qualify for each role (AGT's endpoint qualification by golden tasks), not the phase gate.
