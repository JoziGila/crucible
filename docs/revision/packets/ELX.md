### R4-03 · Critical · Targets: ELX, KLN
**Section:** ELX Writing a circuit; State of the art (connectivity capture); KLN Merge (D-KLN-21).
**Problem:** Because `connect` accumulates idempotently as a set union, two branches that each attach the same pin to a different net merge without textual conflict and silently short the two nets. None of KLN's five merge conditions catches it: the merged program compiles, Queries resolve, ERC passes unless pin types or voltage domains clash, and DRC follows the merged netlist, so the short becomes the design. ELX's merge target scores this case as a success.
**Evidence:** ELX: "`connect` statements accumulate into one value, and connecting the same pins twice is idempotent."; State of the art target "Scripted concurrent-edit branch pairs, target 100% merged without manual conflict when edits touch different nets". KLN D-KLN-21: merge succeeds when the design "compiles, resolves, passes every check that both parents passed, and shows no new geometric overlap or interference". Example: branch A adds `connect(u1.pin("PA5"), led_net)`, branch B adds `connect(u1.pin("PA5"), button_net)`; the merge joins both nets through PA5.
**Fix:** KLN adds a sixth merge condition: "Connectivity. The driver computes the net partition (pins per net) of base, both sides and merge. A merged net that unions nets that are distinct in the base and in each side is `Conflict::NetMerge`, naming the pins, both nets and both Changes. Net renames are matched by provenance, not by name." ELX adds an ERC rule that two named nets join only through an explicit `tie(...)` element (R4-22). Replace the ELX target with "100% of net-merging branch pairs reported as conflicts; 100% of non-overlapping pairs merged clean". Apply the condition to harness `Circuit`s and `std::systems` interface connections too.

### R5-03 · Critical · Targets: KLN, CONTRACT, AGT, FLX, ELX, COV
**Section:** KLN Distributed and remote evaluation (D-KLN-9), Threat model (Cache poisoning); contract §7.1 (Kiln)
**Problem:** The machines allowed to sign shared-cache attestations (CI runners and organization workers) also evaluate untrusted Proposals and run untrusted native code as External Ops (supplier FMUs, IBIS-AMI DLLs, emulators) inside ordinary Linux containers. One escape yields a signing identity that can map any `OpKey` to any output, and 1% spot re-execution catches a poisoned entry that a release consumes once with probability 0.01. Every tenant shares the global public cache domain, and no trust rule stops one tenant's builders from poisoning std results for all of them.
**Evidence:** D-KLN-9: "Only trusted builders write the shared result cache: CI runners and the organization's workers." KLN: "Kiln continuously re-executes 1% of shared cache hits"; residual risk "A compromised CI worker, caught statistically by spot re-execution". COV: "External tools run only in Linux containers on team servers or cloud workers (D-COV-12)". FLX: "FMUs from outside Crucible are untrusted native code." KLN: values with all-public inputs "live in one global public domain that every tenant shares".
**Fix:** (1) Split the worker pools. `untrusted-eval` workers run Proposal CI from agent and external branches and every External Op, in single-use microVMs (Firecracker- or gVisor-class). They hold no attestation key and write only to a per-Proposal namespace. `trusted` builders evaluate only merged protected-branch revisions. (2) A separate attestation service holds the signing keys and signs `(OpKey, ObjectId)` only for jobs dispatched to trusted builders, bound to workload identity. (3) Release gates and every `SignOff` Check accept a cached result only when two independent trusted builders produced the same `ObjectId` (different hosts; for `Portable` operations, different ISAs); otherwise they recompute. (4) Only the operator's own fleet writes the global public domain, with 2-of-n agreement. The default client trust policy is "own organization plus operator public signers". (5) Weight spot re-execution by downstream fan-out, at 100% for nodes that feed released Checks. (6) Hardware runners sign measurements with TPM-held device keys under measured boot. Reword contract §7.1 to: "Only trusted builders evaluating trusted inputs write the shared cache."

### R1-10 · Major · Targets: FLX, PLT, MEC, ELX, CONTRACT
**Section:** Contract §7.1 ("faer for CPU linear algebra"); FLX "Linear algebra layer"; PLT "Third-party numerical libraries"; MEC solver method; ELX D-ELX-13.
**Problem:** faer's dense kernels come from the `gemm` crate, which sizes the reduction block `kc` from cache size and associativity detected at run time and uses FMA microkernels where available. Any product whose inner dimension exceeds that block (at least 512), such as Gram matrices VᵀV in reduced-order modelling and LOBPCG, therefore sums in a machine-dependent order, and FMA and non-FMA microkernels differ across ISA levels. faer as shipped breaks the canonical class, even within one ISA level, for every `Portable` operation that calls it.
**Evidence:** `gemm-common/src/cache.rs`, cloned from https://github.com/sarah-quinones/gemm: `kernel_params` reads `CACHE_INFO`, filled from /sys or CPUID, and computes `auto_kc` from `l1_n_sets` and `l1_assoc`. `gemm-common/src/gemm.rs` defines `v3_fma` with `f64::mul_add`. https://docs.rs/faer/latest/faer/ shows faer 0.24.4 with "cpu feature detection at runtime" and rayon "global parallelism by default", and says nothing on determinism. PLT itself marks faer's behaviour "[unverified]".
**Fix:** Make a canonical linear-algebra crate (or a pinned faer and gemm fork) a phase 0 deliverable owned by PLT and FLX, with fixed machine-independent block sizes, canonical 512-bit lanes, no FMA, sequential or combinator-partitioned updates, and pivot ties broken by index. Unmodified faer runs only in `CpuIsa` mode, and only with `CACHE_INFO` pinned. MEC's constraint solver, ELX's circuit LU and COV's calibration fits use the canonical crate for `Portable` results. Add a determinism-suite case that runs the same factorization under two different `CACHE_INFO` values.

### R2-23 · Major · Targets: ELX, ANV, CONTRACT
**Section:** ELX Board geometry (D-ELX-6), DRC, Pours, planes and vias; contract 7.1 (`anvil-planar`)
**Problem:** The contract calls `anvil-planar` "exact integer-coordinate 2D geometry with lines and arcs", but its operations are not closed over integers: offsets and Minkowski sums with a disc create tangent points and arc intersections at irrational coordinates, and ELX approximates arcs for Booleans. Results must be rounded to the nanometre grid, so a fill generated exactly at the clearance can sit up to about 0.7 nm too close, and the exact integer DRC then flags Crucible's own fills or needs a hidden tolerance.
**Evidence:** contract 7.1 "exact integer-coordinate 2D geometry with lines and arcs (`anvil::planar::boolean`, `offset`, `distance`, `medial_axis`, Minkowski with a disc)"; ELX "Arcs are stored as three integer points"; "it approximates them for the Boolean and reconstructs them in the result"; DRC "Clearance tests compute exact segment, arc and polygon distances in integer arithmetic". Rounding a point to an integer grid moves it by up to √2/2 grid units.
**Fix:** State `anvil-planar` semantics as "exact predicates on stored integer geometry; constructions snapped to the grid in a declared direction". Every construction that feeds a rule snaps conservatively: fill regions round inward (away from obstacles), keep-outs outward, so derived geometry passes the exact DRC by construction. Arc reconstruction keeps an arc only when it passes the exact check, otherwise its polygonal approximation. Oracle: every derived fill in the DRC corpus passes the exact reference checker with zero tolerance.

### R3-18 · Major · Targets: CONTRACT, ING, KLN, ELX
**Section:** CONTRACT 6 and 14 (variant ruling); KLN "Variants and the 150% BOM" (D-KLN-27); ELX "Variants" (D-ELX-4)
**Problem:** The ruling removed `options` and `when`, but the 150% BOM needs a static account of which Instances exist under which option values, and no tab now provides it. ### R3-29 · Major · Targets: CONTRACT, ING, MEC, ELX, FLX
**Section:** CONTRACT 5 (`Quantity<D>`, ruling ING-7); ING "Dimensions" (D-ING-3)
**Problem:** Making angle a base dimension while keeping torque in N·m leaves the basic laws of rotation ill-typed: power τω, work τθ, τ = Iα and kinetic energy ½Iω² each carry stray radians. ω = √(k/I) yields A^(−1/2)·T⁻¹, which rational exponents accept without complaint. Moment of inertia and rotational stiffness have no stated convention, and for a rotational `Network` port, across times through is not a power.
**Evidence:** With A a base dimension and torque M·L²·T⁻²: τω = M·L²·T⁻³·A; with I = kg·m², ½Iω² = M·L²·T⁻²·A²; k = τ/θ = M·L²·T⁻²·A⁻¹, so k/I = T⁻²·A⁻¹. mp-units' strong angular system, the consistent alternative, uses torque in J·rad⁻¹ and moment of inertia in kg·m²·rad⁻² (https://mpusz.github.io/mp-units/latest/users_guide/systems/strong_angular_system/). ELX: a port type declares "its across and through quantities as `Quantity` dimensions".
**Fix:** Choose one consistent system in phase 0 and publish it as a std table. Recommended: keep A as a base dimension and adopt the strong system for derived rotational kinds: `Torque` = J/rad, `MomentOfInertia` = kg·m²/rad², `RotationalStiffness` = J/rad². Named units keep datasheet literals short (for example, `Nm` defined as N·m/rad, while `[N*m]` stays energy). Each `Network` port type declares its power expression, and the compiler checks that it is a power. ING-O-4 gains 50 textbook rotational formulas that must type-check without casts.

### R4-17 · Major · Targets: KLN, MEC, ELX
**Section:** KLN Revisions and lifecycle states (D-KLN-26); Keys and behavior versions.
**Problem:** "Modified since release" compares evaluated `ItemDefinition`s, which include B-rep `ObjectId`s and controlled documents, so an engine or std upgrade that changes bits within tolerance, or a drafting-package update that re-renders PDFs, marks every released Item modified: the noise D-KLN-26 exists to remove. ### R4-22 · Major · Targets: ELX, UIX
**Section:** ELX Writing a circuit (schematic module and editor behavior); Electrical rule checks.
**Problem:** The stored drawing models pin-to-pin wires only, so real schematics cannot be stored: wires meeting wires at junctions, power symbols, no-connect flags, bus entries, sheet symbols. Nothing stops the drawing from lying: a code edit can leave a drawn wire between pins that are no longer connected, and only removed pins are caught. Labels are drawing items, although in every schematic tool a label is connectivity, and net ties (an intended short at one point) have no representation although IPC-2581C carries intended net shorts.
**Evidence:** ELX: `wire w_3c1 [u1.pin("SW"), l1.a] path [(78mm, 40mm)]`; "A wire end that touches no pin is impossible: the editor snaps or refuses."; "Annotations that point at removed pins fail with `SchematicError::StaleAnnotation`"; ELX contains no schematic junction or "net tie". MFG cites IPC-2581C support for "intended net shorts".
**Fix:** The `Schematic` module stores drawn topology: segments whose ends lie on pins, labels, power symbols, sheet pins or other segments (explicit junctions), plus no-connect flags and bus entries. A blocking check `schematic_matches_circuit` maps each drawn connected group to exactly one net; a group spanning two nets is `SchematicError::DrawnShort`, drawn in the danger style and failing release. Label text equals the net name: editing it renames the net in source, and placing a label with an existing net's name writes a `connect`. Net ties are explicit `tie(net_a, net_b, at: footprint)` elements that ERC, DRC, netlists and IPC-2581 export treat as intended shorts; no-connect flags write `no_connect(pin)`. Oracle: the 10⁵-edit property test also asserts that no drawn group spans two nets after any code edit.

### R4-23 · Major · Targets: ELX

**Problem:** Board designers judge a simulator by whether vendor models run. ### R1-49 · Minor · Targets: ELX, FLX
**Section:** ELX "Thermal" (board model) and "Power integrity" (electro-thermal coupling).

### R1-50 · Minor · Targets: ELX, FLX

### R1-52 · Minor · Targets: FLX, COV, ELX
**Section:** FLX oracle table (patch tests, MMS, shell obstacle course, CEED); ELX dipole oracle.
