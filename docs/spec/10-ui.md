# UI and interaction (UIX)

Crucible's interface is where people inspect, review and present what agents design: a fast 3D viewer, a review desk for proposed changes, and a studio for renders, animations, illustrations and reports. Unlike incumbent viewers and AI-built clones, it computes every picture and number from the live model with its status and error, so reviews, slides and reports stay checkable as the design changes. One Rust toolkit and one GPU renderer deliver this identically on every major desktop system and browser, and change the product only through Crucible's one API.

## The interface at a glance

People meet Crucible through one workspace that opens on evidence. This section walks one review of the canonical bracket, then names the pieces it used.

### A review of the bracket

The canonical bracket of [contract 6](../contract.md#6-ingot-syntax-reference) is an L-shaped aluminium plate with a stiffening web and one named check, `static_margin`, that keeps peak stress below 60% of yield. A detail-designer agent proposes widening it from 60 mm to 80 mm so it spans a new rail. Ana, the engineer who owns the part, reviews and presents the change.

1. **Open.** Her Home page lists the Proposal (an agent's branch with its rationale and CI report) in her review queue. It opens in the Review preset on the views the agent saved.
2. **Evidence first.** The header names the author (the agent, its model and its scope) and the risk class the server computed. Below it come the checks whose verdict or margin changed: `static_margin` passes at `SignOff`, with value, limit, margin and error bound. Mass and cost deltas follow, each with its bound.
3. **Look.** The geometry overlay ghosts the old plate outline in blue and fills the new one in orange. A Field view paints von Mises stress on the true geometry; its legend names the fidelity and outlines the neighbourhoods the check excludes around the clamp.
4. **Mark up and ask.** She circles the web-root fillet and types "What is the margin at 5 mm thickness?". The circle becomes a comment anchored to the fillet's faces and her current view, and the question reaches the agent as a request. The agent answers on its branch with a second study and a rendered image.
5. **Approve.** She approves the merge on the approval page with her security key.
6. **Present.** In the Present preset she builds the design-review page. It holds a fine-line isometric illustration with callouts for width, thickness and the check, an animation of the deformed shape under load, and a generated report. She sends the machine shop a read-only web-view link.

When a later Change edits the fillet radius, the report and the web view re-render from the same saved views, and every number in them follows the model. Nothing Ana did wrote product data outside `api`: the comment, the question and the approval are records, and the presentation is a file in the design repository.

### Places and the workspace

Crucible has six places, each with a stable link.

| Place | Content |
| --- | --- |
| Home | Review queue, approval inbox, agent questions, recent designs, notifications |
| Project dashboard | Release readiness, budgets, open Proposals and CI health across a project |
| Design repository overview | Branches, Proposals, releases, BOM views, check trend, presentations, packages |
| Item (phase 2) | One Item: revisions, documents, BOM, where-used, change orders and their review routes, compliance, cost, similar Items; quality records from phase 3 |
| Packages | ECO's package pages and grants; marketplace listings from phase 2 |
| Workspace | Review, present, steer or inspect one branch |

KLN filters every list by access, so a supplier sees only its package scope. Links are `https` on the web and a URL scheme on desktop; they navigate but never act. The breadcrumb `organization / project / design repository / branch` doubles as the branch switcher.

The workspace is one window of regions that dock, collapse and remember their layout per preset and user.

| Region | Contents | Default placement |
| --- | --- | --- |
| Top bar | Breadcrumb, the design's label, preset switcher, palette, presence, notifications | Top |
| Model tree | Structure, features, studies, setups, checks, saved views, presentations | Left, 280 px |
| Viewport | 3D view or a 2D canvas, up to 2×2 | Center |
| Review and agent panels | Proposal, diffs, verdicts, comments; agent conversation, timeline, steering | Right tabs |
| Properties | Parameters, exact measurements, placement | Right, 320 px |
| Code panel | Ingot source of the current file | Beside the viewport from 1,600 px wide, else a tab |
| Version history | Changes on this branch | Bottom, collapsible |
| Status bar | Evaluation progress, result status, display accuracy, units, selection, connection, key hints | Bottom edge |

Detached windows arrive in phase 2. Below 1,280 px side panels become drawers, and below 768 px bottom sheets. The top bar shows the open design's label (confidentiality level, controls and scopes), and every rendered image, export and web view carries it.

**Decision D-UIX-1:** The UI holds no product state: product changes are `api` Edit or Propose calls, and personal views live outside Changes.
*Why:* agents and people must reach the same product through one API (principle 2), while personal camera moves would flood history.
*Rejected:* feature records kept in the GUI, a second source of truth; camera and visibility stored in the model, which makes diffs and merges noisy.

Every command records its `api` call, and "Copy as `api` call" hands any manual step to an agent or a script.

### Presets

A preset arranges the one workspace for a kind of work. Review is the default, because most people open Crucible to judge what an agent did.

| Preset | Primary tools | Default view |
| --- | --- | --- |
| Review | Proposals, diffs, comments, markup, verdicts, variants | Compare overlay; review panel, agent timeline |
| Present | Scenes, illustrations, animations, renders, web views, documents | The scene camera; presentation outline, figure preview |
| Design | Generated dialogs, handles, assembly, measure, code | Shaded with edges; tree, code, properties |
| Simulate | Study templates, conditions, results | Field view; studies, legend, checks |
| Manufacture | Setups, toolpaths, additive preparation, cost, MBOM | Toolpaths; playback, cost |
| Electronics | Schematic, layout, constraint manager, waveforms | 2D canvas beside a 3D board; nets, layers, rules |

**Decision D-UIX-2:** Review, Present, Design, Simulate, Manufacture and Electronics are presets over one workspace that set layout, tools and default view; Review is the default, and switching keeps data, selection and camera.
*Why:* people alternate between judging, showing and steering many times an hour, and one model has one workspace (contract 7.6).
*Rejected:* separate applications per domain, which duplicate state and need export round trips; presets that own data, which couple hidden state to a layout.

Ctrl+1 to Ctrl+6 (Cmd on macOS) switch presets.

### What every result says

Every displayed Body, Field, metric and check carries its result status, the answer to "is the value here and current?" ([contract 5.2](../contract.md#52-how-far-to-trust-a-number)). The quiet default is `Ready` at or above the fidelity the view or check declares; a lower fidelity shows the derived "provisional" badge.

| `ResultStatus` | Viewport | Elsewhere |
| --- | --- | --- |
| `Pending` | Last geometry, progress mark at the edited feature | Spinner; a branch awaiting `Undecided` names the fidelity |
| `Proxy` | Dashed outline, label "proxy": the value is extrapolated from its last one while it recomputes | Values greyed |
| `Ready(Preview)` | "Preview ±0.2 mm" near the edited feature | "≈" and the bound |
| `Ready(Interactive)`, `Ready(SignOff)` | Plain at the declared fidelity; "provisional" below it | Bound on hover |
| `Stale` | Desaturated only after 300 ms, to avoid flicker | Greyed with "stale" |
| `Failed` | Last good geometry ghosted; failing entity outlined | Typed failure at row, span and status bar |
| `Aborted` | Last good geometry with "stopped" and the reason | Retry; nothing cached |

A check's verdict shows as a glyph and text, never by colour alone.

| Verdict | Glyph | Text |
| --- | --- | --- |
| `Pass` | Check mark | Value, limit, margin and bound, with any policy allowances it read |
| `Fail` | Cross in an octagon | Margin and location |
| `Undecided { reason, needed }` | Question mark in a circle | Reason and accuracy needed, with "Refine" or "Evaluate at `SignOff`" |
| `Error(Failure)` | Bar in an octagon | Typed failure with fixes |
| `Skipped { reason }` | Dash | Reason |

Failures show message, cause, location links and fixes; each fix is a previewed edit taken from a typed failure such as `ResolveError`. The status bar shows Kiln's progress ("`Interactive` 128/203 nodes") with a cancel control.

### Saved views, rendered images and render profiles

A `ViewState` is everything needed to look at the model a particular way. Comments, rendered images, presentations, web views and agents all point at one.

```rust
/// Presentation only. Never part of the model, never affects evaluation.
pub struct ViewState {
    pub at: Option<ChangeId>,              // a pinned Change, or None to follow the branch head
    pub camera: Camera,                    // f64 eye, target, up; perspective, orthographic or isometric
    pub style: DisplayStyle,               // ShadedEdges, Shaded, Wireframe, HiddenLine, Illustration (phase 1);
                                           // XRay, Realistic (phase 2); an unavailable style draws as Shaded, with a notice
    pub visibility: Vec<VisibilityRule>,   // hide or isolate, each by Query
    pub sections: Vec<SectionCut>,         // up to six planes or one box
    pub field: Option<FieldView>,          // see Field views
    pub explode: Option<ExplodeState>,     // a step of MEC's explode sequence, or offsets per Instance
    pub animation: Option<AnimationTrack>, // a time range over a motion study, explode sequence, mode or transient
}
```

Shared views are files in the design repository (`views/<name>.view.toml`), so agents read and write them. Personal views and layouts live in a per-user store that `repo` keeps outside Changes.

A Snapshot is the image of a `ViewState` under a `RenderProfile`: locale, theme, display units, pinned font packages and renderer version. The pair determines the image, so a Snapshot re-renders the same way next month and changes only when the model does. Snapshots are never canonical data (the Presentation studio section says why), and they never decide a check.

A dashboard is a file of widgets, each a saved `api` Read query plus a visualization spec, so agents maintain dashboards too. Every chart has a table view for screen readers and export.

### Model tree and version history

The tree unifies structure and the feature list: Assembly, Instances, Part, features and, on demand, the entities each feature created. Top-level nodes add Parameters, Studies, Setups, Checks, Saved views, Presentations and Packages.

- **Rows** show type, name, status glyph, Instance count and presence, never by colour alone. The tree virtualizes 1,000,000 nodes and filters by name, type, status or `Query`.
- **Edits.** Rename writes `#[was(original_name)]`, so call-site identities survive. Delete previews dependents, and reorder refuses illegal moves with the reason ("`web` uses `base`, defined on line 4").
- **Rollback marker.** Dragging it shows the Part as evaluated up to a feature, and edits made there insert at that position.

The *feature list* orders program statements; the *version history* orders Changes in time, and the UI never calls both "history". The version history groups Changes by session and author, people and agents alike. An entry renders read-only, two entries open the review diff, and Restore writes a new Change.

Properties show exact measurements from Anvil (area, length, radius, mass properties with the Material), never values from display meshes.

## Review

Agents author and people judge, so review is the interface's main job. A person must be able to decide in minutes whether a Proposal is right, from evidence rather than a narrated summary.

### The Proposal view

A Proposal opens in the Review preset on its saved views, with its CI evidence before any diff. A Proposal may come from a pull request on another Git host and links back to it (contract 7.1).

| Area | Content |
| --- | --- |
| Header | Title, author (a person, or an agent with model and scope), target branch, labels, risk class with reasons, required reviews |
| Rationale | Text from outside the reader's delegation chain, shown as untrusted text with its origin |
| Evidence | Checks whose verdict or margin changed, then metric deltas, rendered images, studies and manufacturing results, with status and fidelity; for agents, AGT's verifier report, provenance, integrity flags and canonical description |
| Diff tabs | Features, Geometry, Metrics, Source, BOM and lifecycle, Files; Schematic and Layout in the Electronics preset |
| Actions | Approve, Request changes, Comment, Ask the author, Check out |

KLN defines the `ReviewVerdict` and `Comment` records and the branch rules that require reviews; UIX owns `CommentAnchor` and the display. Whether the tabs a reviewer opened are recorded is an organization setting (Collaboration, below).

**Decision D-UIX-18:** Agent activity shows as `api` calls and Changes on the agent's own branch, and any agent action can be inspected, replayed or reverted like a person's.
*Why:* trust comes from seeing real actions rather than narrated summaries, and the contract confines agents to branches.
*Rejected:* chat-only output, which carries no evidence; agents editing the user's working branch, which nobody can review.

### Diffs

Each diff answers one question a reviewer asks, and each is a Kiln node, so source and feature diffs appear at once while geometry refines.

- **Feature diff.** Feature lists aligned by call site, marked added, removed, modified (old → new), reordered and suppressed.
- **Geometry overlay.** Base-only faces ghost in `diff.base` and target-only faces fill in `diff.target`, with a deviation map on modified faces. Side-by-side and swipe views also exist.
- **Correspondence.** The same `EntityId` means the same face, and `HistoryRecord` links pair splits and merges; without provenance, a labelled distance diff applies. Symmetric-difference regions are shown and do not block (contract 7.1).
- **Metrics and source.** Each metric shows base, target, delta and bound, reading "within error" inside the combined bounds. Source diffs are structural, with moves shown as moves and hidden characters marked.
- **Electronics (phase 3).** ELX's schematic diff shows symbols added, removed or moved, wires whose net changed highlighted in both versions, and value changes. Its layout diff shows a per-layer copper difference computed exactly, moved parts with displacement arrows, and rules with the objects they now affect ([ELX](08-electronics-systems.md)).
- **Merge preview.** Before a merge, the panel lists what KLN would refuse, each linked to its place in the model: a check whose verdict worsens, new interference, or an entity touched on both sides ([KLN, Proposals and merge](05-kiln-repo-plm.md#proposals-and-merge)).

**Decision D-UIX-17:** Every comparison uses a blue (base) and orange (target) pair with a second cue: ghost versus solid fill, + and − gutter marks, and labels.
*Why:* WCAG 1.4.1 forbids colour as the only means, and red and green collide for many readers with colour-vision deficiency.
*Rejected:* green and red for added and removed; colour alone.

### Markup, comments and questions

A reviewer steers by pointing, so the cheapest gesture in the interface is to draw on the model and say something. Markup tools draw strokes, arrows, circles and text over a frozen view. On release, each stroke picks the entities it encloses or touches, so the mark knows what it is about.

```rust
pub struct CommentAnchor {
    pub at: ChangeId,                   // the Change the comment was written against
    pub target: AnchorTarget,           // Entities, a Point on a face, a Source span, a Feature or Check call site, a Region
    pub view: ViewState,                // camera, sections and Field view at comment time
    pub marks: Vec<MarkStroke>,         // vector strokes in view coordinates, each with the entities it picked
    pub snapshot: Option<ObjectId>,     // an Asset rendered with the review profile
}
```

**Decision D-UIX-39:** A markup or a question always becomes a record anchored to entities and a `ViewState`: a Proposal comment through `propose.comment`, or an agent request through the agent's session, never a free-floating image.
*Why:* an anchored mark survives rebuilds, an agent can resolve "this fillet" to `EntityId`s without guessing from pixels, and the record joins the Proposal's history.
*Rejected:* screenshot markup attached as an image, which agents must interpret from pixels and which goes stale on the next edit; questions only in a chat pane, which leave no anchored record.

Anchors re-resolve through `HistoryRecord`s on every rebuild: modified entities keep them, splits carry them to every piece, and merges to the result. A deleted target leaves the comment orphaned with a ghost, never attached elsewhere. Agents read comments with resolved anchors, and the mark's strokes reach them as geometry, not as an image.

Merges never endorse free text (contract 7.6). "Endorse text" shows each untrusted span verbatim, with invisible and bidirectional characters highlighted, and endorses one span per action.

From phase 2, "Find similar" in the palette and on an Item page calls KLN's shape-similarity search ([KLN, Items](05-kiln-repo-plm.md#items)). Exact duplicates by `GeometryId` rank first, then near shapes, each with its Item and access-filtered usage. A reviewer can then ask the agent to reuse an existing part instead of approving a new one.

Variant sets (phase 2) show up to 16 linked viewports with one camera, beside a sortable table, a Pareto scatter plot and parallel coordinates. "Promote" turns a variant into a Proposal.

## Approvals

An Act reaches outside Crucible: a release, an export, a program sent to a machine. Its Approval is the last control a person holds over an agent, so it must stay out of reach of any script the agent could influence.

Release and change-order Approvals sign the `ApprovalSubject` (contract 5.6), so re-review after a subject change shows only the delta. Every other Act is approved over its plan's digest.

**Decision D-UIX-29:** Act approvals happen only on the server-generated approval page, served from its own origin and relying-party id, and opened outside the client's own code on every platform.
*Why:* script injected into the main origin must never reach a passkey ceremony, and Apple apps cannot use passkeys for unassociated self-hosted domains [Apple Supporting passkeys].
*Rejected:* a secure dialog per OS; approving inside the app's process, an in-app webview or the viewer of an MCP (Model Context Protocol) host.

### The approval page

- **Origin.** The page lives on AGT's approval origin ([AGT, Plans and the approval page](09-agents.md#plans-and-the-approval-page)), opened through PLT's browser session.
- **Content.** The page shows what contract 7.6 lists, a physical-effect plan's section included. The session's purpose sits collapsed below the typed content as a handle with its integrity flags and expands only on request; text from an `instruction_tainted` context carries a banner naming its taint sources. Steps at a device read as numbered instructions to the person there.
- **Review routes (phase 2).** For a release or change order, the page shows KLN's route: each stage, its quorum, who has signed, who is pending, and any delegation with both names ([KLN, Review routes and delegation](05-kiln-repo-plm.md#review-routes-and-delegation)). The Item place shows the same progress.

The page offers contract 7.6's three outcomes ([AGT, Three outcomes](09-agents.md#three-outcomes)).


### Credentials

Approval credentials are device-bound and never synced (contract 7.6).

Enrolling an approval credential is itself approved on the approval page ([contract 5.4](../contract.md#54-signature-records-and-the-signature-table)). A session that signed in with a synced passkey or single sign-on can request enrolment but never complete it. The page shows each credential's age, and a credential younger than 24 h is greyed for physical-effect Acts and Acts with `controls`.

### Phones, devices and exports

Crucible's phone apps list approval requests read-only. Which Acts a phone browser may approve is contract 7.6's rule; the others show read-only with the reason.

**Physical effects.** The Manufacture preset offers contract 7.6's transfer Acts and, for material-extrusion printers covered by a site safety record, `start_print`. Its confirmation takes the one-time code from the printer's display, or waits for the printer-side button, within 10 minutes before the start. The UI never offers cycle start, resume or jog for any device it transfers to.

**Flashing.** The Electronics preset offers `flash_device`. It flashes only from code that verifies the Approval ([AGT, Physical effects](09-agents.md#physical-effects)).

**Exports.** A person's export of an uncontrolled `public` or `internal` payload to a local folder or application is an audited local write (contract 7.6). Any other export opens an export Act's plan. A desktop install without a team server presents and exports locally, and its Proposal, release and Act commands read "needs a team server".

### Presentation files

A presentation is a file, not a session, so an agent can write one, a reviewer can diff one, and a release can pin one.

**Decision D-UIX-34:** Every presentation output renders from one presentation file in the design repository (`presentations/<name>.present.toml`), through `apps/headless-render` under a pinned `RenderProfile`. The file is an ordered list of scenes, each a saved `ViewState` with callouts, readouts and a caption, under a `report`, `deck` or `figure` layout.
*Why:* one file kind serves reports, decks, illustration sheets and web views, agents author it through `api` like any file, and a pinned profile makes each re-render identical until the model changes.
*Rejected:* a separate slide editor and report generator with their own formats; presentations stored as rendered files, which go stale silently.

A **readout** is a number bound to the model, resolved at render time with its unit, bound and status. It may be a parameter, a measurement, a check's value and margin, a mass property or a cost line. Every number a callout or caption shows is a readout. A typed number with a unit in caption text raises the lint `ui/literal_number_in_caption`, whose fix binds it to a readout. A readout that is not `Ready` at the scene's declared fidelity renders with the provisional badge, so a slide cannot quietly show a stale margin.

Reports render to PDF/A-2u through MEC's drawing pipeline, the archival profile MEC uses for release drawings ([MEC, Drawings](06-mechanical.md#drawings)), and to HTML through `apps/headless-render`. Figures come from Snapshots under the document's pinned profile, and tables come from `api` Read queries, so `std::sim::report` data from Flux, check outcomes and cost lines enter as tables with their bounds. Re-rendering a stored report on the pinned image is byte-identical.

### Figures, typography and the illustration style

The founder's polish reference is the Anatomy project's craft, which builds explanatory figures of real objects and holds them to written rules [Anatomy skill]. Crucible applies those rules with its own renderer to real engineering geometry and Fields.

- **The figure card.** "Fig n" and a short title sit at the top, a live readout at a corner, and the caption and legend below the figure. Words stay out of the drawing apart from callouts and at most one engraved label [Anatomy craft].
- **Typography.** Titles and body text of presentation outputs are set in Source Serif 4, an optical-size serif under the SIL Open Font License 1.1 [Adobe Source Serif]. Numbers use Inter's tabular figures, so columns of readouts align. The canvas is a calm token pair: warm paper with dark ink, or the dark theme's inverse.
- **The Illustration style.** Parts are solid and shaded in four close tones by facing, with lighter tops, and hide what lies behind them. Model edges and silhouettes come from Anvil's exact contours. One subject Instance takes the lit accent tone and the rest stay monochrome; colour appears only when it is the subject, as in a Field or a diff.
- **Cameras.** Isometric presets start at azimuth 45° and elevation 30°, the craft's default, and the figure fills a stated share of its card with consistent scale across a set [Anatomy craft].
- **Callouts.** A callout anchors to an entity like a comment does. Its leader ends on the entity's surface, never in air, and its label clears the geometry.

**Decision D-UIX-40:** Presentation outputs use the figure card, editorial serif typography and the Illustration style by default, and every callout and readout is anchored to the model.
*Why:* the reference shows that calm, solid, precisely labelled figures explain machines better than CAD screenshots, and anchoring keeps them correct as the design changes.
*Rejected:* default CAD shading with blueprint furniture (floating leaders, numbered balloons, dashed hidden edges) on presentation figures; per-output hand styling that agents cannot reproduce.

Drawings keep their standards: MEC's sheets follow ISO 128 and ASME Y14, and the Illustration style never applies to a release drawing.

### Exploded views and motion

Exploded views come from MEC's `explode(asm, steps)`, or from `explode_auto`'s proposed steps ([MEC, Designing across parts](06-mechanical.md#designing-across-parts)). Each Instance moves along its step's direction, and trail lines join its two positions.

Motion is calm and explains a change of state: parts move on critically damped springs along their real disassembly directions, the camera eases over 350 ms, and nothing snaps. Animations pause off screen. Under reduced motion every animation shows one still key frame with a time slider. Video export encodes AV1 with rav1e, a Rust encoder under BSD-2-Clause that enters through PLT's dependency register [rav1e].

From phase 2, animation of moving parts plays MEC's motion studies, whose `Field<(Instances, Time), Transform>` gives every Instance's placement over time, at contract 13.3's rate. A study that reaches a singular position or a limit shows the failure at its time, and interference found by the study is marked in the frames where it occurs.

### Photoreal rendering

Industrial designers, marketing and design reviews want photoreal images from the first concept, and incumbents such as Onshape build them into the product [Onshape Render Studio].

**Decision D-UIX-37:** From phase 2, photoreal images come from a progressive path tracer in compute shaders on G1 and G2, over a two-level bounding volume hierarchy of `DisplayPackage` clusters. A CPU path in `apps/headless-render` serves G3 and servers.
*Why:* wavefront path tracing maps well to GPUs without hardware ray queries [Pharr 2023], reusing display clusters keeps one geometry source, and a CPU path gives every tier the same image.
*Rejected:* waiting for hardware ray queries in wgpu, which not every tier exposes; an external renderer as the only path, which breaks the link between the render and the live model (glTF and OpenUSD export remain for people who prefer one).

The `Realistic` style rasterizes reduced OpenPBR in motion and accumulates path-traced samples when the view is still, until contract 13.3's photoreal row is met. Appearances are OpenPBR records, environments are HDR images shipped as packages, and render scenes are saved views, so a render follows the model.

### Effects from Fields

Convincing fluid, heat, flame and plasma make a simulation legible to people who do not read colour maps. Crucible draws them from data.

**Decision D-UIX-35:** Every visual effect is a visualization of a Field, rendered in the scene's camera and depth. Flow volumes come from velocity and density Fields, glow from temperature Fields as black-body emission, and discharge from electromagnetic Field magnitudes; an effect from an authored analytic Field is captioned "illustrative".
*Why:* an effect drawn from the result is evidence, and the same mechanism serves an illustrative effect without a second, decorative path.
*Rejected:* decorative particle effects untied to results, which a viewer cannot tell from computed ones; effects composited in a separate pass with its own camera, which drift from the geometry.

Effects follow the craft's rule that nothing pops: each effect's intensity rides an attack-and-decay envelope, phase changes cross-fade, and every term fades to zero before the edge of its domain [Anatomy craft].

### Shareable web views

A link is how most people outside engineering see a product, so a web view is the same scene, live, in any browser.

**Decision D-UIX-38:** A shareable web view is a read-only bundle of display data (`DisplayPackage`s, Field display payloads, Snapshots and resolved readouts, never source) behind a label-checked link. A link for people outside the organization is created by a `release_data` Act naming the recipients, and "anyone with the link" is allowed only for `public` payloads whose licences permit it.
*Why:* a viewer that loads no engine module opens within contract 13.3's web-view row, and display data reveal geometry but never the design program, so the exit is visible, approved and minimal.
*Rejected:* sharing the design repository read-only, which exposes source; video-only sharing, which loses orbit, sections and Field toggles; ungoverned public links.

A web-view reader orbits, sections, scrubs animations, switches Field views and opens the presentation's scenes. Links expire and revoke, and comments from outside the organization arrive as untrusted text.

### Rendered images and the audit

`inspect.render`, AGT's method, dispatches to `apps/headless-render`, a service that links the renderer, so `api` depends on neither. It renders a `ViewState` under a `RenderProfile`.

**Decision D-UIX-26:** Snapshots are non-canonical: each carries `PlatformClass::Unverified`, the renderer identity and its `RenderProfile`, and never enters another node's key or an approval subject.
*Why:* software rasterizers generate code for the host CPU at run time [Mesa llvmpipe], macOS has no software renderer, and legends depend on locale and units.
*Rejected:* byte identity across the canonical class, which cannot hold; Snapshots without a profile.

Comparisons use ꟻLIP thresholds, and Proposals and benchmarks use one review profile (`en`, SI with millimetres, light theme). Byte identity holds only on one pinned CI image, with a pinned lavapipe build and fixed `LP_NATIVE_VECTOR_WIDTH` and `GALLIUM_OVERRIDE_CPU_CAPS`. A Proposal's Snapshot is stored once as an Asset, so reviewers and approvers see the same bytes. A render is instruction-capable when imported appearance or any visible Body derives from an untrusted node, and agents query it only through AGT's templated `inspect.ask_render`.

**Decision D-UIX-36:** Before an output publishes or a web-view link is created, a presentation audit refuses it with `PresentationAuditFailed { check, scene, frame }` unless every check holds. No configuration shows interpenetration beyond declared contacts, every shown Instance is mounted, every callout ends on its entity, every number is a `Ready` readout or badged, every text fits its box, nothing pops between frames, and a reduced-motion still exists.
*Why:* the reference's renders check themselves before anyone sees them [Anatomy craft], and an engineering figure that shows parts passing through each other or a stale margin misleads its readers.
*Rejected:* a manual checklist; auditing only stills, which misses faults between animation frames.

The audit uses the model, not pixels. MEC's interference check runs at each explode step and at sampled animation frames, mounting reads the mates, and readouts compare with Kiln's current values. Its result is stored beside the output.

## Steering: asking, pointing and editing

Agents author the program, but people still point, ask, nudge a value or place a part. Every gesture here therefore writes the same Ingot program an agent would, through the same `api`.

### Asking agents

The command palette (Ctrl+K or Cmd+K) ranks commands, features, entities, files, branches, Proposals and settings by match, recent use and preset. Palette, menus, toolbars, keymaps and context menus derive from one command registry. A query that matches nothing, or starts with `>`, goes to an agent as a request, and the palette says so first; from phase 2 the hosted crew answers it.

The agent panel shows the request, a scope chip (permissions, cost cap, time limit), the plan as `api` calls, a timeline and a budget meter. Its controls are Pause, Steer, Fork and Take over. Attachments (a selection as a `Query`, views, comments with their marks, files) enter the agent's context as untrusted text with their origin, never as goal text.

- **Who steers.** Only the delegating human steers, pauses, forks or takes over. Anyone else's steer or mention becomes an inbox request for that human.
- **Steer, pause, rewind.** Steer and Pause use AGT's `session.control` (phase 2, with the hosted crew), and a steer arrives at the next step boundary. Pause stops after the current `api` call, and Kiln cancels in-flight Evaluations, so no half-applied edit exists. "Continue from here" forks a branch at a timeline Change.
- **Pins and questions.** Pins ("do not change the mounting holes") become `require` checks on the branch. Agents ask through typed question cards whose answers return as typed data.
- **Verdicts.** Reject needs a reason, which the agent receives. Cherry-picked features form a new Proposal, which runs its checks before approval.

### Generated dialogs and edit plans

Feature dialogs are generated from Ingot `Feature` metadata: typed fields with units and ranges, toleranced inputs, enumerations, and selection fields that show the readable `Query`. Typing `=` makes any field an expression. Dialogs are modeless: edits preview through literal overrides, Done writes one Change, and Cancel writes nothing.

Every direct manipulation produces an `EditPlan`: the intent plus ranked candidate edits that would realize it. A `LiteralSite` is a call site plus an argument slot (contract 5.5).

```rust
pub enum ManipulationIntent {
    MoveEntity    { target: Query, delta: Transform },
    SetMeasure    { target: Query, measure: Measure, to: DynQuantity },
    PlaceInstance { instance: InstancePath, to: Transform },
    CreateFeature { call: FeatureCall },
}

pub enum EditCandidate {
    SetLiteral    { site: LiteralSite, to: Value },                    // change one literal
    SolveLiteral  { site: LiteralSite, through: CallSite, to: Value }, // invert an expression
    SetParameter  { symbol: Symbol, to: Value, uses: u32 },            // a shared parameter
    InsertFeature { after: CallSite, source: IngotSnippet },           // a direct-edit feature
    SetPlacement  { instance: InstancePath, to: Transform },
}

pub struct EditPlan { pub intent: ManipulationIntent, pub candidates: Vec<EditCandidate>, pub chosen: usize }
```

1. **Driving literal first.** The first candidate is the literal whose call and role created the dragged entity, such as an end cap's extrude distance. Other literals follow by dependence distance, and from phase 2 Anvil's shape derivatives (`anvil::shape_velocity`) refine the order.
2. **Solve through expressions.** For `width / 2`, ING's forward-mode derivatives solve for the free literal from phase 2. When several literals contribute, the plan lists each and never edits more than one silently.
3. **Warn on shared parameters.** "Used by 3 features" appears, and "change only here" introduces a new literal that the diff shows.
4. **Fall back to a direct-edit feature** over Anvil operations, with no privileged path.

During a drag, a chip states the candidate before release ("thickness 4 → 6.2 mm", or "adds `offset_faces` after `fillet`"). Tab cycles candidates, and the code panel shows a ghost diff.

**Decision D-UIX-15:** Gestures edit source through ranked edit plans, changing the driving literal or else appending a direct-edit feature, and a drag evaluates literal overrides so release writes one Change.
*Why:* one model with several editors; intent survives where parameters exist, and history-free editing stays possible where they do not, as in Plasticity and Shapr3D [Shapr3D].
*Rejected:* edits that rewrite history invisibly; refusing direct edits on unparameterized geometry; derivative ranking in phase 1, which needs `shape_velocity`.

### Drag preview

A drag must answer within a frame while the model takes longer to rebuild, so the preview stages its work and writes only on release.

| --- | --- | --- | --- |

A drag runs as AGT's `edit.stream`: a session-scoped stream of override updates that ends in one `edit.apply`. Kiln evaluates each update at the `Drag` priority class, which PLT runs on the `Drag` pool lane ahead of `Foreground` work. Results under overrides key on those overrides, never enter the shared cache and never answer a request without them ([KLN, Scheduling and cancellation](05-kiln-repo-plm.md#scheduling-and-cancellation)).

When a value fails to build, the handle shows the typed failure and the last value that built. Release then offers "Use 7.8 mm (last value that built)", "Keep 9 mm (fails to build)" or "Cancel". Escape writes nothing. Overrides key by `LiteralSite`, which follows `#[was]`, so a concurrent rename maps the override to its new site and the drag continues. Only a deleted literal ends the drag, with a notice.

### Handles and dimensions

Features declare handles (linear, angular, radial, point, planar, count) in their metadata, so std and user packages behave alike. The gizmo draws arrows, rings and plane squares at a constant 96 px. Typing during a drag enters an exact value, or after `=` an expression.

Drags step by zoom-adaptive 1, 2, 5 increments. Alt (Option) moves freely, Shift locks the direction or inference, and Ctrl or Cmd gives one-tenth speed. Control-vertex drags on surfaces (phase 3) use Anvil's `Preview` re-evaluation with zebra and curvature Fields within 16 ms (target).

- **Push-pull** on an end cap changes the extrude distance. On other faces, phase 1 plans `anvil::offset_faces`, which rebuilds adjacent blends with the same parameters and ids; `move_faces` joins in phase 2. A blend that cannot regrow fails with `BlendRegrowFailed`, offering "remove blend" and "reduce radius".
- **Boolean choice.** A chip cycles New Body, Join, Cut and Intersect, defaulting to Cut when the drag enters material.
- **Dimensions.** Selecting a feature shows its driving dimensions at a constant 12 px. Clicking one opens an inline editor for values, units, expressions and tolerances (`4mm ± 0.1mm`), bound through the same `EditPlan`.

### Assemblies

In phase 1, Insert Instance and Add mate are generated dialogs built from `instance` and the mate functions' metadata. Their frame fields take selections as `CoordSys` queries, and the solved placement previews before Done writes one Change. Nobody types Ingot to place a part.

From phase 2, mates draw as glyphs and Instances drag within their remaining degrees of freedom through MEC's solver. "Test motion" moves a mechanism without writing and highlights interference.

"Edit in context" (phase 2) draws the assembly transparent around the Part being designed. Selections on other parts become `Query`s in a context pinned to a past Change of the assembly, which MEC records in `ingot.lock` ([MEC, Designing across parts](06-mechanical.md#designing-across-parts)). "Update context" opens a Proposal that moves the pin and shows the geometry diff, so a cross-part reference is always explicit and reviewed.

### Sketches and reference images

Agents and Ingot sketch from phase 1. The GUI's own sketch tools arrive in phase 2 (contract 13.2). Each writes one of MEC's sketch edits as a source rewrite: trim, extend, split, sketch fillet and chamfer, offset and use edges ([MEC, Sketching](06-mechanical.md#sketching)). Sketches start on a plane, datum or planar face referenced by `Query`.

Inference follows SketchUp [SketchUp drawing basics]: endpoints, midpoints, centres and intersections become `coincident`, and on-edge points `on(entity)`. Directions, equal lengths and 15° steps become the matching constraint, `equal` or a dimension; in 3D the same inferences become `Query` references. Candidates lie within 8 px for mouse and 16 px for touch, with 3 px hysteresis, and each accepted one becomes an explicit constraint call.

Anvil's `solve_constraints` runs every frame while under-constrained geometry moves, within MEC's solve targets, and release writes the solved seeds as one Change. The status bar states the remaining degrees of freedom, and MEC's `SolveReport` draws free motions as arrows. Under-, fully and over-constrained geometry differ in colour and stroke, and each conflict member offers its fix (delete, reference or swap). "Constrain fully" asks an agent for an `EditPlan` preview.

From phase 2, a reference image shows under the sketch, and sketch tools trace over it with the usual inference. MEC's `canvas` feature places it on a plane, calibrated by two points and a length. It is display-only and never part of the Item's definition.

### Tables

From phase 2, a family table editor shows MEC's `family(f, key:, rows: table { … })` literal as a grid with typed, unit-aware cells. It pastes from spreadsheets, shows each row's build status from `RowFailed`, and writes each edit as one Change.

### The code panel

**Decision D-UIX-16:** The code panel is a first-class editor in every preset, linked to geometry through provenance, and ING's language server serves people who prefer their own editor.
*Why:* one model with several editors, and code-CAD users already live in editors that a phase 1 panel cannot out-compete.
*Rejected:* an embedded Monaco, a second text stack; a read-only code view; a full IDE in phase 1.

Phase 1 covers editing, semantic highlighting, diagnostics with fixes, hover with evaluated values, inlay hints, unit-aware completion, navigation and number scrubbing. Refactoring, structural selection and code lenses follow in phase 2, and Vim bindings in phase 3. First-party VS Code and Zed extensions send a custom request that drives Crucible's viewport.

- **Links.** A caret in a statement tints the entities it created and outlines those it modified. Selecting an entity reveals its statement through ING's source map. Hovering `web.edges(joined)` highlights every resolved entity with a count, and a `ResolveError` ghosts the expected ones.
- **Hidden characters.** The editor and every source diff mark bidirectional controls, invisible characters and confusables, answering Trojan Source (CVE-2021-42574 and CVE-2021-42694) [Trojan Source].
- **Edits from tools** reformat only the edited node and keep comments. A rope with incremental re-parsing keeps keystroke-to-paint under 8 ms in a 50,000-line file (target).

Undo writes inverse Changes for the principal's own Changes, and redo writes them again; others' work is undone by rejecting or reverting its Proposal. A drag, dialog or command is one step, and typing groups by word or a 500 ms pause. A later edit to the same statement offers keep, revert or diff.

## UI toolkit

Everything above is drawn by one Rust toolkit. It must render on the GPU, shape every script, virtualize million-row trees, expose a full accessibility tree on every Tier 1 platform, and handle input method editors (IME), the system components that compose Chinese, Japanese, Korean and other scripts. No surveyed toolkit does all of this:

| Option | Gap for Crucible |
| --- | --- |
| GPUI | Tied to Zed, with no documented browser target; Narrator could not read it in a 2025 Windows test [boringcactus 2025] |
| egui | Its README documents AccessKit on Windows and macOS only [egui] |
| Masonry | Paints through Vello and wgpu; its README names backends for winit and Android, not the web [Masonry] |
| Slint | A second UI language |
| Webview shells | A second runtime |

**Decision D-UIX-3:** Crucible builds its own retained-mode GPU toolkit in the style of GPUI, on Taffy, Parley, AccessKit and wgpu.
*Why:* Masonry lacks a non-compute paint path for G3 and a browser target, and closing both gaps is the toolkit's own renderer work.
*Rejected:* Masonry, with no G3 path and no web backend; GPUI, tied to Zed; egui, with no web accessibility; a bake-off whose fallback was fixed in advance.

Chain C of contract 13.2 starts with a risk spike on the toolkit's hardest parts, named in the capability table below. If a part misses its oracle, chain C is re-planned and the toolkit choice stands.

### Architecture

Interface state lives in typed cells (`State<T>`), and product data enters them only through `api` subscriptions. The toolkit, the renderer and every UI entry point depend on `api-schema`, the method catalog and client stubs, and never on `api` itself, so no UI process links the engine (contract 12).

A widget's `render` builds keyed elements, Taffy lays out the realized rows, and elements emit quads, glyph runs, icons, paths and viewport surfaces. These batch into instanced wgpu draws without compute, identical on WebGPU and WebGL2, and frames render only on input, state change, animation or refinement. Other paths tessellate on the CPU, since Vello's original renderer needs compute [Vello]. Vello Hybrid, "roughly beta quality" in April 2026, is re-evaluated at the phase 2 gate [Linebender 2026 Q1].

### Text and accessibility

- **Shaping.** Parley shapes with HarfRust, a Rust port of HarfBuzz that "for the most part passes the HarfBuzz test and fuzzing suites" [HarfRust]. ICU4X resolves bidirectional text.
- **Fonts.** Inter sets interface text, JetBrains Mono code and Source Serif 4 presentation text. Noto covers "more than 1,000 languages and over 150 writing systems" [Noto], and system fonts are only a logged last fallback.
- **Rasterization.** Skrifa loads, scales and hints outlines into an alpha atlas at four subpixel offsets [Skrifa]. Editors handle bidirectional carets, grapheme deletion, IME composition and platform shortcuts.

**Decision D-UIX-4:** Grayscale antialiasing with bundled fonts everywhere, hinted by Skrifa below UI scale 1.5 and unhinted above, with the same code on every OS.
*Why:* identical layout and bitmaps for snapshot oracles, correct rendering over translucent surfaces, and crisp 11 and 12 px text on 1080p displays.
*Rejected:* each OS's text stack, whose metrics differ; LCD subpixel antialiasing, which fails over transparency; unhinted text everywhere, which looks soft beside native applications.

AccessKit adapters provide UI Automation, NSAccessibility and AT-SPI, plus Android for tablets; iPadOS runs the web build. Its web adapter is planned, not released [AccessKit], so Crucible builds it upstream: a hidden DOM mirror with ARIA roles, names, states and bounds, as Flutter web does [Flutter web accessibility]. Virtualization bounds the mirror to about 2,000 realized nodes at under 1 ms per frame (target), and collections expose `aria-setsize` and `aria-posinset`.

**Decision D-UIX-5:** Crucible implements the AccessKit web adapter as a DOM mirror and enables it by default on the web.
*Why:* WCAG 2.2 AA on a Tier 1 platform, with no hidden opt-in step.
*Rejected:* a DOM-based web UI, which breaks the single toolkit; Flutter-style opt-in, where users must first find a hidden control.

Browsers use the EditContext API where available, so a custom-rendered editor receives IME composition and reports caret bounds [MDN EditContext]. EditContext is not Baseline; elsewhere a hidden `<textarea>` proxy sits at the caret, and both paths feed one input stream. The toolkit's platform needs are PLT's services, and PLT's dependency register tracks Taffy, Parley, HarfRust, Skrifa, AccessKit, winit and wgpu, each with a fork plan.

## Renderer

A viewer is only as good as its frame rate and its fidelity to the geometry. One renderer crate, `apps/renderer` on wgpu 30 [wgpu 30 release], draws the viewport, Field views, toolpaths, 2D canvases, overlays and every presentation output on the toolkit's wgpu device.

### GPU capability tiers

wgpu 30 exposes 64-bit atomic min and max (`SHADER_INT64_ATOMIC_MIN_MAX`, `TEXTURE_INT64_ATOMIC`) and indirect-count draws on native backends only [wgpu Features]. The WebGPU Candidate Recommendation Draft of 15 September 2026 has no multi-draw indirect, bindless resources or mesh shaders [W3C WebGPU], and WebGL2 has no compute.

| Tier | Where | Required capabilities | Capacity at 60 fps (contract 13.3 targets, by phase) |
| --- | --- | --- | --- |
| G1 Full | Native Vulkan 1.3, DX12 Shader Model 6.6, Metal 3.1 | Compute, storage buffers, indirect draws | 5M visible triangles (1); 100,000 Instances (2); 1,000,000 Instances on the high band (4) |
| G2 Compute | WebGPU with `core-features-and-limits`; native adapters below G1 | Compute, storage buffers, single indirect draws | 2M visible triangles, or 30 fps at 5M (1); 20,000 Instances (2) |
| G3 Raster | WebGL2, GLES 3.0, WebGPU compatibility mode | Instanced draws, float render targets | 30 fps at 2M visible triangles (1); 10,000 Instances of at most 1,000 distinct Parts (2) |

Compute rasterization is a reported G1 capability, `compute_raster`, present when the adapter exposes wgpu's 64-bit atomic features. M1-series Macs lack it (Platform notes), and a G1 adapter without it declares a measured capacity in the graphics popover. In phase 1, the forward renderer's Instance capacity per tier is a measured target that blocks nothing.

**Decision D-UIX-6:** Every feature works on every tier; tiers differ only in declared capacity and refinement speed, which the graphics popover names.
*Why:* the contract's identical-features rule, stated honestly, since hardware cannot deliver identical scale.
*Rejected:* hiding features on weaker tiers, which breaks parity; one lowest-common-denominator renderer, which wastes native hardware by an order of magnitude.

Every GPU path has a CPU path, and servers render through software Vulkan (Mesa lavapipe) or WARP. PLT's safe mode gets the G3 path, and after device loss the renderer rebuilds from cached packages, typically within one second. Render shaders never affect results, so they need none of the known-answer tests that PLT runs on compute pipelines.

### Display data

Anvil owns tessellation (`anvil::tessellate`) and, from phase 2, the cluster hierarchy (`anvil::cluster_dag`); the renderer never tessellates B-rep.

```rust
/// Produced by Anvil and cached in CAS. Identity: (GeometryId, chordal_error, encoding version); content is fixed.
pub struct DisplayPackage {
    pub geometry: GeometryId,            // name-free: shared by every design with equal geometry
    pub chordal_error: Length,           // max distance from display triangles to the Body, edge tolerance included
    pub bounds: Aabb,
    pub edges: Vec<DisplayEdge>,         // polyline per model edge, with canonical edge number and continuity
    pub pages: Vec<ObjectId>,            // cluster pages, 64 KiB each; triangles carry canonical face numbers
    pub root_pages: Vec<u32>,            // always resident
}
```

- **Fixed content.** A package never changes once written. Streaming status travels in KLN's `ResultEvent` for the node that demanded the package, and a coarser package is another object with its own `chordal_error`.
- **Names join late.** Packages carry canonical entity numbers only. The renderer maps them to `EntityId`s through the Body's face table, keyed by the Body's `ObjectId`, so two designs with equal geometry share pages and each pick returns its own design's `EntityId`s.
- **Watertight.** Anvil tessellates each edge once and shares its vertices with both faces, so healed imports stay watertight.
- **Clusters** hold up to 128 triangles, and level-0 clusters never cross a face, so picking and updates work per face. Pages use meshoptimizer's codecs [meshoptimizer]; meshoptimizer is C++, so it enters through PLT's native-code register with a wasm32 build for the browser renderer, and its codecs never affect results.
- **Updates.** An edit re-tessellates only changed faces, and refinement continues until chordal error projects under 0.5 px (target).

On desktops, the engine process hands tessellations and Field samples to the UI process through PLT's `SharedRing`. The reader copies each published slot before validating its sequence number, so the renderer uploads from owned memory.

**Decision D-UIX-7:** Each Body's display data is a clustered `DisplayPackage` cached in CAS, and culling, level of detail and selection run locally.
*Why:* interaction never waits for the engine, unchanged Bodies cost nothing after an edit, and one format serves desktop, browser, review, web views and CI.
*Rejected:* one mesh per Body, with no level of detail and a full re-upload per edit; server-side video streaming, with latency, bandwidth cost and no offline use.

The scene is a flat table of draw Instances mirroring the Assembly tree. Each has an `f64` transform, visibility, style and selection flags, and identical Parts share one package. On the GPU each translation is a high and low `f32` pair, and shaders subtract the eye position in the same split form.

**Decision D-UIX-8:** Every tier uses reversed-Z float depth, an infinite far plane and relative-to-eye split-precision transforms; the near plane sits at 0.1 times the distance to the nearest visible bound, down to 1 µm.
*Why:* scenes span micrometre details and hundred-metre extents, and reversed-Z float depth gave "a *zero error rate*" in Reed's test [Reed depth precision].
*Rejected:* logarithmic depth, which disables the early depth test; per-frame CPU rebasing, costly at a million Instances.

### Two pipelines

**Decision D-UIX-24:** Phase 1 ships one forward renderer on every tier, with id targets for picking, model edges, per-Part discrete level of detail over level-0 clusters, weighted blended transparency and section caps.
*Why:* both phase 1 golden products are single Parts, and the open cluster-hierarchy implementation on wgpu was unfinished in March 2025 [Stevens 2025].
*Rejected:* the visibility-buffer pipeline in phases 0 and 1, a long chain that GP1 and GP2 do not need.

[[DIAGRAM diagrams/10-ui-frame-graph.jsx: renderer frame graph · two pipelines, both feeding picking]]

Read each column top to bottom as one frame; rows pair stages with the same role, and dashed arrows mark ids that picking reads.

From phase 2, G1 and G2 cull on the GPU against the frustum and last frame's depth pyramid. A cluster draws when its error projects under τ (1 px) and its parent's does not, so the cut is crack-free, as in Nanite [Karis 2021], with on-screen error under 1.5 px (target). Clusters raster into a visibility buffer: packed depth and id through 64-bit atomics where G1 reports `compute_raster`, and `R32Uint` with hardware depth elsewhere [Burns 2013]. A second pass draws newly visible clusters, and a resolve pass shades from triangle ids.

On G2, culling compacts surviving triangle indices into one index buffer for one `drawIndexedIndirect`, reusing vertices and issuing no degenerate triangles. Per-cluster `drawIndirect` with padding is the fallback where that buffer would exceed the binding limit. Where G1 reports `compute_raster`, clusters of sub-two-pixel triangles rasterize in compute, as Bevy's virtual geometry does on wgpu.

**Decision D-UIX-9:** From phase 2, G1 and G2 draw through a cluster hierarchy, two-pass GPU occlusion and a visibility buffer; compute rasterization needs `compute_raster`, and mesh shaders wait for phase 4.
*Why:* this maps Nanite, GPU-driven culling [Haar 2015], niagara and Bevy onto WebGPU core, while mesh shaders would add a G1-only path.
*Rejected:* G2 compute rasterization before stable Chrome, Firefox and Safari ship 64-bit atomic min and max; per-object draws everywhere, CPU-bound beyond about 10,000 Instances.

### Large assemblies and picking

- **Instancing.** A fastener used 40,000 times stores one package and 40,000 transforms of 64 bytes. A binned-SAH bounding volume hierarchy over Instances is rebuilt when the Assembly changes and refit when Instances move; the path tracer reuses it.
- **Streaming (phase 2).** Clusters request pages each frame into a fixed pool with least-recently-used eviction. Native G1 pools default to 1 GiB, at most half of VRAM, and browsers follow PLT's memory table.
- **Coarse first (phase 2).** Root pages load first, meeting contract 13.3's 1,000-part row. Sub-pixel Instances draw as points, and lightweight mode measures with "≈" until Anvil returns exact values.

A click reads the id target (phase 1) or the visibility buffer (phase 2) within contract 13.3's selection row. The triangle's canonical face number maps to the design's `EntityId` through the face table. A hit from a coarse cluster or within a pixel of an edge is confirmed by a CPU ray cast in under 2 ms (target).

G3 picks by CPU ray cast, avoiding WebGL2 readback stalls. Edges and vertices use a pick buffer widened to 4 px for mouse and 12 px for touch. Clicking again cycles stacked entities, and box selection follows CAD's enclosed and crossing convention.

Every selection becomes a `Query` before an edit or a comment uses it. `inspect.suggest_query` returns ranked candidates such as `base.face(role: end_cap)`, each with a robustness rating. Fragile ones carry the lint `ing/l-fragile-selector` and a "Name this selection" fix.

**Decision D-UIX-10:** Picking reads an id target or the visibility buffer and confirms ambiguous hits on level-0 geometry; edits take selections only as ranked `Query` suggestions.
*Why:* a fast pick that is never wrong about identity, and selections that survive rebuilds.
*Rejected:* CPU-only ray casting, slow at assembly scale; raw `EntityId`s in source, which nobody can read.

### Edges, transparency and sections

Model edges come from the package, drawn as screen-space quads 1.25 px wide with analytic antialiasing; tangent joins draw thinner. Silhouettes of curved faces come from id, depth and normal discontinuities, and hidden lines dash in screen space so dashes never crawl. Drawings and vector illustrations use Anvil's exact silhouette curves instead, following Bénard and Hertzmann's survey of the trade-offs [Bénard 2019].

**Decision D-UIX-11:** Phase 1 uses weighted blended transparency; from phase 2, G1 and G2 resolve the nearest k layers exactly in a k-buffer of packed keys.
*Why:* X-ray views of nested housings need exact front layers, and depth-only keys flicker on coincident mating faces.
*Rejected:* depth peeling, a geometry pass per layer; linked lists, with unbounded memory; a fixed k, which exceeds WebGPU's default 128 MiB binding above about 3.3 MP.

Each 32-bit key holds 24 bits of quantized reversed-Z depth and 8 bits hashing Instance and face. The resolve breaks remaining ties by Instance index and canonical face number, and k follows the adapter's `maxStorageBufferBindingSize` and the render resolution each frame. Display opacities clamp to 0.2 to 0.9, where weighted blending is tuned [McGuire 2014], and the graphics popover counts pixels whose layers exceeded k.

Sections take up to six planes or one box, each optionally locked to a face by `Query`. Caps draw where the nearest surface behind the plane is a back face of a closed Body; they are hatched per Material class and show the active Field in Simulate. When the view settles, Anvil's exact section takes over from the caps and supplies area, centroid and second moments.

### Styles, light and colour

Engineering styles use a headlight with hemisphere ambient, so shading never hides geometry. The Illustration style adds the four-tone shading of the Presentation studio section.

- **Appearance.** OpenPBR Surface 1.1.1 in a reduced real-time form with documented deviation, checked against MaterialX references [ASWF OpenPBR]. A `Neutral` appearance drops imported textures and is the default for agent renders.
- **Ambient occlusion.** Ground-truth AO (Jimenez and others, 2016), ported from XeGTAO, runs at half resolution in motion. XeGTAO reports about 2.39 ms at 1080p on an Intel i7-1195G7 integrated GPU [XeGTAO].
- **Colour.** Rendering is linear Rec.709 in 16-bit float targets, output as sRGB, Display P3, or extended range for Realistic views on HDR displays. Khronos PBR Neutral tone-maps only the Realistic style [Khronos PBR Neutral], and lighting scales Field colours only within [0.8, 1.0].

In motion, edges and overlays use analytic antialiasing and surfaces a one-frame morphological filter on id and depth. When the camera stops, the renderer accumulates 16 jittered frames over about 270 ms at 60 Hz, then stops.

**Decision D-UIX-12:** No temporal anti-aliasing during interaction; progressive supersampling when the view is still.
*Why:* engineers judge edges and small features during orbit, and temporal reprojection smears thin lines.
*Rejected:* TAA, with ghosting and history-dependent images; MSAA on the visibility buffer, at four times the memory.

**Decision D-UIX-25:** In motion the 3D view renders at most 2.1 MP and upsamples; edges, overlays, text and still frames stay at native resolution.
*Why:* pixel-proportional stages cost about 2.8 times more on a 5.9 MP panel, so 60 fps would fail before geometry is counted.
*Rejected:* native resolution in motion, which misses 60 fps on mid-band laptops; downscaled edges and text, which blur what people judge.

BRep and Mesh Bodies draw from clusters; SubD Bodies show Anvil's limit surface, with the control cage while editing. Implicit Bodies draw from Anvil meshes at display tolerance; on G1 and G2 they evaluate directly per screen tile instead, with interval pruning, following Keeter's massively parallel method [Keeter 2020]. During edits this runs Anvil's WGSL tape interpreter, which takes tapes as data, so no pipeline compiles inside a drag; a specialized shader compiles only for still views.

## Field views

Simulation results are only useful if people read them correctly, so Fields are painted on the true geometry with their status and error, never exported to a separate post-processor. A `FieldView` in a `ViewState` names a study result and how to show it.

```rust
pub struct FieldView {
    pub source: CallSite,                // the study call whose result is shown
    pub output: Symbol,                  // which result Field, such as von_mises
    pub quantity: DerivedQuantity,       // magnitude, x, y, z, von Mises, principal 1..3, ...
    pub spec: VisualizationSpec,
}

pub enum VisualizationSpec {
    Color { map: Colormap, range: Range, bands: Option<u8>, isolines: Option<u8> },
    Vectors { density_px: f32, scale: VectorScale },
    Streamlines { seeds: SeedRake, max_length: Length, tolerance: f32 },
    Isosurfaces { values: Vec<f64>, opacity: f32 },
    Deformation { exaggeration: Exaggeration, show_undeformed: bool },
    Volume { map: Colormap, opacity_ramp: Ramp },
    Emission { model: EmissionModel },   // black-body glow, flow streaks, discharge (Presentation studio)
    Discretization { show: DiscretizationLayers }, // octree cells, cut and aggregated cells, degree, reduced regions
    Chart { kind: ChartKind },           // line probe, waveform, Bode, Smith, eye
}
```

**Decision D-UIX-13:** Field colours come from Flux's per-pixel WGSL evaluators on the UI device, in phase 1 for H¹ Lagrange elements up to p = 4 on the immersed octree.
*Why:* linear interpolation of high-order solutions misplaces peaks, and the UI's device avoids a host round trip [Nelson 2012].
*Rejected:* fixed per-vertex sampling everywhere, a silent error near stress concentrations; a separate post-processor.

Other discretizations, until Flux ships their evaluators, and tiers without compute use refined vertex samples, with interpolation error under 1% of the colour range (target). Probes always use Flux's exact sampler, and display data never feed checks ([FLX, Display](03-flux.md#display)). During a geometric drag, physics results show as `Proxy`; from phase 3 Flux's reduced models answer parametric drags.

Rainbow maps distort data and fail readers with colour-vision deficiency [Crameri 2020]. Crucible ships the Scientific colour maps (v8.0.1): batlow for sequential data, vik for diverging data and a cyclic map for phase [Crameri colour maps]. Paul Tol's palette serves categories [Tol palettes], and a value-suppressing palette shows uncertainty [Correll 2018].

**Decision D-UIX-14:** Rainbow and jet colormaps are not offered, not even as an option; imported legacy presets map to batlow with a one-time notice.
*Why:* the evidence of distortion and accessibility harm, and defaults decide most users' choices.
*Rejected:* offering jet "for familiarity", since familiarity is why the harm persists.

## Simulation, manufacturing, drawings and electronics

Each engineering domain has views its specialists expect, and each must stay the same program seen through a domain's eyes. This section names what the Simulate, Manufacture and Electronics presets and the drawing editor add.

### Studies and results

A study is Ingot source with Flux's semantics, built by selection: a template, then faces or Bodies with a condition. Conditions are fixed, force, pressure, preload, temperature and convection, plus Flux's analyst idealizations ([FLX, Contact, constraints and fracture](03-flux.md#contact-constraints-and-fracture)). Phase 1 offers rigid and distributing remote points, point masses with rotary inertia, and grounded and two-point springs; phase 2 adds bushings and fastener and spot-weld connectors. Each becomes a statement with a `Query` and typed quantities, such as `pressure(web.face(role: end_cap), 2.5MPa)`, drawn as scaled glyphs. Flux's pre-flight flags unassigned Materials, unconfirmed contacts, rigid-body modes, unit errors and envelope warnings, each with a fix.

`Interactive` studies re-run after edits within contract 13.3's row, and `SignOff` Evaluations queue locally or on workers with position, time and cost. The results panel lists each check's verdict, value, limit, margin and bound. For the canonical bracket it reads, for example, "`static_margin`: `Pass` at `SignOff`, 94 MPa ± 1.5 MPa (`Estimated`) against 144 MPa", with the excluded neighbourhoods named. A region that meets a singular set gives `Undecided { SingularPoint }` with the fix "exclude a stated distance". A bound wider than the margin offers refinement or `SignOff`, and two Evaluations compare as a difference Field.

From phase 2, a submodel template takes a global Field and a region and builds Flux's local re-solve, with the transfer error in the budget. Goal-oriented adaptivity makes routine submodeling unnecessary, so the template serves the cases where it remains the workflow: a shell-modelled frame with a solid weld detail, or a supplier's loads on a local part.

A study published as a `#[feature]` is a simulation app. Its generated dialog exposes only the inputs the author chose, with typed ranges, and its checks run on every use, so a non-specialist gets an answer that is versioned and checked. For example, a sales engineer's `bracket_sizer(load, span)` feature wraps `static_stress` on the bracket, locks Material and supports, and returns the smallest catalog thickness whose `static_margin` passes.

### Manufacturing

CAM, posts, stock simulation and slicing arrive in phase 2 (contract 13.2), so phase 1's Manufacture preset shows MFG's DfAM check Fields, the 3MF build layout and the cost panel.

- **Cost panel (phase 1).** Unit cost at chosen quantities by Part, process and source, each line with assumptions and range. Edits show deltas with their cause ("fillet radius 2 → 3 mm: machining −$0.42"), and quantity curves show process crossovers. Quotes take the place of estimates with their date, and cost targets are checks.
- **Toolpath playback and editing (phase 2).** Polylines are dashed by move type and coloured by type or feed. Tool, holder, machine and stock come from MFG, with stock labelled "display" between key frames, and collisions are marked where and when they occur. Selecting passes, a boundary or a plane in playback writes one of MFG's toolpath edits (trim, delete passes, reverse, reorder, relink, change tool) as source after the strategy call ([MFG, Milling, drilling and probing strategies](07-manufacturing.md#milling-drilling-and-probing-strategies)). Edits address MFG's stable pass keys, so they survive regeneration.
- **NC code panel (phase 2).** Posted NC text links both ways through MFG's `BlockMap` to toolpath points, workingsteps and design features. Each finishing workingstep shows its cutter compensation mode and declared wear range, and G41 and G42 blocks show their D register.
- **Setup sheet and additive (phase 2).** MFG's `setup_sheet` previews and diffs like any drawing, and a layer slider shows per-layer paths from Crucible's slicer.
- **EBOM and MBOM (phase 2).** A side-by-side tree shows the engineering BOM beside the manufacturing BOM. Dragging lines into stations, kits and phantoms writes MFG's MBOM rule source through edit plans, and KLN's reconciliation check shows its state per line.

### Drawings

MEC owns drawing standards, `auto_drawing` and `revision_markers`; UIX owns the editors. PMI (product and manufacturing information) shows on annotation planes, filtered by saved view. A drawing is an Ingot file of sheets, views and annotations, where each view is a `ViewState` and each dimension references entities by `Query`.

- **Sheet editor.** A 2D canvas shows Anvil's exact hidden-line views; placing views and dimensions writes Ingot edits. From phase 2 a sheet may hold 2D-only geometry, and an imported DWG or DXF opens as an editable drawing program through ECO's import.
- **Driving dimensions.** Editing a driving dimension on a sheet writes model source through the same `EditPlan` as a drag. A dimension that traces to exactly one literal writes it, and otherwise the editor offers ranked plans. Driven and reference dimensions stay read-only.
- **Automatic drawings.** The editor calls MEC's `auto_drawing` and shows the result as an `EditPlan` preview; agents refine it afterwards in a separate Proposal.
- **Revision markers.** The editor previews MEC's markers and revision rows before the release plan is prepared.
- **Dangling references** show in the danger style with their `ResolveError` and fixes, never re-attached silently.

### Electronics

**Decision D-UIX-27:** Schematic and layout editors draw through the public `crucible:ui/canvas2d` world of retained 2D primitive buffers with layer, net and entity ids, which the renderer draws and hit-tests. *Why:* element trees cannot draw a layered board with a live router head within 2 ms, and principle 1 needs an open mechanism.
*Rejected:* electronics as element-tree panels, too slow; a privileged built-in board view; package shaders.

Buffers hold lines, arcs, polygons and text, and placement drag runs live rule checks the same way. The drag lane is the drag path of the Steering section: `edit.stream` updates at the `Drag` priority class. The schematic, layout and constraint-manager canvases show ELX's contents within ELX's targets, such as 16 ms per mouse move with 50 shoved items.

The renderer offers net highlight, high-contrast and dimmed-layer modes over any buffer. A schematic label is connectivity, so editing it renames the net in source. A drawn group spanning two nets draws in the danger style, from ELX's `schematic_matches_network`. Selection is one set of `EntityId`s, so schematic, layout, 3D board and enclosure cross-probe with no extra work.

## Collaboration

People and agents work on one branch at once, and the interface must show who is doing what without becoming a monitoring tool.

Live sessions, presence and follow mode arrive in phase 2 (contract 13.2). The UI draws KLN's presence as avatars, labelled 3D pointers, remote selections and drag ghosts, interpolated over 100 ms. Clicking an avatar follows that person or agent.

**Decision D-UIX-19:** Presence uses six colours per theme, each paired with initials and a name, and every pair stays 0.10 apart in Oklab under simulated colour-vision deficiency.
*Why:* WCAG 1.4.1, and a search at two lightness levels finds six colours at least 0.108 apart in both themes, while eight reach only 0.075 in the dark theme.
*Rejected:* hashed hues, which collide; eight colours, with about a third less separation.

**Decision D-UIX-30:** Presence, follow mode and recording of viewed review tabs are organization settings, and a works-council mode disables every per-person activity record and analytic.
*Why:* German works councils co-determine "the introduction and use of technical devices designed to monitor the behaviour or performance of the employees" [BetrVG §87], which would otherwise block deployment.
*Rejected:* always-on activity records; per-deployment configuration files.

- **Concurrent edits.** Live edits go through KLN's server-sequenced edit log ([KLN, Live sessions](05-kiln-repo-plm.md#live-sessions)). The client applies its patch at once, the relay orders it, and the client rebases pending patches with the merge that branches use. A pair of edits therefore merges the same way live or on branches. Literal edits are last-writer-wins in sequence order, the earlier author can restore their value in one click, and advisory locks show holder and expiry.
- **Offline.** The workspace keeps working against the local replica and says "Offline: changes saved locally". On reconnection, pending patches fast-forward or rebase when nothing conflicts and the disconnection lasted at most 60 s; otherwise they rejoin as a branch with a merge offer (contract 7.1).
- **Notifications** cover mentions, review requests, Act requests, failed checks on watched branches, agent questions and releases. Only blocking agent questions and failed release checks interrupt, and delivery follows the label rule of the last section.

## Input, accessibility and localization

An engineer reaches the interface through a mouse, trackpad, keyboard, pen, touch, 3D mouse, screen reader or headset, in their own language and units, and every path must reach every capability.

### Pointer, keyboard and devices

Zoom goes toward the cursor, and orbit pivots on the surface point under it. Trackpads pan with two fingers, pinch to zoom and orbit with Shift. A view cube offers named views, F fits the selection and Shift+F fits all; double click selects the feature that made an entity.

Keymaps are TOML files layered over a navigation preset, and the presets imitate nine products (Reference). Single-key shortcuts act only with the viewport or tree focused (WCAG 2.1.4), and shortcuts bind to logical keys by default.

**Decision D-UIX-20:** Navigation and key presets imitate the nine products in the Reference table, and each ships only when its reference table cites the vendor's published defaults.
*Why:* navigation muscle memory is the main switching cost, and only a cited table can be checked without daily users.
*Rejected:* full UI skins of other products, a trade-dress risk; bindings from memory; no presets.

Palette synonym sets cover each product and CAM vocabulary, while command names, the palette and menus stay Crucible's own. Preset names take the descriptive "-like" form, which retained counsel reviews before release.

**Decision D-UIX-31:** Crucible reads 3D mice as HID devices through PLT's `NavDeviceEvent` on every desktop OS and through WebHID in Chromium [MDN WebHID]; vendor drivers are optional.
*Why:* no vendor SDK licence sits on a critical path, and one decoder serves every platform.
*Rejected:* the vendor SDK as the only path, which makes its licence a dependency; `spacenavd`, a GPL-3.0 daemon, as the Linux path [spacenavd].

Retained counsel checks each vendor's device terms before its devices are listed. Other browsers offer the desktop app.

- **Pen and touch.** Pressure and tilt reach sketch tools and markup, and pen hover shows inference. Desktop pens on macOS and X11 depend on PLT's winit patches. Touch layouts give 44 px targets, a 12 px pick radius, a 140 px gizmo and a radial tool menu, and every drag has a tap-then-type path (WCAG 2.5.7).
- **XR review (phase 3).** Multiview stereo at 90 Hz per eye on G1, true and tabletop scale, ray selection, hand-placed sections, comments and verdicts. Shared sessions follow in phase 4 and passthrough overlay in phase 5.

**Decision D-UIX-33:** XR review runs on OpenXR runtimes natively and on WebXR in browsers, which reaches visionOS: Safari 18.0 for visionOS 2 "adds support for `immersive-vr` sessions with WebXR" [WebKit Safari 18].
*Why:* the web build covers Apple's headset without another native shell.
*Rejected:* a native visionOS shell before the founder approves it as a Tier 2 target; no visionOS path.

### Accessibility

The interface targets WCAG 2.2 level AA on every Tier 1 platform, including the browser, and the same criteria on Tier 2 tablets [W3C WCAG 2.2]. The Reference section maps each criterion to Crucible's approach. Each Tier 1 target publishes an Accessibility Conformance Report built on the accessibility oracles and an external audit, which contract 9 requires before a preview target becomes generally available.

With the viewport focused, Ctrl+Arrow (Cmd on macOS) orbits in 15° steps, Shift+Arrow pans, Plus and Minus zoom, and 1 to 7 pick named views. Arrows move selection to adjacent entities, Alt+Up and Alt+Down climb and descend ownership, and Ctrl+K takes a typed `Query`. Tab cycles a tool's handles, arrows nudge them, and sketch points take absolute `[40mm, 20mm]` or relative `<15mm, 0>` input. Markup has a keyboard path too: a selection plus a typed comment anchors like a stroke.

Tree rows describe type, status and authorship ("Feature rib, 3 of 7, modified by Ana, check failed: margin −4%"). The viewport's accessible children mirror the selection and its neighbours, described from Anvil measures ("planar face, 40 by 60 mm, normal +Z"). "Describe view" speaks Parts, section, Field summary and check states, and the probe's keyboard mode walks a grid. Every presentation figure carries alternative text generated from its scene: what is shown, the callouts and the readouts.

**Decision D-UIX-21:** The 3D viewport is screen-reader operable through a structural model (selection, adjacency, owning feature and Instance) rather than through pixels.
*Why:* CAD geometry has meaning in topology and features, which can be spoken and navigated.
*Rejected:* marking the viewport decorative, which excludes blind engineers and reviewers.

Reduced motion follows the OS: camera moves cut, panels cross-fade within 100 ms, and animations show their still frame. High-contrast themes raise text to 7:1 and non-text to 4.5:1, Windows forced colours map tokens to system colours, and "Simulate colour vision" applies Machado's matrices [Machado 2009].

### Localization and units

- **Messages** use Project Fluent through `fluent-rs` for CLDR plurals, gender and case [Project Fluent], and ICU4X formats numbers, dates and lists. Every string in `apps/` has a message id, and expanded and right-to-left pseudo-locales run the snapshot and layout suites on every merge.
- **Right to left.** Layout uses logical start and end, and from phase 2 panels, indentation and directional icons mirror. The viewport, view cube, axes and gizmo keep their geometry, Ingot stays left to right, and quantities are isolated from the surrounding direction.
- **Display units** are per quantity kind with SI-mm, SI-m, US-inch and US-feet-inch presets and never change the model. A typed value enters source as typed (`1.5in`), and a repository's preferred units make mixed units a lint with a convert fix.
- **Formatting** follows the locale (4,5 mm in German), while Ingot always uses the period. Toleranced values show enough digits for the tolerance, dual units are optional, and extreme values use SI prefixes or exponents. A presentation's `RenderProfile` fixes its locale and units, so a report renders the same way for every reader.

## Design system and onboarding

A calm, consistent visual language lets people read evidence quickly and makes every output look like one product. It uses neutral surfaces, one accent, colour reserved for meaning, and numbers set for reading. Every value is a token in `apps/ui-toolkit/tokens`, and a theme is a token file. Type roles, sizes and density steps are tabulated in the Reference.

Inter supplies tabular figures and a slashed zero [Inter], JetBrains Mono has a no-ligature variant [JetBrains Mono], Noto Sans Arabic UI sets Arabic interface text, and Source Serif 4 sets presentation text. All ship under the SIL Open Font License 1.1 with their notices (contract 7.7). There are no all-caps labels and no italics for meaning.

Colours are authored in Oklch (CSS Color 4) [Ottosson Oklab]. Tokens cover surfaces, text and borders, an `accent` for selection and focus, meanings (`status.*`, `diff.base`, `diff.target`) and the presentation canvas (`paper`, `ink`, `lit`). Text reaches 4.5:1 against `surface.panel`, controls and status colours 3:1, and the diff pair 3:1 against `viewport.background`.

Presence colours are six slots per theme at two Oklab lightness levels, each at least 3:1 against `surface.panel` with chroma at least 0.08. The presence decision sets their separation under Machado's three matrices at severity 1.0, applied in linear sRGB. Unassigned Parts shade neutral grey.

Docked panels separate by 1 px borders, and only floating surfaces cast shadows. Icons sit on a 16 px grid with 1.5 px strokes and carry a text name. Motion only explains a change of state or place: 100 ms hover feedback, 150 ms popovers and 350 ms camera moves. Selection is instant, and progress of unknown length is a 1.5 s shimmer, static under reduced motion.

Built-in themes are Light, Dark and two high-contrast variants, following the OS. A custom theme below the contrast oracle still loads, labelled "below WCAG AA contrast", unless the organization forbids it.

- **First run** asks four skippable questions: role (review, design, simulation, manufacturing, electronics), keymap preset, unit system and theme. It opens a template, never an empty screen.
- **Templates** are design repositories published as packages, mirroring the golden products, each with a presentation.
- **Tutorials** are packages of steps, each with instructions, an optional pointer by command id (never by pixel), and a completion predicate evaluated through `api`. GUI, code and agent paths therefore all count, and each tutorial's scripted solution runs in CI on every release.
- **Migration.** Synonym sets make "Boss-Extrude" or "Press Pull" find `extrude`. Proprietary formats enter through ECO's translators as External inputs (contract 7.7), with ECO's `TranslationReport` beside the model. Reconstruction of imported solids arrives as a reviewed Proposal, and a concept guide maps familiar terms.

## Performance, privacy and extension

The interface must stay fast, must never leak what a label protects, and must let any package extend it the way Crucible's own views do.

Contract 13.3 owns the shared performance rows, and PLT owns browser startup and memory. UIX adds its own targets: 8.3 ms interface-only frames, palette results in 30 ms over 100,000 items, and 8 ms keystroke-to-paint on 50,000 lines. Arrived results display within 50 ms, and no UI-thread stall exceeds 50 ms.

**Decision D-UIX-28:** Above `internal` or with any `controls`, nothing the UI sends outside the organization carries content, and copies stay out of clipboard history and cloud clipboards where the OS allows.
*Why:* labels stop at `api` unless egress channels consult them, and ITAR's end-to-end condition fails once a third party holds plaintext.
*Rejected:* content-rich notifications for every label; per-feature opt-outs instead of one auditable rule.

Notifications, emails and push payloads carry ids and generic text, never rendered images or names. Crash reports upload only signature and module list, bundles go only to the organization's own server, and a policy can forbid copying. PLT keeps the CAS, journal and caches out of cloud-synced folders and OS backup. Web views and presentations leave only through the exits their decisions name.

**Decision D-UIX-22:** UIX's telemetry uses PLT's one opt-in pipeline and schema from phase 2, and the signed policy `telemetry.performance = off` with an egress allowlist turns it off.
*Why:* engineering data is confidential, and two pipelines with different payloads and retention cannot both be honest.
*Rejected:* opt-out telemetry; a separate UI pipeline; compile-time exclusion, which contradicts PLT's single binary.

UIX contributes frame-time histograms per tier, interaction latencies, command counts, typed failure codes and settings. It never sends source, geometry, names, paths, values or prompts, and an inspector shows each payload first. Minidumps can hold design data in thread stacks, so uploads and reproduction bundles ask first and show their content. After a crash the workspace restores the last `ViewState`, panels and comment drafts, and every finished gesture is already a Change.

Test suites cover rendering correctness, visual regression, interaction, accessibility, presentation, performance and usability, each with an oracle. Input to photon runs on PLT's camera rig at each gate.

**Decision D-UIX-32:** UIX meets its target at each gate with 90% success on the phase's core tasks, measured by an outside usability lab.
*Why:* task success shows whether professionals can do the work, while scores from people with strong habits in other tools measure familiarity.
*Rejected:* a System Usability Scale of 75 as a criterion, which penalizes unfamiliarity; no usability target, since oracles cannot show that work is learnable.

Core tasks are the steps of the phase's golden products, led by review and presentation, and System Usability Scale scores are only tracked.

### Extending the interface

Principle 1 applies to the interface: domain views from other tabs use the extension points open to any package. Dialogs and handles come from `Feature` metadata, commands are registry entries, visualizations are `VisualizationSpec`s, and themes, keymaps, templates, presentations and tutorials are data. Code-driven views are Wasm components in the `crucible:ui` WIT (WebAssembly Interface Types) package (Reference).

- **Sandbox.** Panel and canvas Wasm components get no files, network or clock and reach data only through `api`. `crucible:api/edit` needs the user's grant per package, and third-party ones run in PLT's sandboxed worker process (contract 7.4).
- **Budget.** Panel logic gets 2 ms of CPU per frame, and three over-budget frames pause it with a notice.
- **Chrome.** Every panel shows its package identity and may not use modal or system-styled elements, so it cannot imitate Crucible's dialogs. Panel edits record the package in the Change's provenance.
- **Host services.** The toolkit supplies accessibility, theming, localization and keyboard access, and selection is one shared set of `EntityId`s.

**Decision D-UIX-23:** Built-in and package views extend the interface only through declarative data, Wasm component panels and Wasm component canvases, never through shaders or the GPU.
*Why:* no privileged code, plus accessibility, theming, localization and parity for every panel, with canvases for dense 2D editors.
*Rejected:* native shared libraries, unsafe, per-OS and impossible on the web; webview panels, a second runtime; custom shaders, with their portability and review cost.

### The `crucible:ui` WIT package

WIT types cannot be recursive, so a UI tree is a flat list of nodes in pre-order, each naming its parent by index.

```wit
package crucible:ui@0.1.0;

interface types {
    type layer-id = u32;
    enum node-kind { column, row, stack, text, button, field, item-list, data-table, chart, viewport-ref, canvas-ref }
    variant prop-value { text(string), number(f64), flag(bool), entity(u64), command(string) }
    record prop { name: string, value: prop-value }
    /// One element of a UI tree; `parent` indexes an earlier node, and the root has none.
    record node { kind: node-kind, key: u64, parent: option<u32>, props: list<prop> }
    record ui-event { node: u32, kind: string, args: list<prop> }
    record command-call { command: string, args: list<prop> }
    enum primitive-kind { line, arc, polygon, label }
    record primitive { kind: primitive-kind, points: list<tuple<f64, f64>>, net: option<u64>, entity: option<u64>, text: option<string> }
    record primitive-batch { primitives: list<primitive> }
    record hit { layer: layer-id, index: u32, entity: option<u64>, net: option<u64> }
}

interface view {
    use types.{node, ui-event, command-call};
    render: func() -> list<node>;                           // a tree from data read through api
    handle: func(event: ui-event) -> list<command-call>;    // calls go through the registry and api
}

interface canvas-host {
    use types.{primitive-batch, layer-id};
    submit: func(layer: layer-id, batch: primitive-batch);  // imported; retained until a later submit
}

interface canvas {
    use types.{hit, command-call};
    on-hit: func(hit: hit) -> list<command-call>;           // hits resolved from the same buffers
}

world panel    { import crucible:api/read; import crucible:api/edit; export view; }
world canvas2d { import crucible:api/read; import crucible:api/edit; import canvas-host; export view; export canvas; }
```

- **Windows 11.** DX12 by default, Vulkan as an alternative; G1 needs Shader Model 6.6. On Windows ARM64, Chrome keeps WebGPU behind a flag, so browser users run G3.
- **macOS.** Apple's feature tables give 64-bit atomic min and max to Apple8 GPUs (M2-series) on macOS and to every Apple9 GPU [Apple Metal feature tables]. M1-series Macs (Apple7) therefore run G1 without `compute_raster`. Indirect-count draws exist only on DX12 and Vulkan, so every tier uses single indirect draws. Display P3 is the default, and ProMotion gets 120 Hz interface frames.
- **Linux.** Vulkan; Wayland and X11 with fractional scaling; AT-SPI. IME runs through winit on both, and X11 reports a caret position rather than an area [winit Window].
- **Browsers.** WebGPU is on by default in Chrome and Edge on Windows, macOS and ChromeOS (since 113) and in Safari 26 [gpuweb implementation status]. Firefox has it on Windows (since 141) and Apple silicon (since 147, or 145 on macOS 26). On Linux, Chrome enables it only for Intel Gen12+ and NVIDIA on Wayland, so many Linux users run G3. G2 page pools split into 128 MiB bindings.
- **Browser services.** The CAS and replica live in OPFS [MDN OPFS], and a service worker caches the shell. Shared-memory threads need a secure context and cross-origin isolation [MDN SharedArrayBuffer], so the app's pages are served cross-origin isolated. The web-view viewer build loads no engine module. EditContext and WebHID are not Baseline and have fallbacks, and Noto CJK downloads on first use.
- **Tablets (phase 3).** On iPadOS the web build runs in a thin WKWebView shell with WebKit's WebGPU (contract 7.4). It runs only first-party Wasm components, evaluates registry ones remotely, and shows packages only as dependencies of an opened design. The shell rests on PLT's phase 1 device-farm spike: cross-origin isolation under the app's URL scheme, synchronous OPFS handles, WebGPU in WKWebView and the memory ceiling. PLT names the fallbacks: the single-threaded build, WebGL2 and remote evaluation. Android Chrome has WebGPU from Android 12, and device-loss recovery is tested on Tier 2 hardware every release.
- **Everywhere.** Engineering styles stay SDR, so colours match across displays. Tier 3 builds use Vulkan and AT-SPI without a support commitment. Only the shortcut modifier, text chords, menu bar location and native dialogs differ by OS.
