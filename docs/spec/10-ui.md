# UI and interaction (UIX)

Crucible's interface is a live, GPU-rendered view of one typed Ingot program. People see geometry, physics and cost as computed, judge changes through evidence-linked review, and steer designs and agents through code, direct manipulation or conversation. One Rust toolkit and one wgpu renderer give Windows, macOS, Linux and the browser one feature set, across three declared GPU capability tiers.

## Interface principles

These eight rules bind every later section. Reviewers can reject any screen that breaks one.

1. **The interface edits only through `api`.** Every product-changing action is an Ingot edit or a `repo` operation that an agent could issue with the same call.
2. **Result status is always visible.** Every displayed result is labelled proxy, coarse (with error bound), exact, stale or failed, and exact is the quiet default. Simulation results also name their Flux fidelity mode, interactive or sign-off.
3. **Evidence sits beside claims.** A number on screen links to the check, measurement or Field that produced it.
4. **One gesture, one transaction.** A drag, a dialog commit or a typed edit becomes one `repo` change and one undo step.
5. **Panels never own data.** Modes, panels and viewports are projections of the model.
6. **Keyboard and screen reader complete.** Everything a pointer can do, the keyboard and the accessibility tree can do.
7. **Calm by default.** Color carries meaning only, motion explains state changes only, and nothing redraws when idle.
8. **Agents are named collaborators.** Agents appear with presence, history and scoped permissions, never as anonymous automation.

**Decision D-UIX-1:** The UI holds no product state of its own: every product-changing action is an `api` Edit or Propose call that changes Ingot source or `repo` records, per-user presentation state lives in `ViewState`, and shared views are repository files. *Why:* contract principle 2 (one model, three editors) and agent parity: anything a person does, an agent can do, inspect and replay. *Rejected:* GUI-side feature records synchronized to code (two sources of truth); storing camera and visibility in the model (pollutes diffs and merges).

Every command records its `api` call. The version history shows it, and "Copy as `api` call" puts it on the clipboard, so people can hand any manual step to an agent or a script.

## Information architecture

### Places

### The workspace

| Region | Contents | Default placement |
| --- | --- | --- |

Panels dock left, right or bottom, or detach to separate windows on desktop, and layouts are saved per mode per user. Below 1280 px of width the side panels collapse to drawers; below 768 px they become bottom sheets. F6 and Shift+F6 cycle focus between regions.

### Model tree

The tree unifies structure and history: Assembly, then Instances, then Part, then its feature list, then features, then (on demand) the entities each feature created. Top-level nodes add Parameters, Studies, Manufacturing setups, Checks, Saved views and Packages.

- **Rows** show a type icon, name, status glyph (error, warning, failed check, suppressed, stale), Instance count and presence dots. Status never relies on color alone.
- **Scale.** The tree is virtualized and holds 1,000,000 nodes; scrolling and expanding stay within one frame (target).
- **Filter** by name, type, status or a `Query` expression typed into the filter field.
- **Edit actions.** Rename is a symbol rename, suppress sets an Ingot attribute, and delete previews dependents first. Reorder moves a statement after a dependency check and refuses illegal moves with the reason ("`web` uses `base`, defined on line 4").
- **View actions.** Hide and isolate change `ViewState` only.
- **Rollback marker.** Dragging the marker within a feature list shows the Part as evaluated up to that feature. It is a view, labelled "Showing state after `rib`", and edits made there insert at that position.

The *feature list* orders program statements. The *version history* orders `repo` changes in time. The UI never calls both "history".

### Properties and feature dialogs

Feature dialogs are generated from the `Feature` metadata that Ingot declares. They contain groups, typed fields with units and ranges, `Tol<T>` inputs, enumerations as segmented controls, and entity references as selection fields showing the readable `Query`. Typing `=` in any field switches it to an expression.

Dialogs are modeless and live: each change previews through the coarse-first pipeline, Done commits one change and Cancel discards the draft. For selected geometry, the panel shows exact measurements from Anvil (area, length, radius, normal, mass properties with the assigned Material), never values derived from display meshes.

### Version history

The version history shows `repo` changes on the current branch, grouped by session and author, people and agents alike. It supports:

- **Time travel.** Selecting an entry renders the model at that change from CAS, read-only, under a banner naming the change.
- **Compare.** Any two entries open the review diff.
- **Restore.** Creates a new change that returns the source to that state; history is never rewritten.
- **Provenance.** Each entry lists its `api` calls and an Ingot diff summary; filters select by author, agent, feature or file.
- **Graph.** A toggle shows branches and merges.

### Modes

**Decision D-UIX-2:** Design, Simulate, Manufacture and Review are presets over one workspace: each sets the panel layout, tool palette, selection filters and default display style, and switching never reloads or converts data and keeps selection and camera. *Why:* engineers alternate between intent and evidence many times an hour, and one model has one workspace. *Rejected:* separate applications or documents per domain (duplicate state, export round-trips); modes that own data (hidden coupling).

| Mode | Primary tools | Default display style | Default panels |
| --- | --- | --- | --- |
| Design | Sketch, features, direct edit, assembly, measure | Shaded with edges | Tree, code, properties |
| Simulate | Study setup, loads and supports, run, results | Field view | Tree (studies), properties, legend, checks |
| Manufacture | Setups, toolpaths, additive preparation, cost | Shaded with toolpaths | Setups, operations, playback, cost |
| Review | Proposals, diffs, comments, approvals, variants | Compare overlay | Review panel, agent timeline |

Ctrl+1 to Ctrl+4 (Cmd on macOS) switch modes; the palette lists them too.

### Result status and errors

```rust
/// Attached to every displayed Body, Field, metric and check result.
pub enum ResultStatus {
    Proxy,                               // GPU-only transform of old geometry during a drag
    Coarse { bound: ErrorBound },        // streamed early by Kiln, error stated
    Exact,                               // final result for this change
    Stale { since: ChangeId },           // model changed; result not yet recomputed
    Failed { error: api::BuildError },   // typed error with suggested fixes
}
```

| Status | Viewport treatment | Elsewhere |
| --- | --- | --- |
| Proxy | Dashed outline, label "preview" | — |
| Coarse | Label "coarse ±0.2 mm" near the edited feature | Metrics show "≈" and the bound |
| Exact | No decoration | Plain values |
| Stale | Desaturated only if the update takes more than 300 ms, to avoid flicker | Tree spinner; metrics greyed with "stale" |
| Failed | Last good geometry ghosted; failing entity outlined | Error at the tree row, the source span and the status bar |

Errors render as message, cause, location links and fix actions. Each fix is an edit the user can preview before applying, taken from typed errors such as `ResolveError`. The status bar summarizes Kiln progress ("Exact 128/203 operations") with a cancel control.

### View state and saved views

```rust
/// Presentation only. Never part of the model, never affects evaluation.
pub struct ViewState {
    pub at: ChangeId,                    // repo change this view refers to
    pub camera: Camera,                  // f64 eye, target, up; perspective or orthographic
    pub style: DisplayStyle,             // ShadedEdges, Shaded, Wireframe, HiddenLine, Realistic, XRay
    pub visibility: Vec<VisibilityRule>, // hide or isolate, each by Query

```

Saved views are files in the design repository (proposed path `views/<name>.view.toml`, confirmed by `repo`), so agents read and write them, snapshots and comments cite them, and review opens on them. Transient per-user view state persists locally.

### Project dashboards

A dashboard is a file listing widgets, stored in a design repository or in a project's shared settings repository (`repo` decides). Each widget is a saved `api` Read query plus a visualization spec, so agents can create and update dashboards.

Standard widgets are release readiness (required checks and approvals), check trend, open Proposals by state, CI health, budgets versus targets (mass, cost, power) with variance, BOM summary, activity feed and agent spend. Every chart has a table view for screen readers and export.

## UI toolkit

### Choice

Crucible needs a Rust toolkit that draws on the GPU and renders text in every script. It must expose a full accessibility tree on every Tier 1 platform including the browser, handle input method editors (IME), virtualize million-row trees and behave identically everywhere. No surveyed toolkit meets all of these today:

| Candidate | Strength | Blocking gap for Crucible |
| --- | --- | --- |
| GPUI (Zed) | Proven 120 fps editor UI; instanced SDF primitives; Taffy layout | "Tied to Zed" for the near future; no documented browser target; Narrator could not read it in a 2025 Windows test |
| egui | Mature; runs on web; Rerun's viewer is built on egui and wgpu | Immediate-mode layout limits (first-frame size guess, per-frame layout cost); README documents AccessKit on Windows and macOS only, none on web; no shaping or bidi listed |
| Xilem / Masonry (Linebender) | AccessKit, Parley text, modular | Still settling: Masonry received a new layout system and rendering abstraction in Q1 2026 |
| Slint | Narrator and IME worked in the 2025 test | A second UI language (its own markup) beside Rust and Ingot |
| Iced and others | Various | Missing accessibility or IME in the same 2025 test |
| Dioxus or Tauri (webview) | Native accessibility and IME through the browser engine | Second runtime and compositor beside the wgpu viewport; behavior differs between WebView2, WebKitGTK and WKWebView |

**Decision D-UIX-3:** Crucible builds its own retained-mode GPU toolkit in the style of GPUI, assembled from proven open crates: Taffy for layout, Parley (HarfRust shaping, ICU4X bidi, Fontique fallback, Skrifa outlines) for text, AccessKit for accessibility, and wgpu for drawing. It lives in `apps/ui-toolkit` under Apache-2.0 or MIT. *Why:* the hard, standards-heavy parts (layout, shaping, accessibility) come from maintained crates; the thin widget and state layer is product-specific and must stay under Crucible's control for identical behavior on every platform. *Rejected:* adopting GPUI (not independent of Zed, no web), egui (layout model and web accessibility), Masonry as a dependency (unsettled API; reconsidered at each phase gate), webview UI (two runtimes, inconsistent engines, viewport compositing cost).

### Architecture

1. **State cells.** Interface state lives in typed cells (`State<T>`) owned by the app context; mutating a cell notifies its observers. Product data is never copied into cells beyond what `api` subscriptions deliver.
2. **Widgets.** A widget is a struct whose `render` builds an element tree from state cells. Only widgets that observe a changed cell re-render; unchanged subtrees reuse cached layout and primitives.
3. **Elements.** Keyed elements give stable identity across frames for focus, animation, accessibility node ids and text selection.
4. **Layout.** Taffy computes Flexbox, Grid and Block layout. Virtualized containers (list, tree, table, code editor) lay out only realized rows.
5. **Paint.** Elements emit primitives into a scene: quads (signed-distance rounded rectangles with borders), shadows (closed-form erf for rectangles), glyph runs, icons, images, vector paths and viewport surfaces.
6. **Draw.** Primitives batch by type into instanced draws in wgpu. The UI needs no compute shaders, so it draws identically on WebGPU and WebGL2.
7. **Damage.** Frames render only when input, a state change, an animation or a viewport refinement requires one. An idle window issues no GPU work.

Icons rasterize into the glyph atlas, and other vector paths (charts, thumbnail sketches) tessellate on the CPU. Vello was considered for 2D paths, but its original renderer relies on GPU compute, which WebGL2 lacks, and Vello Hybrid was "roughly beta quality" in April 2026. It is re-evaluated at the phase 2 gate.

pub trait Render: 'static + Sized {

pub struct WidgetContext<'a, W> { /* app, window, widget handle */ }

### Text

- **Shaping and layout.** Parley shapes text with HarfRust, a Rust port of HarfBuzz that "for the most part passes the HarfBuzz test and fuzzing suites". ICU4X resolves bidirectional text, Parley breaks lines, and Fontique enumerates fonts and selects fallbacks.
- **Bundled fonts.** Inter sets interface text and JetBrains Mono sets code. Noto families cover scripts Inter lacks, such as Arabic, Hebrew, Devanagari and CJK; Noto spans "more than 1,000 languages and over 150 writing systems". Bundling makes text metrics identical on every platform, and system fonts serve only as a logged last fallback.
- **Rasterization.** Glyph outlines come from Skrifa and rasterize on the CPU into an alpha-only atlas at four horizontal subpixel offsets. Color comes from the instance color at draw time, as in GPUI. Antialiasing is grayscale on every platform, with a contrast curve tuned per display scale.
- **Numbers.** Numeric fields, tables and dimensions use tabular figures and a slashed zero, so columns align and 0 differs from O.
- **Editing.** Single-line and multi-line editors support selection, bidi caret movement, grapheme-aware deletion, IME composition with underline styles, and platform text shortcuts (Option+Arrow on macOS, Ctrl+Arrow elsewhere).

**Decision D-UIX-4:** Grayscale antialiasing with bundled fonts on every platform, instead of each OS's text rasterizer and LCD subpixel antialiasing. *Why:* identical layout and glyph bitmaps across platforms (snapshot oracles depend on it), correct rendering over translucent and colored surfaces, and one code path. *Rejected:* OS text stacks as in Zed, which shapes with each OS's APIs (per-platform metric differences break identical behavior and visual regression tests); LCD subpixel antialiasing (fails over transparency and rotated text; one platform class only).

### Accessibility architecture

- **Native.** AccessKit adapters provide UI Automation on Windows, NSAccessibility on macOS and AT-SPI on Linux. Android and iOS adapters serve Tier 2 tablets. AccessKit's push model (a full tree, then incremental updates) fits the toolkit's keyed elements.
- **Browser.** AccessKit's web adapter is planned but not yet available. Crucible builds it and offers it upstream: a hidden DOM mirror with ARIA roles, names, states and bounding boxes, positioned over the canvas and updated from the same AccessKit tree updates. Flutter web uses the same pattern of translating its semantics tree into an accessible DOM.
- **Always on.** Flutter web enables its mirror only on request for performance reasons. Crucible's mirror is on by default because virtualization bounds it to realized nodes (about 2,000 in a full workspace). Target: under 1 ms per frame of mirror updates.
- **Virtualized collections** expose `aria-setsize` and `aria-posinset`, so a screen reader announces "row 4,512 of 1,000,000" without materializing every row.
- **Viewport semantics** are specified under Accessibility.

**Decision D-UIX-5:** Crucible implements the AccessKit web adapter as a DOM mirror and enables it by default on the web. *Why:* WCAG 2.2 AA on a Tier 1 platform, with no hidden opt-in step. *Rejected:* a DOM-based web UI (breaks the single toolkit and identical behavior); Flutter-style opt-in (screen-reader users must discover a hidden control first).

### Text input in the browser

The browser shell uses the EditContext API where available, which lets a custom-rendered editor receive IME composition and report caret bounds to the operating system. EditContext is not Baseline, so other browsers get a hidden `<textarea>` proxy positioned at the caret. Both paths feed one internal text-input event stream, and the IME oracle runs on both.

## Renderer

The renderer is one crate, `apps/render`, on wgpu 30. It draws the viewport, Field views, toolpaths, overlays and headless snapshots. The UI toolkit's own 2D drawing uses the same wgpu device.

### GPU capability tiers

Feature sets differ sharply across backends. wgpu 30 exposes 64-bit atomics, indirect-count draws, binding arrays and subgroups on native backends only, and mesh shaders are experimental.

The WebGPU Candidate Recommendation Draft of 15 September 2026 defines no multi-draw indirect, no bindless resources and no mesh shaders. Its only wide atomic is the optional `atomic-vec2u-min-max` feature, which Dawn implements as 64-bit atomic min and max.

WebGL2 has no compute at all. On Linux, Chrome enables WebGPU only for Intel Gen12+ and NVIDIA on Wayland, and Firefox ships WebGPU on Windows and Apple silicon Macs but not yet on Linux.

| Tier | Where | Required capabilities | Capacity at 60 fps on the reference laptop (targets) |
| --- | --- | --- | --- |
| G1 Full | Native Vulkan 1.3, DX12 Shader Model 6.6, Metal 3.1 | Compute, storage buffers, indirect draws; `SHADER_INT64_ATOMIC_MIN_MAX` or `TEXTURE_INT64_ATOMIC` enables software rasterization | 1,000,000 Instances; 2 billion instanced source triangles; 5M unique visible triangles |
| G2 Compute | WebGPU core in browsers; native adapters lacking G1 features | Compute, storage buffers, single indirect draw | 100,000 Instances; 200M instanced source triangles; 5M unique visible triangles |
| G3 Raster | WebGL2 and GLES 3.0 | Instanced draws, float render targets | 10,000 Instances; 2M visible triangles |

**Decision D-UIX-6:** Every feature works on every tier; tiers differ only in declared capacity and refinement speed, and the status bar's graphics popover names the tier and its limits. *Why:* the contract's identical-features rule, stated honestly, since hardware cannot deliver identical scale. *Rejected:* hiding features on weaker tiers (breaks parity); one lowest-common-denominator renderer (wastes native hardware by an order of magnitude).

A CPU path exists for every GPU path, including picking and Field sampling. Headless servers and broken drivers render through wgpu on software Vulkan (Mesa lavapipe on Linux) or WARP (DX12 on Windows). When the GPU device is lost, the renderer rebuilds all resources from cached display packages, typically within one second, and the status bar says "Graphics restarted".

### Display data

Anvil owns tessellation; the renderer never tessellates B-rep. The contract's decision "engine ships changed triangles, camera and selection local" becomes this protocol:

```rust
/// Produced by Anvil and Kiln, cached in CAS under hash(Body, display tolerance).
pub struct DisplayPackage {
    pub body: BodyHash,
    pub status: ResultStatus,            // Coarse { bound } while streaming, then Exact
    pub chordal_error: Length,           // max distance from display triangles to the exact Body
    pub bounds: Aabb,
    pub faces: Vec<EntityId>,            // face table; clusters store indices into it
    pub edges: Vec<DisplayEdge>,         // polyline per model edge, with EntityId and continuity (sharp, G1, G2)
    pub pages: Vec<CasRef<ClusterPage>>, // cluster DAG pages, 64 KiB each
    pub root_pages: Vec<u32>,            // always resident
}
```

- **Faces and edges share vertices**, so model edges never crack away from faces.
- **Clusters hold up to 128 triangles.** Level-0 clusters never cross a face boundary, so highlighting, picking and incremental updates work per face. Coarser levels may merge faces and keep a per-triangle face index for approximate picking.
- **Compression** uses meshoptimizer's codecs: lossless vertex encoding, index encoding near one byte per triangle, and meshlet encoding of 5 to 7 bits per triangle, decoded at several GB/s on worker threads.
- **The cluster DAG** follows meshoptimizer's `clusterlod` approach: cluster, group neighbors with `meshopt_partitionClusters`, simplify each group with locked borders, re-cluster, and repeat. The simplification is a std operation in Anvil, so its result is deterministic and cached like any other. Every node stores a monotone error bound in Part units.
- **Incremental updates.** When an edit changes a Body, only changed faces are re-tessellated (cached per face hash and tolerance). Their level-0 clusters arrive first; coarser DAG levels rebuild in the background, because a Part in focus never needs them.
- **Display tolerance** follows the view: the renderer requests refinement until chordal error projects under 0.5 px (target). Anvil states the error achieved, and the status bar shows it on demand ("display accuracy 0.004 mm").

**Decision D-UIX-7:** Display data is a cluster-DAG `DisplayPackage` per Body, produced off the UI thread and cached in CAS; culling, LOD selection, camera and selection run locally in the renderer. *Why:* local interaction never waits for the engine, unchanged Bodies cost nothing after an edit, and one format serves desktop, browser, review and CI. *Rejected:* a monolithic mesh per Body (no LOD, full re-upload on every edit); server-side rendering with video streaming (latency, bandwidth, no offline use, cost per viewer).

### Scene and precision

- **Scene graph.** A flat, data-oriented table of draw Instances mirrors the Assembly tree. Each row holds a Part reference, a world transform, visibility, style overrides, and selection and hover flags. Identical Parts share one `DisplayPackage`.
- **Relative-to-eye transforms.** World transforms are `f64`. On the GPU each translation is stored as a high and low `f32` pair, and shaders subtract the eye position in the same split form. Positions stay precise to the micrometer at kilometer scale without per-frame CPU work.
- **Depth.** Depth is 32-bit float with reversed Z and an infinite far plane. Nathan Reed's analysis found this gives "a *zero error rate*" in his test, far better than every other option. The near plane adapts to 0.1 times the distance to the nearest visible bound, down to 1 µm.
- **Instance BVH.** A binned-SAH bounding volume hierarchy over Instances is rebuilt when the Assembly changes and refit when Instances move.

**Decision D-UIX-8:** Reversed-Z float depth, an infinite far plane and relative-to-eye split-precision transforms on every tier. *Why:* Crucible spans MEMS to ships, so one scene can hold micrometer details and hundred-meter extents. *Rejected:* logarithmic depth (disables early depth test, costs fragment depth writes); per-frame CPU rebasing of transforms (CPU cost at a million Instances).

### Frame pipeline (G1 and G2)

[[DIAGRAM: renderer frame graph. Boxes in order: "Upload deltas (pages, transforms, selection)" → "Instance cull (frustum + last-frame depth pyramid)" → "Cluster LOD cut (projected error < 1 px)" → "Cluster cull (frustum, backface cone, occlusion)" → "Raster pass 1 → visibility buffer + depth" → "Build depth pyramid" → "Re-test culled clusters → raster pass 2" → "Resolve (shading, Field colors, selection tint)" → "Edges and silhouettes" → "Transparency" → "Ambient occlusion" → "Overlays (gizmos, dimensions, cursors)" → "Tone map, output transform, anti-aliasing" → "UI composite". A side arrow from "Raster pass 1" to "GPU picking readback".]]

1. **Upload deltas**: new and evicted cluster pages, changed Instance transforms, selection and hover sets.
2. **Instance culling** in compute against the frustum and the previous frame's depth pyramid.
3. **LOD cut.** For each visible Instance, a cluster is drawn when its own error projects under the threshold τ (1 px default) and its parent's error does not. Monotone DAG errors make the cut crack-free, as in Nanite's cluster hierarchy, which switches detail by view without cracks. On-screen geometric error therefore stays under 1.5 px: 0.5 px from tessellation plus 1 px from LOD (targets).
4. **Cluster culling**: frustum, backface cone (from meshoptimizer bounds) and occlusion against the reprojected depth pyramid. Survivors append to a visible list; occlusion rejects go to a retest list.
5. **Raster pass 1** writes a visibility buffer. On G2 it is an `R32Uint` target packing a 25-bit visible-cluster slot and a 7-bit triangle index, plus a depth buffer. On G1 devices with 64-bit atomics it is a 64-bit buffer of packed depth and the same id, written by atomic max from fragment shaders and the compute rasterizer alike; reversed Z keeps the nearest surface at the maximum. Other G1 devices use the G2 layout.
6. **Depth pyramid** built from the new depth, conservative toward far.
7. **Raster pass 2** retests rejected clusters against the new pyramid and draws the newly visible ones. This two-pass scheme removes popping without a CPU readback.
8. **Resolve.** A compute pass reads each pixel's triangle, reconstructs barycentrics, interpolates attributes and shades by display style. It also writes face indices and normals for the edge pass.
9. **Edges, transparency, ambient occlusion, overlays, tone mapping and anti-aliasing**, specified below.

On G2, the visible list is drawn with one `drawIndirect` whose instance count is the number of visible clusters. A vertex shader pulls cluster vertices from storage buffers and emits degenerate triangles past a cluster's triangle count. This needs no multi-draw indirect, which WebGPU lacks.

On G1, clusters whose triangles project under about two pixels are rasterized in compute, writing packed depth and ids with 64-bit atomics. Bevy's virtual geometry writes its visibility buffer the same way, with 64-bit storage-texture atomics on wgpu. Dawn added `atomic-vec2u-min-max` experimentally on Vulkan in February 2026; where a browser exposes it, G2 enables compute rasterization too.

On G3, the CPU culls Instances against the BVH, chooses one DAG cut per Instance at coarse granularity, and issues instanced indexed draws per Part and LOD. Shading is forward, writing ids and normals to extra render targets for edges and caps, and ambient occlusion runs as a half-resolution fragment pass. Picking ray-casts on the CPU against the Instance BVH and level-0 clusters, which avoids WebGL2 readback stalls and stays within 16 ms at G3's declared capacity (target).

**Decision D-UIX-9:** Virtualized geometry uses a cluster DAG, GPU-driven culling with two-pass occlusion and a visibility buffer on G1 and G2, with compute rasterization of small triangles on G1 only. Mesh shaders are an optional G1 path, adopted only if they measure at least 15% faster on the large-assembly benchmark. *Why:* this is the state of the art in practice (Nanite; GPU-driven cluster culling since Haar and Aaltonen 2015; depth-pyramid occlusion culling as in zeux's niagara; Bevy's open implementation on wgpu) and it maps onto WebGPU core. *Rejected:* mesh-shader-only pipelines (experimental in wgpu, absent on the web); per-object draw calls with discrete LODs everywhere (CPU-bound beyond about 10,000 Instances).

### Very large assemblies

- **Instancing.** A fastener used 40,000 times stores one `DisplayPackage` and 40,000 transforms of 64 bytes each.
- **Streaming.** Clusters that want refinement write page requests into a GPU buffer read back every frame. A loader fetches pages from the local CAS, or from the team server's CAS through `api`, and decodes them on worker threads. It uploads them into a fixed GPU page pool with least-recently-used eviction, and root pages stay resident.
- **Budgets (defaults, adjustable).** Page pool 1 GiB on G1 desktops (at most 50% of VRAM), 512 MiB on G2, 256 MiB on G3 and Tier 2 devices.
- **Coarse first.** Opening an assembly loads only root pages, so the whole product is visible quickly. Target: complete coarse view of a 1,000-part assembly within 2 s from warm cache, fully refined within the contract's 10 s.
- **Nothing vanishes.** Instances smaller than a pixel draw as one-pixel point sprites instead of disappearing, so reviewers never lose small fasteners. Model edges fade out on Instances smaller than 48 px on screen, to avoid noise.
- **Lightweight mode.** Assemblies open from display packages alone. Picking still yields `EntityId`s from the face tables. Measurements made there show "≈" with the display error until Anvil returns the exact value.

Nanite caps a scene at 16 million Instances; Crucible's G1 target is one million Instances in phase 2 and ten million for building and ship-scale products in phase 5.

### Picking and selection

- **Faces.** A click reads the visibility buffer under the cursor, maps the triangle to its face index and `EntityId`, and highlights the face in the next frame. Contract target: under 16 ms.
- **Confirmation.** A hit from a coarse cluster, or within one pixel of an edge, is confirmed by a CPU ray cast against level-0 data. Confirmation takes under 2 ms (target) and precedes the selection commit.
- **Edges and vertices.** Edges and vertices render into a pick buffer of IDs widened to the pick radius: 4 px for mouse and pen, 12 px for touch. Precedence is vertex, then edge, then face, within the radius.
- **Pick-through.** Clicking again in place cycles through the stacked entities under the cursor, and a list popup names them.
- **Box and lasso selection.** A GPU frustum query over clusters returns faces or Instances. Left-to-right drag selects entities fully inside; right-to-left selects entities crossing the boundary, matching common CAD convention.
- **Filters.** Selection filters (face, edge, vertex, Body, Part, Instance, feature) are toggles in the status bar, with mode-specific defaults.

Every selection becomes a `Query` before it is used in an edit. The UI calls `api` Inspect `suggest_queries(entities)`, which returns ranked candidates such as `base.face(top)`, `part.faces(cylindrical, radius == 4.2mm)` or a name, each with a robustness rating. Index-based or otherwise fragile queries carry a warning and a one-step "Name this selection" fix.

**Decision D-UIX-10:** Picking reads the visibility buffer and confirms ambiguous hits against level-0 geometry; selections enter edits only as `Query` values chosen from ranked suggestions. *Why:* a fast pick that is never wrong about identity, and selections that survive rebuilds as the contract requires. *Rejected:* CPU-only ray casting (too slow at assembly scale); storing raw `EntityId`s in source (unreadable and brittle under topology changes).

### Edges and silhouettes

- **Model edges** come from `DisplayPackage.edges`, the exact B-rep edges sampled within display tolerance. They render as screen-space quads with analytic coverage antialiasing, 1.25 px wide at scale 1 by default, depth-tested against the visibility buffer with a slope-scaled tolerance so coplanar faces never hide them.
- **Tangent edges** (G1 joins, such as fillet boundaries) render thinner and lighter, or not at all, per display style. G2 joins render like tangent edges.
- **Silhouettes** of curved faces depend on the view, so the resolve pass detects them in image space. A pixel lies on a silhouette when its Body or face id, depth or normal differs from a neighbor's beyond a threshold scaled by pixel footprint.
- **Hidden-line mode** draws hidden model edges dashed. The dash pattern advances in screen space, so dashes do not crawl during orbit.
- **Exact drawings.** Vector hidden-line output for drawings and PDF export uses exact silhouette curves from Anvil, not the image-space pass. The renderer only previews it.

Bénard and Hertzmann's tutorial covers the trade-offs between exact object-space contours and fast hardware methods; Crucible uses the fast method for display and the exact method for documents.

### Transparency

**Decision D-UIX-11:** Transparency uses a hybrid scheme on G1 and G2: the nearest k transparent layers per pixel (k = 4 by default; k = 2 above 8 megapixels on G2) resolve exactly with a two-pass k-buffer built from 32-bit atomics, and deeper layers merge with weighted blended order-independent transparency (McGuire and Bavoil). G3 uses weighted blended transparency alone. *Why:* X-ray views of nested housings need exact order in the front layers, where people look. The k-buffer needs only 32-bit storage-buffer atomics, which WebGPU core provides, and memory stays at 41 bytes per pixel for k = 4 (85 MB at 1920×1080). *Rejected:* depth peeling (one geometry pass per layer); per-pixel linked lists (unbounded memory); weighted blending alone (front layers mis-ordered in nested shells); moment-based transparency (better tail accuracy, but more targets for little gain behind four exact layers).

Weighted blending is tuned for opacities between about 0.2 and 0.9, and Crucible clamps transparent display opacities to that range. The graphics popover counts pixels whose layers exceeded k, so the approximation is never silent. Transparency serves X-ray style, ghosted context (Instances outside an isolate at 15% opacity), translucent Materials and Field isosurfaces.

### Section views

- **Cuts.** Up to six clip planes, or one box, positioned with the gizmo or typed values. Each plane can be offset, flipped and locked to a face or datum by `Query`, so the section follows the design through rebuilds.
- **Caps.** A pixel lies inside material when the nearest surface behind the clip plane is a back face of a closed Body. The resolve pass then draws a cap at the plane depth, in the Part color with an optional hatch per Material class. Open Bodies get no cap and show their interiors in a distinct inside shade.
- **Exact section.** After the view settles, the UI requests the planar section from Anvil and overlays the exact section curves. The properties panel shows section area, centroid and second moments from those curves, never from the display mesh.
- **Fields on caps.** In Simulate mode, caps show the active Field sampled on the cutting plane, so interior stress or temperature is visible without a separate slice.
- **Sharing.** Section cuts live in `ViewState`, so saved views, comments and review snapshots reproduce them exactly.

### Materials, lighting and display styles

| Style | Shading | Edges | Use |
| --- | --- | --- | --- |
| Shaded with edges | Headlight plus hemisphere ambient, ambient occlusion | Model edges and silhouettes | Default for Design |
| Shaded | As above | Silhouettes only | Clean views |
| Wireframe | None | All edges, hidden dimmed | Topology inspection |
| Hidden line | White faces | Visible solid, hidden dashed | Drawing preview |
| Realistic | Image-based lighting, OpenPBR appearance, shadows | Optional | Appearance review and renders |
| X-ray | Hybrid transparency | Model edges | Assembly interiors |
| Field view | Colormap with limited lighting | Model edges | Simulate mode |

- **Appearance model.** Material appearance uses OpenPBR Surface 1.1.1 (ASWF, April 2026): metal or dielectric base with GGX microfacets and F82-tint Fresnel, coat, fuzz, thin-film iridescence and transmission. The real-time path evaluates a reduced form and documents the deviation. Offline references come from the MaterialX implementation of OpenPBR.
- **Lighting.** Realistic style uses prefiltered environment lighting plus one shadowed key light. Engineering styles use a headlight with a hemisphere ambient, so shading never hides geometry from the current viewpoint.
- **Ambient occlusion.** Screen-space ground-truth ambient occlusion (Jimenez et al. 2016, as in Intel's MIT-licensed XeGTAO) with a 5×5 depth-aware denoise. XeGTAO (now archived by Intel; Crucible ports the method to WGSL) reports about 0.56 ms at 1920×1080 on an RTX 2060 but about 2.39 ms on an Intel i7-1195G7 integrated GPU. Crucible therefore runs the low preset at half resolution during camera motion and accumulates full-quality samples when the view is still.
- **Hardware ray tracing.** When available, an optional path-traced Realistic preview is offered in phase 5, rendering progressively with sample counts shown. The engineering styles never depend on ray tracing, since wgpu exposes ray queries only as an experimental feature.

### Anti-aliasing and the still frame

During camera motion, model edges and overlays carry analytic antialiasing and surfaces use a one-frame morphological filter on the id and depth discontinuities, with no temporal history and therefore no ghosting. When the camera stops, the renderer accumulates 16 jittered frames over about 270 ms at 60 Hz, then stops rendering.

**Decision D-UIX-12:** No temporal anti-aliasing during interaction; progressive supersampling when the view is still. *Why:* CAD people judge edges and small features during orbit, and temporal reprojection smears thin lines; a still view converges to a 16-sample reference image, which also feeds snapshot oracles. *Rejected:* TAA (ghosting on thin edges, non-deterministic history); MSAA on the visibility buffer (four times the buffer memory and per-sample resolve).

### Color management

- **Working space.** Rendering is linear, with Rec.709 primaries in 16-bit float targets. Values outside [0, 1] are kept (extended range).
- **Output.** wgpu 30 lets a surface choose a color space. Crucible outputs sRGB by default, Display P3 where the platform supports it (Metal, and WebGPU surfaces in browsers), and extended-range output for Realistic previews on HDR displays.
- **Tone mapping.** Realistic style uses the Khronos PBR Neutral tone mapper, which maps colors 1:1 up to a threshold and compresses highlights. It was designed for product, architecture and CAD visualization and is adopted by Blender, Autodesk and Dassault Systèmes. Engineering styles, the UI and colormaps are display-referred and never tone-mapped.
- **Colormap colors.** Field colors are exact colormap entries. Lighting may only scale their luminance within [0.8, 1.0], and an "unlit" toggle shows them flat. The probe always gives the number, so no one reads values from shading.
- **Interface colors** are authored in Oklch (CSS Color 4) and converted to the output space, so they look identical in sRGB and Display P3.

### Display of Implicit, SubD and Mesh Bodies

| Representation | Default display | Advanced display | Picking yields |
| --- | --- | --- | --- |
| BRep | Cluster DAG from Anvil tessellation | — | Face, edge or vertex `EntityId` |
| Implicit | Anvil meshes at display tolerance, then cluster DAG | G1 and G2: direct GPU evaluation for very detailed fields such as lattices | Body `EntityId` plus the implicit's region labels |
| SubD | Limit surface tessellation from Anvil | Control cage overlay while editing | Face or edge of the cage or limit surface |
| Mesh | Cluster DAG directly | — | Triangle region `EntityId` |

Direct implicit rendering compiles the Anvil expression to WGSL and evaluates it per screen tile with interval-arithmetic pruning, following Keeter's massively parallel method (SIGGRAPH 2020). A lattice bracket with millions of struts then never needs a triangle mesh for display. The status label states the evaluation tolerance.

### Frame budgets

Targets on the reference laptop at 1920×1080. They refine the contract's targets, and frame-time tests measure them per stage with GPU timestamp queries. CPU and GPU work overlap by one frame, so each must fit within 16.7 ms on its own.

| Stage | Processor | Budget (target) |
| --- | --- | --- |
| UI input, state updates, layout, paint | CPU, UI thread | 3.0 ms |
| Scene deltas, uploads, command encoding | CPU, render thread | 2.5 ms |
| Instance and cluster culling, LOD cut | GPU | 1.0 ms |
| Raster passes and depth pyramid, 5M visible triangles | GPU | 6.0 ms |
| Resolve and edges | GPU | 2.5 ms |
| Ambient occlusion, transparency, overlays | GPU | 2.5 ms |
| Tone map, filter, UI composite | GPU | 1.0 ms |
| **GPU orbit frame** | GPU | **13.0 ms, leaving 3.7 ms headroom within 16.7 ms (60 fps)** |

- **Interface-only frames** (scrolling, typing, panels) target 8.3 ms, so 120 Hz displays stay smooth.
- **Input to photon.** Pointer events apply to the camera in the frame they arrive, with no more than one frame queued (target ≤ 2 frames plus display scan-out). Pointer samples come from coalesced events.
- **Never block the UI thread.** Engine calls, file reads and decoding run on workers. A UI-thread stall over 50 ms is a test failure, and telemetry reports it when the user opted in.
- **Idle.** Zero GPU submissions after the still-frame accumulation completes.

## Field visualization

Fields are painted on geometry, never exported to a separate post-processor. A `FieldView` pairs a `Field` with a `VisualizationSpec` and lives in `ViewState`.

```rust
pub struct FieldView {
    pub field: FieldRef,                 // a Field<Domain, V> produced by a study
    pub quantity: DerivedQuantity,       // magnitude, x, y, z, von Mises, principal 1..3, ...
    pub spec: VisualizationSpec,
}

pub enum VisualizationSpec {
    Color { map: Colormap, range: Range, bands: Option<u8>, isolines: Option<u8> },
    Vectors { density_px: f32, scale: VectorScale },
    Streamlines { seeds: SeedRake, max_length: Length, tolerance: f32 },
    Isosurfaces { values: Vec<f64>, opacity: f32 },
    Deformation { exaggeration: Exaggeration, show_undeformed: bool },
    Volume { map: Colormap, opacity_ramp: Ramp },  // phase 4
}
```

### Sampling contract with Flux

Accuracy is the first goal. The renderer never interpolates a high-order Field linearly without stating the error.

1. **Vertex samples.** Flux samples the Field at display-mesh vertices and returns values plus an interpolation-error estimate per cluster. The renderer asks Anvil to refine clusters whose error exceeds 1% of the color range (target).
2. **Per-pixel evaluation (G1 and G2).** Flux uses high-order and isogeometric discretizations and already compiles kernels for wgpu, so it can also return a WGSL evaluator plus coefficient buffers. The resolve pass then evaluates the Field exactly at each pixel's surface point, as ElVis [unverified] does for high-order finite elements.
3. **Probes** always call Flux's sampler at the exact surface point, so the readout carries Flux's own error estimate.

**Decision D-UIX-13:** Field colors come from per-pixel evaluation of Flux-provided GPU evaluators where the tier allows, otherwise from adaptively refined vertex samples with a stated interpolation error; probes always sample exactly. *Why:* linear interpolation of high-order solutions misplaces peaks, and the peak value is what engineers sign off on. *Rejected:* fixed per-vertex sampling (silent error near stress concentrations); exporting results to a separate post-processor (breaks one model).

### Colormaps

Crameri, Shephard and Heron show that rainbow maps distort data and fail for readers with color-vision deficiency, about 8% of men and 0.5% of women. Crucible ships only perceptually uniform maps from the Scientific colour maps suite (v8.0.1), which is perceptually ordered, readable with color-vision deficiency and readable in grayscale.

| Data | Default map | Notes |
| --- | --- | --- |
| Sequential (stress, temperature, magnitude) | batlow | Perceptually uniform, monotonic lightness |
| Diverging (signed stress, error versus target) | vik | Midpoint fixed at zero or a chosen reference |
| Cyclic (phase, angle) | A cyclic map from the same suite | Same color at both ends of the range |
| Categorical (regions, materials, bodies) | Paul Tol's qualitative palette | Distinct for colour-blind readers and in print |
| Uncertainty-aware | Value-suppressing uncertainty palette | Colors fade toward neutral as error grows (Correll, Moritz and Heer, CHI 2018) |

**Decision D-UIX-14:** Rainbow and jet colormaps are not offered, not even as an option. Imported legacy presets map to batlow, with a one-time notice. *Why:* scientific evidence of distortion and accessibility harm; defaults decide most users' choices. *Rejected:* offering jet "for familiarity" (familiarity is the reason the harm persists).

### Legends, ranges and envelope marking

- **Legends** always show the Field name, derived quantity, unit (following the user's unit preferences), range, colormap, result status and the study's fidelity mode. Ranges use rounded tick values.
- **Clipping is visible.** Values above or below a fixed range render in out-of-range colors with a fine hatch, and the legend counts the clipped area. Nothing saturates silently.
- **Extremes.** Minimum and maximum markers are placed automatically, with values and locations, and are hidden only on request.
- **Validity envelope.** Regions where any assumption leaves its `ValidityEnvelope` are hatched diagonally and listed, for example "Plastic strain beyond the linear-elastic envelope in 3 regions". Each listing links to the region and the governing assumption.
- **Error overlay.** A toggle shows Flux's error-estimate Field. In the value-suppressing palette, value and error combine in one map.

### Contours, vectors, streamlines, isosurfaces, deformation

| Visualization | Method | Tiers | Phase |
| --- | --- | --- | --- |
| Smooth color and bands | Per-pixel colormap lookup; bands from quantized values | All | 1 |
| Isolines | Fragment shader using screen-space derivatives of the Field value for constant-width lines | All | 1 |
| Vector glyphs | Arrows on a jittered screen-space grid of constant density, scaled by magnitude and colored by map | All | 2 |
| Surface flow texture | Image-space line integral convolution on visible surfaces | G1, G2 | 4 |
| Streamlines and pathlines | Adaptive Runge–Kutta 4(5) from a seed rake, drawn as shaded ribbons or tubes | GPU on G1, G2; worker threads on G3 | 4 |
| Isosurfaces | Marching tetrahedra on adaptively subdivided elements, or marching cubes on sparse grids; GPU compaction by prefix sum | GPU on G1, G2; CPU on G3 | 3 |
| Deformation | Vertex displacement by the displacement Field times exaggeration | All | 1 |
| Mode shapes and transients | Animated deformation or time scrubbing with cached frames | All | 2 |
| Volume rendering | Ray marching through sparse grids with an opacity ramp | G1, G2 | 4 |

- **Deformation scale.** Auto-exaggeration sets the largest displacement to 5% of the bounding-box diagonal. The legend shows "deformation ×215" in the same weight as the Field name, a "true scale" toggle sets 1:1, and the undeformed outline can be ghosted.
- **Interactive versus cited.** Streamlines dragged interactively integrate in the renderer with a stated tolerance and are labelled "display integration". Streamlines cited in reports or checks come from the same algorithm run as a Flux operation, deterministic and cached.
- **Reduced motion.** Mode-shape animation shows the peak state with a phase slider instead of looping.
- **Line probes and plots.** A path drawn on the model (or a section curve) produces a chart of the Field along it, with error bands.

## Direct manipulation

Direct manipulation edits the same Ingot program the code panel shows. Sketch-n-Sketch showed that output edits can be mapped back to small program changes by running the program "in reverse". Crucible applies that idea to typed CAD programs, using provenance and differentiation from the Ingot tab.

### From gesture to Ingot edit

Every manipulation produces an `EditPlan`: the user's intent plus ranked candidate edits that would realize it.

```rust
pub enum ManipulationIntent {
    MoveEntity   { target: Query, delta: Transform },        // faces, edges, sketch geometry
    SetMeasure   { target: Query, measure: Measure, to: Quantity<Dyn> }, // distance, angle, radius
    PlaceInstance{ instance: InstancePath, to: Transform },
    CreateFeature{ call: FeatureCall },                       // from a tool or push-pull on a region
}

pub enum EditCandidate {
    SetLiteral    { span: SourceSpan, to: Value },                 // change a number in source
    SolveLiteral  { span: SourceSpan, through: ExprId, to: Value }, // invert an expression to hit a target
    SetParameter  { symbol: Symbol, to: Value, uses: u32 },         // shared parameter; uses shown
    InsertFeature { after: FeatureId, source: IngotSnippet },       // direct-edit feature appended in history
    SetPlacement  { instance: InstancePath, to: Transform },
}

pub struct EditPlan {
    pub intent: ManipulationIntent,
    pub candidates: Vec<EditCandidate>,  // ranked; index 0 is the default
    pub chosen: usize,                   // Tab cycles during the drag
}
```

Ranking follows four rules, in order:

1. **Prefer the literal that drives the entity.** `api` Inspect returns, for the dragged quantity, the literals that contribute to it and the derivative of the quantity with respect to each. Ingot computes these with its algorithmic differentiation. The nearest single literal with a non-zero derivative ranks first.
2. **Solve through simple expressions.** When the value comes from an expression such as `width / 2`, the plan solves for the free literal by Newton steps on the derivative. When several literals contribute, the plan lists each and never edits more than one silently.
3. **Warn on shared parameters.** A parameter used in several places shows "used by 3 features". Changing it is offered; "change only here" introduces a new literal, and the diff shows that.
4. **Fall back to a direct-edit feature.** When no parameter controls the entity, the plan appends a std direct-edit feature such as `move_faces`, `offset_faces`, `replace_face` or `delete_faces`. These are ordinary Ingot features over Anvil operations, with no privileged path.

During a drag, a chip near the cursor states the chosen candidate in words, such as "thickness 4 → 6.2 mm" or "adds move_faces after fillet". Tab cycles candidates, and the code panel shows the pending change as a ghost diff.

**Decision D-UIX-15:** Direct manipulation edits source through ranked edit plans: change the driving literal when one exists, otherwise append a direct-edit feature, always showing which before commit. *Why:* one model with three editors; design intent survives when parameters exist, and history-free editing remains possible when they do not, as in Plasticity and Shapr3D's hybrid workflow. *Rejected:* opaque "synchronous" edits that rewrite history invisibly (magic, breaks review); refusing direct edits on unparameterized geometry (blocks imported and agent-made models).

| Stage | When | What the user sees | Target |
| --- | --- | --- | --- |

- **Drag lane.** Kiln gives drag evaluations their own lane. A new value cancels the outdated evaluation, and only the edited Part's downstream features are re-evaluated. The coarse result streams first, at the tolerance named in the label.
- **Proxy limits.** The proxy applies only when the edit is affine on the selected entities, such as moving a face or extruding a cap. Otherwise the stage is skipped and the handle alone moves until the coarse result arrives.
- **Failing values.** When a value fails to build (for example, a fillet radius larger than an adjacent face), the handle takes the danger style. It shows the typed error and the last value that built. Releasing on a failing value commits nothing and offers three actions: "Use 7.8 mm (last value that built)", "Commit anyway" (a failing build, as in code) and "Cancel".
- **Escape** cancels the gesture at any time and restores the prior state with no `repo` change.

### Handles and gizmos

Features declare handles in their Ingot UI metadata, so std features and user packages get the same treatment.

| Handle kind | Drags | Typical feature |
| --- | --- | --- |
| Linear | A length along a direction (face normal, edge, axis) | Extrude, offset, shell, chamfer distance |
| Angular | An angle about an axis | Revolve, draft, pattern angle |
| Radial | A radius or diameter | Fillet, hole, cylinder |
| Point | A 2D or 3D point, with snapping | Sketch points, spline points, origins |
| Planar | Two directions in a plane | Sketch region move, placement |
| Count | An integer, by dragging along the pattern direction | Linear and circular patterns |

- **Transform gizmo.** Three axis arrows, three rotation rings and three plane squares, drawn at a constant 96 px on screen. Axes carry X, Y and Z letters and distinct arrowhead shapes as well as color. The frame aligns to world, local or a picked face or edge.
- **Exact entry.** Typing a number during a drag enters an exact value, as in SketchUp's measurements box. Units are optional (the design's default unit applies), and `=` starts an expression such as `=width/2`.
- **Modifiers.** Drags step by zoom-adaptive increments in a 1, 2, 5 sequence and show the step size. The same modifiers apply to every drag: Alt (Option) moves freely without increments or inference, Shift locks the current direction or inference, and Ctrl or Cmd gives fine control at one-tenth speed.

### Push-pull

- **On a face**, push-pull drags along the normal. On the end cap of an extrude it changes the extrude distance; on any other face it plans `offset_faces` or `move_faces`.
- **On a sketch region**, it creates an extrude.
- **Boolean choice.** A chip cycles New Body, Join, Cut and Intersect. The default is Cut when the drag enters existing material and Join when it leaves it, and the chip always names the choice.
- **Coplanar faces.** Push-pull can select all faces coplanar with the picked face, shown highlighted before the drag starts.

### Sketching

- **Starting.** A sketch starts on a plane, datum or planar face. The reference becomes a `Query`, so the sketch follows the face through rebuilds. The camera turns normal to the sketch plane unless the user turned that off, and with reduced motion it cuts without animation.
- **Drawing tools.** Line and polyline, rectangle (corner, center, three-point), circle, arc (three-point, tangent, center), slot, polygon, ellipse, conic, spline (fit and control points), point and text.
- **Editing tools.** Offset, trim and extend, mirror, pattern, and project (include model edges by `Query`). Any entity can toggle to construction geometry.
- **Source form.** A sketch is an Ingot block of entity and constraint statements, following the Ingot tab's syntax:

```
let profile = sketch(base.face(top)) {
    let a = line(p0, p1)
    let b = arc(tangent_to: a, end: p2)
    horizontal(a)
    dim(a.length, 40mm)
    coincident(b.end, origin.y_axis)
}
```

- **Solving.** The 2D constraint solve is an operation owned by Anvil and called through `api`. Dragging under-constrained geometry runs the solver every frame. Target: a 200-entity sketch solves in under 5 ms.
- **Degrees of freedom.** The status bar states "3 degrees of freedom remain". Hovering an under-constrained entity shows small arrows for its free directions.
- **Constraint states.** Under-constrained geometry draws in the secondary text color, fully constrained in primary, and conflicting in danger. Each state also has a distinct stroke: dashed endpoints, solid, and a crossed glyph.
- **Conflicts.** A conflicting constraint lists the constraints it conflicts with, and offers "Delete", "Make reference dimension" or "Replace conflicting constraint".
- **Constraint glyphs.** Glyphs (parallel, perpendicular, tangent, coincident, horizontal, vertical, equal, symmetric, concentric, fixed) appear next to entities on hover or selection, or always if the user prefers. Clicking a glyph selects the constraint; Delete removes it.
- **Agent help.** "Constrain fully" asks an agent through `api` for a set of constraints and dimensions. The result appears as an `EditPlan` preview, never as an instant change.

### Snapping and inference

| Inference | Kind | Result in a sketch | Result in 3D |
| --- | --- | --- | --- |
| Endpoint, midpoint, center, quadrant | Point | `coincident` with that point | Placement reference by `Query` |
| Intersection | Point | Two `coincident` constraints | Reference to both entities |
| On edge, on face | Point | `on(entity)` | Point on the face |
| Horizontal, vertical, on axis | Linear | `horizontal`, `vertical` | Axis-aligned delta |
| Parallel, perpendicular to an edge | Linear | `parallel`, `perpendicular` | Direction from that edge |
| Tangent | Linear | `tangent` | — |
| Extension of an edge, alignment with a point | Linear | Construction alignment | Alignment guide |
| Equal length or radius | Value | `equal` | — |
| Value equal to a named parameter | Value | Expression referencing the parameter | Expression |
| Angle increments (15° default) and grid increments | Value | Dimension with that value | Delta with that value |

- **Candidates** come from a 2D R-tree in sketches and the Instance BVH plus cluster bounds in 3D. They are gathered within an 8 px radius for mouse and pen and 16 px for touch, then ranked by priority and distance.
- **Stability.** A 3 px hysteresis keeps a chosen inference from flickering, and at most two inference lines show at once.
- **Display.** Each inference shows a glyph with a distinct shape, a dashed guide line and a short text label ("Midpoint", "Parallel to edge 12"). Color is a secondary cue.
- **Locks.** Shift locks the current inference, and Alt (Option) suppresses all inference, as for every drag. Arrow keys lock axes as in SketchUp: Right for X, Left for Y, Up for Z, Down toggles parallel or perpendicular.
- **Committing.** Every inference committed in a sketch becomes an explicit constraint statement; nothing is inferred silently after the fact.

### Dimensions on the canvas

- **Display.** Selecting a feature shows its driving dimensions in the viewport. Dimension text faces the camera at a constant 12 px size, with leaders placed to avoid overlap.
- **Editing.** Clicking a dimension opens an inline editor that accepts values, units, expressions and tolerances (`4mm ± 0.1mm`, or asymmetric limits). Tab moves to the next dimension, Enter commits, Escape cancels.
- **Binding.** The editor shows what the value is bound to (a literal, a named parameter or an expression), using the same `EditPlan` as dragging.
- **Kinds.** Driven (reference) dimensions show in parentheses and are read-only. Toleranced dimensions show their limits, and GD&T frames attached to faces render as standard feature control frames.

### Assemblies

- **Mates** draw as glyphs between Instances, and selecting one highlights both referenced entities.
- **Degrees of freedom.** Each Instance can show its remaining degrees of freedom as arrows. Dragging an Instance moves it within them, using the assembly solver through `api`, and commits a placement or joint value as an Ingot edit.
- **Motion.** A "Test motion" toggle drags through mechanism motion without committing, with interference highlighted live as red caps where Bodies overlap.

### Undo and redo

- **Scope.** Undo reverts the current user's own changes, newest first. It never reverts another person's or an agent's change.
- **Mechanism.** Undo creates an inverse `repo` change, so history stays append-only. Redo re-applies it. Undoing many steps, copying, then redoing to the present leaves the design unchanged, the principle Figma states for multiplayer undo.
- **Conflicts.** If someone else has since edited the same statement, the user sees the conflict and chooses to keep theirs, revert theirs, or open both in a diff.
- **Granularity.** A drag, a dialog commit or a palette command is one step. Typing in the code panel groups by word or a 500 ms pause.
- **Agent changes** are undone by rejecting or reverting the Proposal, never by an individual's undo stack.

### Live links between source and geometry

The Ingot tab provides a source map: each `EntityId` maps to the operation that created it and that operation's source span.

- **Source to geometry.** Placing the caret in a statement highlights, in the viewport, the entities that statement created (solid tint) and modified (outline). Hovering an identifier such as `web` highlights its Body.
- **Geometry to source.** Selecting an entity reveals its creating statement in the code panel and its feature in the tree. Alt-click jumps the code panel there.
- **Lists of entities.** For `Query` expressions such as `web.edges(joined)`, hover highlights every resolved entity and shows the count. A `ResolveError` shows the expected entities ghosted with the suggested fixes.

**Decision D-UIX-16:** The code panel is a first-class editor in every mode, with bidirectional highlighting through provenance, not a script console. *Why:* the contract's one model, three editors; code-CAD users in the phase 1 wedge live in the source. *Rejected:* an embedded external editor such as Monaco (second text stack, no native build, no shared accessibility); a read-only code view (breaks the three-editor principle).

### Source safety and collaboration in code

- **Hidden characters.** The editor and every source diff render Unicode bidirectional control characters and mixed-script confusable identifiers as visible marked glyphs with a warning. This answers the Trojan Source attacks, CVE-2021-42574 and CVE-2021-42694, which hide logic from reviewers.
- **Collaboration.** Collaborators' carets and selections show in their presence colors with name labels. Edits merge through the `repo` CRDT over the syntax tree, so the panel never shows conflict markers during live editing.
- **Formatting.** Structural edits from manipulation or agents reformat only the edited node and keep comments, so diffs stay minimal.
- **Large files.** The buffer is a rope with incremental re-parsing. Target: keystroke to paint under 8 ms in a 50,000-line file.

## Review

Review is where people judge agent and colleague work. A Proposal opens in Review mode on its saved views, with the evidence the CI report attached.

### The proposal view

| Area | Content |
| --- | --- |
| Header | Title, author (person or agent, with model and permission scope), target branch, state, required approvals |
| Rationale | The Proposal's rationale, linked to the request or issue it answers |
| Evidence | CI report: checks that changed state first, then metric deltas, snapshots, simulation and manufacturing results, each with result status and, for simulations, fidelity mode |
| Diff tabs | Features, Geometry, Metrics, Source, Files (BOM, drawings, manufacturing outputs) |
| Threads | Anchored comments with status |
| Actions | Approve, Request changes, Comment, Check out branch, Ask author (person or agent) |

The Evidence area answers "why should I trust this" before any diff. Checks that turned red appear first, then those that turned green, then metric changes beyond threshold, then everything else.

A reviewer can approve from the summary, but required-approver policies from `repo` can require opening the Geometry tab first. The UI records which tabs were viewed as part of the approval.

### Diffs

- **Feature diff.** Two feature lists aligned by feature identity, following the semantic merge in `repo`. Markers show added, removed, modified (with parameter old → new), reordered and suppression changed. Selecting a row shows the source hunk and both geometries.
- **Geometry overlay.** Three views of the base and target Bodies, over the same camera:
  1. *Overlay*: unchanged faces neutral; faces only in the base in `diff.base`, drawn as translucent ghosts; faces only in the target in `diff.target`, solid. A deviation map colors modified faces by signed distance to the other version, with the diverging map and a legend.
  2. *Side by side*: two linked viewports.
  3. *Swipe*: a draggable divider that reveals one version over the other, like Onshape's compare slider.
- **Face correspondence.** Faces with the same `EntityId` are "same", and `HistoryRecord` split and merge links pair the rest. Without provenance (for example, imported meshes), a geometric distance diff applies and says so.
- **Metrics diff.** A table of mass, volume, center of mass, bounding box, cost, check margins, simulation peaks and manufacturing time. Each row shows base value, target value, delta and percent, with result status and error bound. Rows sort by significance; a delta smaller than the combined error bounds shows "within error" instead of a direction.
- **Source diff.** A structural diff over the syntax tree: moved blocks show as moves, and formatting-only changes are hidden on request. Same invisible-character warnings as the editor.

**Decision D-UIX-17:** Every comparison, in geometry and in source, uses a blue (base) and orange (target) pair, always with a second cue: fill style (ghost versus solid) in the viewport, + and − gutter marks in source, and labels. Onshape uses blue and red for geometry and green and red for code. *Why:* WCAG 1.4.1 (color is never the only means) and the 8% of men with color-vision deficiency, for whom red and green collide. *Rejected:* green and red for added and removed (fails for many of those readers); color alone (fails 1.4.1).

### Comments anchored to geometry

```rust
pub struct CommentAnchor {
    pub at: ChangeId,                    // the change the comment was written against
    pub target: AnchorTarget,
    pub view: ViewState,                 // camera, sections, Field view at comment time
    pub snapshot: CasRef<Image>,         // rendered still frame, for email and mobile
}
pub enum AnchorTarget {
    Entities(Vec<EntityId>),             // faces, edges, Instances
    Point { entity: EntityId, uv: [f64; 2] }, // a point on a face in its parameter space
    Source(SourceSpan),
    Feature(FeatureId),
    Metric(MetricId),
    Region(Box3),                        // free 3D box for "this area"
}
```

- **Re-anchoring.** On every rebuild, anchors re-resolve through `HistoryRecord`s: modified entities keep the anchor, split entities carry it to all pieces, merged entities carry it to the merge result.
- **Lost anchors.** A deleted entity leaves the comment "orphaned", shown at its last position with a ghost of the original geometry. It is never silently attached elsewhere, which mirrors `Query`'s no-silent-substitution rule.
- **Threads.** Threads have states (open, resolved, won't fix) and markdown bodies with quantity rendering, @mentions of people and agents, and links to views. A pin appears in the viewport; clicking it restores the comment's view.
- **Storage.** Comments are `repo` records attached to the Proposal or branch, so `api` Read returns them to agents with resolved anchors.

### Approvals

- **Approve and request changes** are `repo` operations. Approval records the reviewer, the exact change approved and the tabs viewed.
- **Re-review.** Any new change after approval marks the approval "outdated". The re-review shows only the delta since the approval.
- **Signatures.** Release approvals are signed through `repo` using the platform's credential store. The UI states exactly what is being signed: change id, checks, BOM summary.
- **Visibility.** Policies (required reviewers, code owners for packages and subassemblies, release gates) come from `repo` and show as a checklist in the header.

## Agent interaction

Agents work only on branches through `api` (contract section 7). The UI makes their work visible, steerable and reviewable, and gives people the same commands agents use.

### Command palette

- **Opening.** Ctrl+K or Cmd+K opens the palette, and F1 also opens it.
- **Content.** One list mixes commands, features from std and installed packages, entities (by name or `Query`), files, branches, Proposals, settings, help topics and agent requests.
- **Ranking.** Fuzzy search ranks by match quality, recent use and the current mode. Each row shows its keyboard shortcut.
- **Arguments.** Commands with arguments open an inline form in the palette (for example "fillet → select edges → radius"), so keyboard users never leave it.
- **Natural language.** A query that matches no command, or starts with `>`, goes to the default agent as a request. The palette states this before sending.
- **One registry.** Palette, menus, toolbars, keymaps and context menus all derive from one command registry, so no command exists in only one place.

### Agent panel

The agent panel holds conversations with agents. A conversation targets a branch (an existing one, or a new branch created on start) and has a visible permission scope and cost cap.

| Element | Behavior |
| --- | --- |
| Request input | Text with attachments: current selection (as `Query`), saved views, comments, files, sketches drawn on screen |
| Scope chip | Permissions (read only, edit branch, run studies, propose), cost cap and time limit; editable before start |
| Plan | The agent's plan as a checklist; each step expands to its `api` calls |
| Activity timeline | Live list of actions: edits (with mini diffs), builds, checks, studies, snapshots, questions |
| Live view | "Follow agent" makes the viewport show the agent's branch and focus, like following a person |
| Budget meter | Spend versus cap in tokens, compute and money, with forecast to completion |
| Controls | Pause, Resume, Stop, Steer, Fork, Take over |

**Decision D-UIX-18:** Agent activity is shown at the level of `api` calls and `repo` changes, always on the agent's own branch, and any agent action can be inspected, replayed or reverted like a person's. *Why:* trust comes from seeing real actions, not narrated summaries, and the contract confines agents to branches. *Rejected:* chat-only output (no evidence); agents editing the user's working branch in place (unreviewable; collides with the person's edits).

### Steering mid-task

- **Steer.** A message sent while an agent runs is delivered at its next step boundary as a priority instruction. The timeline marks where it arrived.
- **Pause.** Pause stops after the current `api` call completes. Kiln cancels in-flight evaluations, so no half-applied edit exists.
- **Rewind.** Selecting a timeline entry and choosing "Continue from here" forks a new branch at that change with new instructions. The original branch stays for comparison.
- **Pinning.** People can pin parameters or regions ("do not change mounting holes"). Pins become Ingot `require` checks added to the branch, so a violation fails the build instead of relying on the agent's memory.
- **Take over.** Take over checks out the agent's branch in the user's workspace and pauses the agent. "Hand back" resumes it with a note describing the user's changes.
- **Questions.** Agents ask through a structured question card (choices, value fields, select-in-viewport). The answer goes back as typed data, and pending questions appear in notifications.

### Approving and rejecting

- **Proposal gate.** Agents propose only after building, passing every check and attaching snapshots (contract section 7). A proposal that arrives in Review therefore already has evidence.
- **Reject** requires a reason. The reason is stored on the Proposal and given to the agent, so it can learn within the task.
- **Partial accept.** A reviewer can cherry-pick features from the feature diff into a new Proposal. The UI previews the result and runs checks before offering approval.
- **Sensitive actions.** Actions that leave the branch (release, external purchase, sending files to a vendor) always need explicit human confirmation through the platform's secure dialog, whatever the agent's scope.

### Variants side by side

Agents and people often explore several designs: parameter sweeps, optimization results, or alternatives from several agents.

- **Variant set.** A variant set is a list of branches or parameter assignments with shared metrics, created by an agent or by "Explore variants" on any parameter.
- **Grid view.** Up to 16 linked viewports (4×4) share one camera, each labelled with its key parameters and metrics. Display packages are shared where Bodies are identical, so the grid costs little more than one view on G1.
- **Table and chart.** A sortable table of variants by metric and a scatter plot of any two metrics with the Pareto front highlighted. Parallel coordinates serve more than two objectives.
- **Selection** in any view highlights the same variant in all views.
- **Pick and continue.** "Promote" turns a variant into a Proposal; "Merge features from" brings features from one variant into another via the semantic merge.
- **Large sets.** Sets over 16 variants show as a paged grid of still thumbnails rendered from saved views, with live rendering only for the focused page.

## Simulation, manufacturing and cost

### Study setup by selection

A study is Ingot source (Flux owns its language and semantics). The UI builds it by selection and generates the source.

1. **Choose a study type** from the palette or Simulate toolbar: static structural, modal, thermal, coupled, flow and others that Flux provides. Templates come from std.
2. **Select faces, edges or Bodies, then choose a boundary condition**: fixed, displacement, force, pressure, bearing load, bolt preload, temperature, heat flux, convection, inlet, outlet, wall and so on. Each becomes a statement with a `Query` and typed quantities, such as `pressure(part.face(inner), 2.5MPa)`.
3. **Glyphs.** Boundary conditions render as glyphs scaled to the view with value labels: arrows for forces, hatching for fixed supports, and colored sheets for pressure and temperature. Distributed loads show their distribution on hover.
4. **Materials.** Unassigned Bodies are flagged; assignment uses the Material library browser with property curves and provenance.
5. **Contacts** are detected automatically and listed for confirmation, never applied silently.
6. **Pre-flight.** Flux reports missing constraints (rigid-body modes), unit inconsistencies and envelope warnings before running. Each item has a fix.

### Running and exploring results

- **Fidelity choice.** Each run chooses interactive (approximate, with error estimate) or sign-off fidelity, as Flux defines. The run header always shows which.
- **Interactive studies** re-run automatically after edits. Results stream coarse-first with a progress bar and a convergence plot. Contract target: interactive update under 1 s.
- **Sign-off runs** are queued as Kiln evaluations, locally or on team or cloud workers through `api`. They show queue position, estimated time and cost, and notify on completion.
- **Results panel.** The Field and derived-quantity selectors, the Field view controls specified earlier, probes, the extremes list, envelope warnings, and checks with margins. For example, "peak_stress < 0.6 × yield: margin 18% ± 4%" links to the location and the Field.
- **Error indicators.** Flux's error estimate shows as a number on every probe and as an optional overlay. When the estimated error exceeds the margin of any check, the check shows "inconclusive" instead of pass. The user is offered refinement or sign-off fidelity.
- **Comparison.** Two runs or two Proposals' results compare with a difference Field on matched geometry, using the diverging map.

### Toolpath preview and playback

Manufacturing data comes from the manufacturing subsystem (MFG) through `api`. The UI draws it:

| Element | Rendering |
| --- | --- |
| Toolpaths | Polylines colored by move type (cutting, linking, rapid, plunge) using distinct dash patterns and colors; optional coloring by feed rate or engagement with batlow |
| Tool and holder | Mesh models of the tool, holder and machine kinematics from MFG |
| Stock | Material-removal simulation result as a Body updated during playback |
| Collisions and gouges | Marked at the time and place they occur, listed in a table, each linking to the operation |
| Additive | Layer slider; per-layer paths, supports and overhang analysis Field |

- **Playback** has play, pause, speed (0.1× to 100×), scrub by time or by operation, and step by move. The timeline shows operations and tool changes in parallel lanes.
- **Stock updates.** In-process stock comes from MFG's material-removal simulation, sampled at key frames and interpolated for display. The interpolation is labelled "display" and only the MFG result is cited in checks.
- **Machine time** and the cycle-time breakdown show beside the timeline and update with toolpath edits.

### Cost panels

- **Content.** The cost panel shows unit cost at chosen quantities, with a breakdown by Part, process (machining time, material, setup, finishing, purchased Catalog parts) and source. Each line has its assumptions and an uncertainty range.
- **Live.** Cost recomputes with design edits. Changes show as deltas with the edit that caused them ("fillet radius 2 → 3 mm: machining −$0.42").
- **Quantity curves** plot unit cost against volume per process, so crossovers between machining, molding and printing are visible.
- **Supplier quotes** obtained through MFG replace estimates and are labelled as quotes with their date.
- **Checks.** Cost targets are Ingot checks, so they show in the check list and in review deltas like any other check.

### Drawings and model-based definition

The mechanical tab owns drawing standards (ISO and ASME rules); UIX owns the editors.

- **Model-based definition first.** GD&T and other product manufacturing information attach to faces as typed properties (contract section 5). The viewport shows them on annotation planes, filtered by saved view, and STEP AP242 carries them out.
- **Drawings are source.** A drawing is an Ingot file of sheets, views and annotations. Each view is a `ViewState` with projection, scale and section; each dimension references entities by `Query`.
- **Sheet editor.** A 2D sheet canvas on the same toolkit and renderer shows exact hidden-line views from Anvil. Views are placed by drag or by typed position; dimensions by selecting edges or vertices. Each placement is an Ingot edit with an undo step.
- **Automatic dimensioning** runs as an agent request and arrives as an `EditPlan` preview.
- **Dangling references.** A dimension whose `Query` no longer resolves shows in the danger style with its `ResolveError` and fixes. It is never re-attached silently.
- **Output.** PDF, SVG and DXF export go through the `io/` crates.
- **Phases.** 3D PMI display and a basic drawing for golden product 1 in phase 1; the full sheet editor in phase 2.

## Collaboration

### Presence

Live collaboration on source uses the `repo` CRDT over the syntax tree. Presence is ephemeral and separate from the document, as in Loro's ephemeral store: a timestamped last-writer-wins key-value map per peer with a 30 s default timeout.

```rust
pub struct Presence {
    pub who: Principal,                  // person or agent identity from api, with display name and color slot
    pub branch: BranchId,
    pub mode: Mode,
    pub camera: Option<Camera>,          // for follow mode; sent at most 10 times per second
    pub pointer: Option<PointerRay>,     // viewport cursor as a ray, so others see it in their own view
    pub selection: Vec<EntityId>,
    pub code: Option<(FileId, SelectionRange)>,
    pub activity: Activity,              // idle, sketching "profile", running study "static_1", ...
}
```

- **Avatars** in the top bar show who is on this design and branch. Agents appear with an agent badge and their task.
- **Live cursors.** Remote cursors draw in the viewport as small labelled 3D pointers, and their selections as outlined faces in the person's presence color. Cursor updates are interpolated over 100 ms so motion is smooth at low update rates. Code panel carets work the same way.
- **Activity.** A person's current tool and target show in their avatar tooltip and as a subtle label in the tree ("Ana is editing `rib`").
- **Edits in flight.** A remote edit shows its coarse preview to others as it happens, with the author's color outline, so nobody is surprised by a jump.

**Decision D-UIX-19:** Presence colors come from a six-color categorical set per theme, chosen to stay distinct under protan, deutan and tritan simulation (Machado, Oliveira and Fernandes 2009). Every color pairs with initials and a name label, never color alone. *Why:* WCAG 1.4.1; a preliminary screen found six colors that keep a minimum pairwise Oklab distance of about 0.07 under all three simulations, while the best eight-color set fell to about 0.03. The screen used matrices recalled from the paper and is repeated with its Table 1 before release [unverified]. Beyond six people, colors repeat and labels carry identity. *Rejected:* hashing user ids to arbitrary hues (collisions, unreadable pairs); eight or more colors (pairs collapse under color-vision deficiency).

### Follow mode

Clicking an avatar follows that person or agent. The viewport mirrors their camera and mode, the code panel mirrors their file and scroll, and a colored frame plus "Following Ana" shows around the workspace; any local navigation stops following. Followers of a presenter can be gathered with "Ask everyone to follow me", which each person accepts.

### Notifications

- **Sources.** Mentions, review requests, approvals, check failures on watched branches, agent questions, agent completions, study completions and release events.
- **Center.** A notification center in the top bar groups items by design repository. Each item deep-links to its exact view.
- **Delivery.** OS notifications go through the platform layer, and email digests are optional. Per-project settings choose which events notify.
- **Urgency.** Only agent questions blocking a running task and failed release checks are urgent. Nothing else interrupts.

### Concurrent edits to the same geometry

The CRDT merges source edits, and the UI makes the consequences visible:

- **Same literal.** The `repo` CRDT must treat each literal as an atomic value, so concurrent edits never interleave characters ("4" edited to "6" and to "8" never becomes "68"). The later edit wins, as in Figma's last-writer-wins property rule, and the earlier author sees a toast with the competing value and a one-click restore.
- **Breaking merges.** When a merged edit breaks a build, the failing feature shows both authors and both changes, with fix actions.
- **Locks.** People can lock a feature or subassembly for a time ("Ana is reworking the gearbox housing until 14:00"). Locks are advisory and visible, and agents respect them by policy.

### Offline and reconnection

When the connection drops, the workspace keeps working against the local `repo` replica and CAS, and the status bar shows "Offline: changes saved locally". On reconnection, local changes sync through the CRDT. Any build or check that changes state because of merged remote work produces a single summary notification.

## Input

### Mouse, trackpad and keyboard

- **Navigation.** Orbit, pan and zoom bindings come from the active preset. Zoom goes toward the cursor; orbit pivots on the surface point under the cursor at gesture start, shown with a small pivot marker.
- **Trackpads.** Two-finger scroll pans, pinch zooms, and Shift plus two-finger scroll orbits, all with pixel-precise deltas from the platform layer.
- **View cube.** A view cube in the viewport corner offers named views (top, front, iso), with keys for each.
- **Fit.** "Fit selection" (F) and "Fit all" (Shift+F, or double middle click) frame the target.
- **Clicks.** Single click selects, and Shift or Ctrl click adds or toggles. Double click selects the feature that made the entity. Right click opens a context menu built from the command registry; in presets that orbit with the right button, a drag beyond 4 px orbits instead.

### Keymaps

Keymaps map key chords and pointer gestures to commands in the command registry. A keymap is a TOML file; user keymaps layer over a preset.

```toml
# keymap: user overrides on top of a preset
preset = "fusion"

[[binding]]
keys = "Ctrl+Shift+E"
command = "feature.insert"
args = { feature = "std::mech::extrude" }
when = "mode == design && !text_focus"

[[pointer]]
gesture = "drag(middle)"
modifiers = ["Shift"]
action = "camera.orbit"
```

| Preset | Orbit | Pan | Zoom | Notes |
| --- | --- | --- | --- | --- |
| Crucible (default) | Right drag | Middle drag | Wheel | Left drag stays free for selection and box select |
| SOLIDWORKS-like | Middle drag [unverified] | Ctrl + middle drag [unverified] | Wheel | Zoom direction configurable |
| Fusion-like | Shift + middle drag | Middle drag | Wheel | Double middle click fits all |
| Onshape-like | Right drag [unverified] | Ctrl + right drag [unverified] | Wheel | |
| Blender-like | Middle drag [unverified] | Shift + middle drag [unverified] | Wheel | Numpad views |

The Fusion bindings follow Autodesk's published defaults. The other presets need verification against each product's current defaults before release; the oracle compares each preset with a reference table maintained by people who use those tools daily.

- **Context.** `when` clauses use a small, documented context language (mode, focus region, selection kind, text focus).
- **Conflicts.** The keymap editor shows conflicting bindings and offers resolution.
- **Character keys.** Single-character shortcuts follow WCAG 2.1.4: they act only when the viewport or tree has focus, and a setting turns them off or remaps them.
- **Layouts and platforms.** Shortcuts bind to logical keys by default (so `Ctrl+Z` follows the layout's Z), with an option for physical-key bindings for game-style navigation. Primary-modifier chords map Ctrl to Cmd on macOS.

**Decision D-UIX-20:** Navigation and key presets imitate SOLIDWORKS, Fusion, Onshape and Blender, but command names, the palette and menus stay Crucible's own. *Why:* muscle memory for navigation is the main switching cost; vocabulary must stay coherent (one name per concept). *Rejected:* full UI skins of other products (trade dress risk, incoherent vocabulary); no presets (needless switching friction).

### 3D mice

- **Native.** On Windows and macOS, Crucible integrates the 3Dconnexion driver's navigation interface through the platform layer [unverified: exact SDK name and licensing]. On Linux it reads the device through the open `spacenavd` daemon [unverified].
- **Browser.** In Chromium browsers, WebHID reads six-axis HID reports directly after the user grants access. WebHID is experimental and not Baseline, and Firefox and Safari lack it [unverified], so those browsers show a notice offering the desktop app for 3D mouse use.
- **Navigation model.** Six-axis input drives the camera in object mode (the model moves) or camera mode (fly-through for large assemblies), with dominant-axis and speed settings. The pivot rules match the mouse. Device buttons bind to commands through the keymap.

### Pen and touch

- **Pen.** Pressure and tilt reach sketch tools. Pen hover shows inference before contact, and the barrel button maps to a command, by default orbit while held. Palm rejection uses the platform's pen and touch arbitration.
- **Touch gestures.** One finger selects or drags handles. Two fingers pan, pinch zooms, twist rolls. Two-finger tap undoes and three-finger tap redoes, both with a visible toast and an undo button for discoverability.
- **Touch targets.** Touch layouts give targets at least 44 px, with the pick radius at 12 px and the snap radius at 16 px. The transform gizmo grows to 140 px.
- **Large-touch layout.** Tablets get a radial tool menu at the pen or finger position and a bottom-sheet properties panel.
- **Single-pointer alternatives.** Every drag has a non-drag path: tap a handle, then type a value or use plus and minus steppers. This meets WCAG 2.5.7.

### Keyboard operation

Every pointer action has a keyboard path. With the viewport focused:

| Action | Keys |
| --- | --- |
| Orbit in 15° steps | Ctrl+Arrow (Cmd+Arrow on macOS) |
| Pan by 5% of the view | Shift+Arrow |
| Zoom in and out | Plus and Minus |
| Named views and fit | Number keys 1 to 7 for named views, F to fit selection |
| Move selection to an adjacent entity | Arrow keys |
| Select owning feature or Instance; enter it | Alt+Up; Alt+Down |
| Select by query | Ctrl+K, then type a `Query` such as `faces(cylindrical, radius < 5mm)` |
| Cycle the active tool's handles | Tab and Shift+Tab |
| Nudge the focused handle by one increment | Arrow keys while the handle has focus |
| Set the focused handle exactly | Type a value or expression, then Enter |

- **Sketching by keyboard.** Points and lengths are typed in the measurement field: absolute coordinates `[40mm, 20mm]` and relative `<15mm, 0>`, following SketchUp's bracket convention. Constraints apply to the selection from the palette.
- **Focus.** The focused handle shows the focus ring, and its value is announced. Escape leaves the active tool, and a second Escape returns focus to the region.
- **Drawing tools.** While a drawing tool is active, arrow keys lock inference axes instead (see Snapping and inference).

### Screen-reader access to the model

- **Tree.** The model tree is a tree role with level, position, expanded state, type, status and dimensions in the description. For example: "Feature rib, 3 of 7, modified by Ana, check failed: peak_stress margin −4%".
- **Viewport.** The viewport is a focusable region whose accessible children mirror the current selection and its neighbors: the selected entity, its owning feature, adjacent faces and the Instance. Each has a spoken description from Anvil measures ("planar face, 40 by 60 mm, normal +Z, on part bracket, created by extrude base").
- **Keyboard navigation of geometry.** Arrow keys move selection between adjacent faces. Alt+Up selects the owning feature or Instance, and Alt+Down enters it. Each move announces the new entity and keeps it in view, which also serves keyboard-only users who can see.
- **Describe view.** A command speaks the visible content: Parts, the active section, the Field view summary (range, extremes and their locations), and check states.
- **Code.** The code editor exposes text with caret and selection, line numbers, diagnostics as annotations, and inlay values as separate announcements on request, so users are not flooded.
- **Fields.** The probe has a keyboard mode: arrows walk a grid of probe points across the selected face, announcing value and error. "Jump to maximum" and "Jump to minimum" exist as commands.

**Decision D-UIX-21:** The 3D viewport is screen-reader operable through a structural model (selection, adjacency, owning feature and Instance) rather than through pixels. *Why:* CAD geometry has meaning in topology and features, which can be spoken and navigated; no accessibility API can describe pixels usefully. *Rejected:* marking the viewport as a decorative image (excludes blind engineers and reviewers from geometry work).

### Motion and sensory settings

- **Reduced motion** follows the OS setting and an in-app override. Camera transitions cut, panel animations become cross-fades of 100 ms or less, mode-shape animation becomes a static peak with a slider, and the progress shimmer becomes a static bar. Every essential animation (toolpath playback, transient results) has explicit play controls and never autoplays.
- **High contrast.** A high-contrast theme raises text contrast to at least 7:1 and non-text contrast to at least 4.5:1. On Windows, forced-colors mode maps the tokens to system colors.
- **Color-vision checks.** A "Simulate color vision" view applies Machado et al.'s matrices for protan, deutan and tritan deficiency, at a chosen severity, to the whole window. Designers use it to check their own Material colors and annotations.
- **Captions.** Tutorial videos and voice comments carry captions or transcripts.

## Localization and units

### Strings and formatting

- **Messages** use Project Fluent through `fluent-rs`. Fluent lets translations be more expressive than the source and handles CLDR plurals, gender and grammatical case per locale.
- **Formatting.** ICU4X formats numbers, dates, lists and relative times and handles collation and segmentation.
- **Hard-coded strings** fail lint: every string in `apps/` goes through a message id.
- **Source of truth.** English messages are the source. Translations live in the repository and pass CI checks for missing arguments and invalid selectors.
- **Pseudo-localization.** Pseudo-locales run on every pull request: one expands strings by 40% with accented characters, one uses right-to-left pseudo text. Both run the snapshot and layout suites.

### Right-to-left scripts

- **Layout.** All toolkit layout uses logical start and end, never left and right. In Arabic and Hebrew the panel order, alignment, tree indentation, breadcrumb and directional icons mirror.
- **Not mirrored.** The viewport, the view cube, axis labels, charts' numeric axes and the transform gizmo keep their geometric orientation, since 3D space has no reading direction.
- **Mixed text.** Ingot code stays left to right. RTL comments and strings render with bidi isolation, and quantities like "4 mm" are isolated so they never reorder in RTL sentences.

### Unit display preferences

- **Per-kind units.** Each user picks display units per quantity kind, such as length (mm, cm, m, in, ft-in), angle (deg, rad), force (N, kN, lbf), stress (MPa, psi, ksi) and temperature (°C, K, °F). Presets cover SI-mm, SI-m, US-inch and US-feet-inch, and display units never change the model.
- **Entering values.** A value typed into a field is written into the source exactly as typed, with its unit (`1.5in`). This avoids rounding from conversion. A repository can declare preferred units; mixed units then raise a lint warning with a convert fix.
- **Decimal separators.** Display follows the locale (4,5 mm in German). Fields accept the locale separator and the period. Ingot source always uses the period.
- **Precision.** Display precision is per unit (default 2 decimals for mm, 3 for in, 1 for deg). Toleranced values always show enough digits to express the tolerance. Negative zero shows as 0.
- **Dual units.** An option shows values in two units, such as "40 mm [1.575 in]".
- **Very small or large values** use SI prefixes where conventional (µm, GPa) and otherwise scientific notation with a superscript exponent.

### Browser specifics

- **Startup.** The Wasm app streams and compiles while the shell paints a skeleton workspace from the last session. Targets: interactive in 3 s on a warm HTTP cache and 6 s cold on a 50 Mbit/s link, with a Wasm payload under 20 MB compressed.
- **Storage.** The local CAS cache and `repo` replica live in the origin private file system (OPFS), widely available since March 2023. Workers use its synchronous access handles. Storage quota is shown in settings, and the app warns before eviction risk.
- **Offline.** A service worker caches the app shell. "Make available offline" pins a design's replica and display packages in OPFS.
- **Threads.** Wasm threads need shared memory, which requires cross-origin isolation headers on the hosting origin [unverified: current browser requirements]. The platform layer serves them; the single-threaded fallback is slower but complete.
- **GPU selection.** WebGPU adapters with `core-features-and-limits` run G2. Compatibility-mode adapters (WebGPU over OpenGL ES 3.1, from Chrome 146) run G3 like WebGL2, because the G2 vertex path needs vertex-stage storage buffers, which only `core-features-and-limits` guarantees. On G2 the page pool is split into bindings of at most 128 MiB, the default `maxStorageBufferBindingSize`, unless the adapter grants more.

### Offline behavior on every platform

- **Native** works fully offline: the local `repo` replica, CAS and evaluation need no network, and air-gapped installs work (contract section 9).
- **Agents** that run remotely are unavailable offline. The agent panel says so and offers local agents if an organization has configured them.
- **Sync status** is always in the status bar: online, syncing (with count), offline, or conflict needing attention.

## Onboarding and migration

### First run

The first run asks four questions, each skippable and changeable later: role (design, simulation, manufacturing, review), navigation preset, unit system and theme. It then opens a template design, not an empty screen. Empty panels always show the next useful action and its shortcut.

### Templates

Templates are design repositories published as packages: Ingot source, checks, saved views and a short guided tour. The first set mirrors the golden products, which are fully specified and verified: machined bracket, lattice bracket, gearbox, welded frame with guards, molded enclosure with PCB, and drone. "New from template" creates a branch-ready design repository.

### Interactive tutorials

- **Packaging.** A tutorial is a package of steps. Each step has instructions, an optional UI pointer (by command id or region, never by pixel position) and a completion predicate. The predicate is evaluated through `api`, for example "the Part has a 2 mm fillet on the joined web edges".
- **Any path counts.** Because completion is checked on the model, learners may complete a step with the GUI, the code panel or an agent.
- **Accessibility.** Steps are announced to screen readers and keyboard-operable, and pointers never cover the target (WCAG 2.4.11).
- **Verification.** Each tutorial ships a scripted solution that CI runs on every release, so tutorials never rot.

### Migration from other CAD tools

- **Navigation and keys.** Presets for SOLIDWORKS, Fusion, Onshape and Blender users.
- **Vocabulary.** The command registry carries synonyms per preset. Typing "Boss-Extrude" or "Press Pull" in the palette finds `extrude` or push-pull and shows "In Crucible: extrude".
- **Data.** STEP AP242 import with PMI, plus proprietary formats through licensed translator plugins (contract section 7). An imported Body arrives as a Part with a direct-edit history.
- **Feature recognition.** Rebuilding imported solids as Ingot features runs as an agent task. The result arrives as a Proposal, reviewed with the geometry overlay against the import, so the reconstruction is checked rather than trusted.
- **Concept guide.** A built-in guide maps familiar concepts to Crucible's (configurations to parameters and variant sets, design tables to parameter files, PDM check-in to `repo` changes).

### Telemetry

**Decision D-UIX-22:** Telemetry is off until the user opts in; the payload schema is public; organizations can force it off; air-gapped builds exclude the sender at compile time. *Why:* engineering data is confidential, and trust depends on verifiable restraint. *Rejected:* opt-out telemetry (consent by default is not consent); collecting model content for product improvement (unacceptable confidentiality risk).

- **What may be sent.** Frame-time histograms per GPU tier and adapter class, interaction latencies, command ids with counts, typed error codes, crash signatures and settings choices.
- **What is never sent.** Source, geometry, names, file paths, comments, parameter values or prompts.
- **Inspection.** A telemetry inspector in settings shows every payload before it is sent, and a CI oracle scans payloads for forbidden content.
- **Retention.** Raw events are kept 90 days; aggregates are kept longer.

### Crash and error reporting

- **Capture.** The platform layer captures native crash dumps. Rust panics and Wasm traps install a hook that records the build id, GPU adapter and driver, recent command ids and recent `api` call names. Values and content are never recorded.
- **Consent.** Reports are sent only with consent, per crash or by setting.
- **Reproduction bundles.** For reproducible bugs, the user can attach a bundle: branch, `api` call log and `ViewState`. The user previews it before sending. The bundle replays deterministically because evaluation is deterministic (contract principle 4).
- **Recovery.** After a crash, the workspace restores the last `ViewState`, open panels and unsent comment drafts. Model state is never lost, since every committed gesture is already a `repo` change.

## Extending the interface

Contract principle 1 (no privileged code) applies to the interface. Domain views from other tabs, such as the electronics board view or the sheet-metal flat pattern, use the same extension points as any third-party package.

| Extension point | Form | Example |
| --- | --- | --- |
| Feature dialogs and handles | Ingot `Feature` metadata | A gear feature declares a module field and a radial handle for the pitch diameter |
| Commands | Registry entries that map to `api` calls, with names, synonyms and default keys | "Add fastener stack" |
| Study and boundary-condition templates | Ingot packages with UI metadata | A bolt preload template |
| Visualizations | A Field plus a `VisualizationSpec` | Draft-angle analysis as a Field painted with a diverging map |
| Panels | Wasm component exporting `crucible:ui/panel` | Electronics layer stack, nesting layout, harness table |
| Themes, keymaps, templates, tutorials | Data files in packages | A company theme; a training course |

Panel Wasm components return element trees in the toolkit's vocabulary: stacks, grids, text, fields, tables, charts, trees and viewport overlays (lines, labels, glyphs, faces highlighted by `Query`). They never draw pixels or ship shaders.

```wit
package crucible:ui@0.1.0;

interface panel {
    use types.{element, ui-event, command-call};
    /// Rebuild this panel's element tree from data the panel read through the API.
    render: func() -> element;
    /// React to an event; returned calls go through the command registry and api.
    handle: func(event: ui-event) -> list<command-call>;
}

world ui-panel {
    import crucible:api/read;   // always granted, scoped to the open design repository
    import crucible:api/edit;   // only when the user grants it to this package
    export panel;
}
```

- **Sandbox.** Panel Wasm components run in the sandbox with no files, network or clock. They reach data only through `api` under the scopes the user granted.
- **Budget.** Each panel gets 2 ms of CPU per frame. A panel that exceeds it three frames in a row is paused with a notice and a resume button.
- **What the host provides.** Because panels return elements, the toolkit supplies accessibility, theming, localization (panels ship Fluent messages), keyboard operation and identical behavior on every platform.
- **Cross-probing.** Selection is one set of `EntityId`s for the whole workspace. Any panel showing an entity highlights it, so selecting a chip on the board view selects it in 3D and in the tree with no extra work.

**Decision D-UIX-23:** The interface is extended only through declarative data and sandboxed Wasm component panels that return toolkit elements; built-in domain panels use the same mechanism; no extension draws pixels or ships shaders. *Why:* no privileged code, plus accessibility, theming, localization and platform parity for every panel. *Rejected:* native plugin libraries (unsafe, per-OS, impossible on the web); webview panels (second runtime, inconsistent accessibility); custom shaders (portability across GPU tiers and security review cost; custom looks come from Fields instead).

## Platform notes

- **Windows 11 x86-64.** wgpu uses DX12 by default, with Vulkan as an alternative, and G1 needs Shader Model 6.6 for 64-bit atomics. Text and accessibility go through AccessKit's UI Automation adapter. Windows forced-colors mode maps to tokens.
- **Windows 11 ARM64.** The native app runs DX12. Chrome keeps WebGPU behind a flag on Windows ARM64, so browser users there get G3 (WebGL2) unless they enable it. The status bar's graphics popover explains this and offers the desktop app.
- **macOS on Apple silicon.** On the Metal backend, wgpu enables 64-bit texture atomics only from MSL 3.1, and some older Apple GPUs may lack 64-bit atomic min and max [unverified]. Those Macs run G1 without compute rasterization. wgpu offers indirect-count draws only on DX12 and Vulkan, so every compute tier uses single indirect draws.
- **macOS display and menus.** Display P3 output is the default, ProMotion displays get 120 Hz interface frames, and the global menu bar is generated from the command registry.
- **Linux x86-64 and ARM64.** Vulkan backend; Wayland and X11 through the platform layer, including fractional scaling. Accessibility goes through AT-SPI, and IME support depends on the platform layer's integration with IBus and Fcitx [unverified]. Mesa lavapipe serves the CPU path in CI and on machines without working drivers.
- **Browsers.** WebGPU is on by default in Chrome and Edge on Windows, macOS and ChromeOS (since 113) and in Safari 26. Firefox enables it on Windows (since 141) and on Apple silicon Macs (since 147, or 145 on macOS 26). On Linux, Chrome enables WebGPU only for Intel Gen12+ and for NVIDIA on Wayland, and Firefox has not shipped it, so many Linux browser users run G3.
- **Browser APIs.** EditContext and WebHID are not Baseline, so both have fallbacks or notices. OPFS is widely available, and bundled fonts avoid browser font-access restrictions while keeping metrics identical.
- **Tablets and phones.** iPadOS runs Safari 26 WebGPU or a native shell if the Platform tab provides one. Android Chrome has WebGPU on Qualcomm, ARM and Intel GPUs from Android 12. Mobile GPUs lose devices more often under memory pressure, so device-loss recovery is tested on Tier 2 hardware every release.
- **HDR and wide gamut.** wgpu 30 supports surface color spaces per backend. Metal has the widest range; GLES supports sRGB only. Engineering styles stay SDR on every platform so colors match across displays.
- **CJK fonts.** Noto CJK families are large, so the browser build downloads them on first use of those scripts and caches them in OPFS. The native build bundles them.
- **Tier 3 (FreeBSD and other Unix systems).** Community builds use wgpu on Vulkan and AccessKit's AT-SPI adapter; no CI or support commitment.
- **Identical behavior.** The toolkit, text stack, fonts and renderer are the same code everywhere. Platform-specific behavior is limited to the shortcut modifier (Cmd on macOS), text-navigation chords, the menu bar location and native dialogs, each listed in one platform conventions table owned with the Platform tab.

## Open questions

1. **Own toolkit cost.** Building and maintaining the toolkit is a multi-year commitment. Should Crucible instead fund Masonry upstream and adopt it once its layout and rendering abstractions settle? Decide at the phase 1 gate after a two-week spike on both.
2. **Mesh shaders.** Do mesh shaders on Vulkan, DX12 and Metal beat compute culling plus indirect draws by the 15% threshold on CAD scenes? A phase 2 benchmark decides.
3. **Field evaluators.** Can Flux emit WGSL evaluators for every discretization it uses (isogeometric, immersed, high-order), or only some? The answer sets how often the vertex-sample fallback applies.
4. **Web 64-bit atomics.** When `atomic-vec2u-min-max` reaches stable browsers, does G2 reach G1 capacity? Track per browser.
5. **3D mouse SDK.** The licensing and redistribution terms of the vendor navigation SDK need legal review, along with the Linux and browser paths.
6. **Navigation presets.** Exact current default bindings of SOLIDWORKS, Onshape, NX and Blender need confirmation by expert users; trade-dress review applies to preset names.
7. **Usability thresholds.** Are 90% task success and System Usability Scale 75 the right phase gates for professional CAD users, who start with strong habits from other tools?
8. **visionOS.** Should Crucible build a native visionOS shell, or rely on WebXR in Safari?
9. **Saved view location.** Should saved views and dashboards live in the design repository, as proposed, or in a separate metadata store so they do not create changes? `repo` decides.

## Contract change requests

1. **Add `ResultStatus` to the core types (section 5).** Every subsystem that streams results (Kiln, Anvil, Flux, MFG) and every consumer (UI, agents, CI) needs one shared type for proxy, coarse with `ErrorBound`, exact, stale and failed. Without it, each subsystem invents its own status labels; it is distinct from Flux's fidelity modes, which describe how a simulation was configured.
2. **Clarify "WebGL2 fallback" in section 7 and "identical features" in section 9.** WebGL2 has no compute shaders. Every feature still works there, but capacity and refinement speed differ by declared GPU tier (D-UIX-6). The contract should state that parity means identical features and results, with capacity tiers published per platform.
3. **Name the display data contract.** The overview says "engine ships changed triangles". The contract should name `DisplayPackage` (cluster DAG pages with chordal error, cached in CAS) as the cross-subsystem type, owned jointly by Anvil and UIX.
4. **Add `ViewState` to the core types.** Agents, review, comments, dashboards and snapshots all reference camera, visibility, sections and Field views. One type prevents parallel "view" abstractions in the `api` and agent tabs.
