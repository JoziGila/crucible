# UI and interaction (UIX)

Crucible's interface is a GPU-rendered view of one typed Ingot program, and it changes the product only through `api`. One Rust toolkit and one wgpu renderer give every Tier 1 platform the same features on three declared GPU tiers, with a forward renderer in phase 1 and virtualized geometry from phase 2. Every result shows its status and error, review puts evidence before diffs, and agents work visibly on their own branches.

## Workspace and information architecture

**Decision D-UIX-1:** The UI holds no product state of its own. Every product-changing action is an `api` Edit or Propose call that changes Ingot source or `repo` records; per-user presentation state lives in `ViewState`, and shared views are repository files. *Why:* contract principle 2 (one model, three editors) and agent parity: anything a person does, an agent can do, inspect and replay. *Rejected:* GUI-side feature records synchronized to code (two sources of truth); camera and visibility in the model (noisy diffs and merges).

Every command records its `api` call, and "Copy as `api` call" hands any manual step to an agent or a script. The top bar shows the label of the open design (level, controls and scopes), and every snapshot and export carries it.

### Model tree, dialogs and version history

The tree unifies structure and history: Assembly, Instances, Part, feature list, features, and on demand the entities each feature created. Top-level nodes add Parameters, Studies, Manufacturing setups, Checks, Saved views and Packages.

- **Rows** show type, name, status glyph, Instance count and presence, never relying on color alone. The tree is virtualized to 1,000,000 nodes and filters by name, type, status or a typed `Query`.
- **Edits.** Rename writes `#[was(old_name)]`, so `OpSite`s survive. Delete previews dependents, and reorder refuses illegal moves with the reason ("`web` uses `base`, defined on line 4").
- **Rollback marker.** Dragging it shows the Part as evaluated up to a feature, and edits made there insert at that position.

The *feature list* orders program statements; the *version history* orders Changes in time. The UI never calls both "history".

Feature dialogs are generated from Ingot `Feature` metadata. They hold typed fields with units and ranges, `Tol<T>` inputs, segmented enumerations and selection fields that show the readable `Query`. Typing `=` makes any field an expression. Dialogs are modeless: edits preview through literal overrides, Done writes one Change, and Cancel writes nothing.

Properties show exact measurements from Anvil (area, length, radius, mass properties with the Material), never values from display meshes. The version history groups the branch's Changes by session and author, people and agents alike. An entry renders read-only under a banner, two entries open the review diff, and Restore writes a new Change, so history is never rewritten.

## UI toolkit

Crucible needs a Rust toolkit that draws on the GPU, shapes every script, exposes a full accessibility tree on every Tier 1 platform, handles input method editors (IME) and virtualizes million-row trees. No surveyed toolkit met all of these in 2025. GPUI is tied to Zed with no documented browser target, and Narrator could not read it in a 2025 Windows test. egui's README documents AccessKit on Windows and macOS only. Masonry got a new layout system in Q1 2026, Slint adds a second UI language, and webview shells add a second runtime.

**Decision D-UIX-3:** Crucible chooses between its own retained-mode GPU toolkit, in the style of GPUI, and Masonry at month 3 of phase 0, after a six-week bake-off; the own toolkit is the working choice. Either way, maintained crates do the standards-heavy work: Taffy for layout, Parley for text, AccessKit for accessibility and wgpu for drawing. *Why:* the widget layer must behave identically everywhere, and deciding before about 20 engineer-years ride on it keeps sunk cost from deciding (R6-23). *Rejected:* GPUI (tied to Zed, no web); egui (layout model, no web accessibility); a webview UI (two runtimes); deciding at the phase 1 gate. (revised in round 2)

The bake-off builds three screens with both options on Windows, macOS, Linux and Chrome: a 1,000,000-row tree, a properties panel with an IME field, and a code panel on a 50,000-line file. UIX-O-A11Y-1, UIX-O-IME-1 and the frame budgets judge it.

### Architecture

Interface state lives in typed cells (`State<T>`), and product data enters them only through `api` subscriptions. A widget's `render` builds keyed elements from cells, Taffy lays them out (virtualized containers lay out only realized rows), and elements emit quads, glyph runs, icons, paths and viewport surfaces. These batch into instanced wgpu draws without compute, so the UI draws identically on WebGPU and WebGL2, and frames render only on input, state change, animation or refinement.

Other paths tessellate on the CPU. Vello's original renderer needs GPU compute, and Vello Hybrid was "roughly beta quality" in April 2026; it is re-evaluated at the phase 2 gate.

### Text and accessibility

- **Shaping.** Parley shapes with HarfRust, a Rust port of HarfBuzz that "for the most part passes the HarfBuzz test and fuzzing suites"; ICU4X resolves bidi.
- **Fonts.** Inter sets interface text and JetBrains Mono code, Noto covers "more than 1,000 languages and over 150 writing systems", and system fonts are only a logged last fallback.
- **Rasterization.** Skrifa loads, scales and hints outlines into an alpha atlas at four subpixel offsets. Editors handle bidi carets, grapheme deletion, IME composition and platform shortcuts.

**Decision D-UIX-4:** Grayscale antialiasing with bundled fonts on every platform. Glyphs are hinted by Skrifa's hinter below UI scale 1.5 and unhinted above, with the same code on every OS. *Why:* identical layout and bitmaps across platforms for snapshot oracles, correct rendering over translucent surfaces, and crisp 11 and 12 px text on 100%-scaled 1080p displays (R6-43). *Rejected:* each OS's text stack (metric differences); LCD subpixel antialiasing (fails over transparency); unhinted text at every scale (soft beside native applications). (revised in round 2)

AccessKit adapters provide UI Automation, NSAccessibility and AT-SPI, plus Android and iOS for Tier 2 tablets. Its web adapter is planned, not shipped, so Crucible builds it upstream with two engineers. It is a hidden DOM mirror with ARIA roles, names, states and bounds, as Flutter web does for its semantics tree. Virtualization bounds the mirror to about 2,000 realized nodes, costing under 1 ms per frame (target). Collections expose `aria-setsize` and `aria-posinset` ("row 4,512 of 1,000,000").

**Decision D-UIX-5:** Crucible implements the AccessKit web adapter as a DOM mirror and enables it by default on the web. *Why:* WCAG 2.2 AA on a Tier 1 platform, with no hidden opt-in step. *Rejected:* a DOM-based web UI (breaks the single toolkit); Flutter-style opt-in (users must first find a hidden control).

Browsers use the EditContext API where available, so a custom-rendered editor receives IME composition and reports caret bounds. EditContext is not Baseline; elsewhere a hidden `<textarea>` proxy sits at the caret, and both paths feed one input stream.

## Renderer

The renderer is one crate, `apps/renderer`, on wgpu 30. It draws the viewport, Field views, toolpaths, 2D canvases, overlays and headless snapshots, on the toolkit's wgpu device.

### GPU capability tiers

wgpu 30 exposes 64-bit atomics and indirect-count draws on native backends only. The WebGPU Candidate Recommendation Draft of 15 September 2026 has no multi-draw indirect, bindless resources or mesh shaders, and WebGL2 has no compute.

| Tier | Where | Required capabilities | Capacity at 60 fps (contract 13.3, targets) |
| --- | --- | --- | --- |
| G1 Full | Native Vulkan 1.3, DX12 Shader Model 6.6, Metal 3.1 | Compute, storage buffers, indirect draws; 64-bit atomic min and max for compute rasterization | 100,000 Instances and 5M visible triangles; 1,000,000 Instances on the high band |
| G2 Compute | WebGPU with `core-features-and-limits`; native adapters below G1 | Compute, storage buffers, single indirect draws | 20,000 Instances; 2M visible triangles (30 fps at 5M) |
| G3 Raster | WebGL2, GLES 3.0, WebGPU compatibility mode | Instanced draws, float render targets | 10,000 Instances of at most 1,000 distinct Parts; 30 fps at 2M visible triangles |

Ten million Instances, for ships and buildings, is a phase 5 high-band target.

**Decision D-UIX-6:** Every feature works on every tier; tiers differ only in declared capacity and refinement speed, and the graphics popover names the tier and its limits. *Why:* the contract's identical-features rule, stated honestly, since hardware cannot deliver identical scale. *Rejected:* hiding features on weaker tiers (breaks parity); one lowest-common-denominator renderer (wastes native hardware by an order of magnitude).

Every GPU path has a CPU path, including picking and Field sampling, and servers render through software Vulkan (Mesa lavapipe) or WARP. PLT's safe mode gets the G3 path on WARP, lavapipe or Metal. After device loss the renderer rebuilds from cached display packages, typically within one second, and says "Graphics restarted".

### Display data

Anvil owns tessellation (`anvil::tessellate`); the renderer never tessellates B-rep.

```rust
/// Produced by Anvil, cached in CAS; layout fixed jointly by ANV and UIX.
pub struct DisplayPackage {
    pub geometry: GeometryId,            // pages are keyed by GeometryId and tolerance
    pub status: ResultStatus,            // Ready(Preview) while streaming, then the requested fidelity
    pub chordal_error: Length,           // max distance from display triangles to the Body
    pub bounds: Aabb,
    pub faces: Vec<EntityId>,            // canonical face number -> EntityId; clusters index into it
    pub edges: Vec<DisplayEdge>,         // polyline per model edge, with EntityId and continuity
    pub pages: Vec<ObjectId>,            // cluster pages, 64 KiB each
    pub root_pages: Vec<u32>,            // always resident
}
```

- **Sharing.** Pages are keyed by `GeometryId` and tolerance, so renamed or reused geometry shares them; only the face table carries names.
- **Clusters** hold up to 128 triangles, and level-0 clusters never cross a face, so picking and updates work per face. meshoptimizer's codecs compress pages. Its `clusterlod` method builds the DAG as a deterministic Anvil operation with monotone error bounds.
- **Phases and tolerance.** Phase 1 packages carry level-0 clusters from Anvil's tessellation; cluster-DAG pages arrive in phase 2 (contract 13.2) in the same layout. An edit re-tessellates only changed faces, and refinement continues until chordal error projects under 0.5 px (target).

**Decision D-UIX-7:** Display data is a clustered `DisplayPackage` per Body, level 0 in phase 1 and a cluster DAG from phase 2, produced off the UI thread and cached in CAS; culling, LOD selection, camera and selection run locally. *Why:* interaction never waits for the engine, unchanged Bodies cost nothing after an edit, and one format serves desktop, browser, review and CI. *Rejected:* a monolithic mesh per Body (no LOD, full re-upload per edit); server-side video streaming (latency, bandwidth, no offline use). (revised in round 2)

The scene is a flat table of draw Instances mirroring the Assembly tree, each with an `f64` transform, visibility, style and selection flags; identical Parts share one package. On the GPU each translation is a high and low `f32` pair, and shaders subtract the eye position in the same split form. A binned-SAH BVH over Instances is rebuilt when the Assembly changes and refit when Instances move.

**Decision D-UIX-8:** Reversed-Z float depth, an infinite far plane and relative-to-eye split-precision transforms on every tier, with the near plane at 0.1 times the distance to the nearest visible bound, down to 1 µm. *Why:* one scene spans micrometre details and hundred-metre extents, and Reed found reversed-Z float depth gave "a *zero error rate*" in his test. *Rejected:* logarithmic depth (disables early depth test); per-frame CPU rebasing (costly at a million Instances).

### Two pipelines

**Decision D-UIX-24:** Phase 1 ships one forward renderer on G1, G2 and G3. It has per-face and per-Instance id targets for picking, model edges, level-0 clusters with per-Part discrete LOD, weighted blended transparency and section caps. Ambient occlusion runs at half resolution, and G1 and G2 draw the GP2 lattice by direct implicit evaluation. *Why:* both phase 1 golden products are single Parts, and the open cluster-DAG implementation on wgpu was unfinished in March 2025 (R6-24). *Rejected:* building the visibility-buffer pipeline in phases 0 and 1 (a long chain that GP1 and GP2 do not need).

[[DIAGRAM: renderer frame graph in two lanes. "Phase 1 forward (all tiers)": uploads → CPU Instance cull → per-Part LOD → forward raster with id targets → edges → weighted transparency → AO → overlays → composite. "Phase 2 virtualized (G1, G2)": uploads → GPU Instance cull → DAG cut → cluster cull → raster pass 1 → depth pyramid → raster pass 2 → resolve → edges → k-buffer → AO → overlays → composite. Each raster pass feeds "picking".]]

From phase 2, G1 and G2 cull on the GPU against the frustum and last frame's depth pyramid. A cluster draws when its error projects under τ (1 px) and its parent's does not, so the cut is crack-free, as in Nanite, with on-screen error under 1.5 px (target). Clusters raster into a visibility buffer (`R32Uint` on G2; packed depth and id by 64-bit atomics on G1), a second pass draws newly visible clusters, and a resolve pass shades from triangle ids.

On G2, culling writes surviving triangle indices into one compacted index buffer drawn with one `drawIndexedIndirect`, so vertices are reused and no degenerate triangles are issued (R6-46). Per-cluster `drawIndirect` with padding is the fallback where the buffer would exceed the binding limit. On G1, clusters of sub-two-pixel triangles rasterize in compute with 64-bit atomics, as Bevy's virtual geometry does on wgpu.

**Decision D-UIX-9:** From phase 2, virtualized geometry uses a cluster DAG, GPU-driven culling with two-pass occlusion and a visibility buffer on G1 and G2, a compacted index buffer on G2, and compute rasterization of small triangles on G1 only. `UIX-O-PERF-1` on GP3 and GP4 gates it, and mesh shaders are adopted on G1 only if at least 15% faster. *Why:* the state of the art in practice (Nanite; GPU-driven culling since Haar and Aaltonen 2015; zeux's niagara; Bevy), mapped onto WebGPU core. *Rejected:* mesh-shader-only pipelines (absent on the web); per-object draws everywhere (CPU-bound beyond about 10,000 Instances). (revised in round 2)

### Large assemblies and picking

- **Instancing.** A fastener used 40,000 times stores one package and 40,000 transforms of 64 bytes.
- **Streaming (phase 2).** Clusters request pages each frame into a fixed pool with least-recently-used eviction. Native G1 pools default to 1 GiB, at most half of VRAM, and browsers follow PLT's memory table.
- **Coarse first.** Root pages load first, so a 1,000-part assembly shows a coarse view in 2 s and refines within contract 13.3's 10 s from warm cache. Sub-pixel Instances draw as points, and lightweight mode measures with "≈" until Anvil returns exact values.

A click reads the id target (phase 1) or visibility buffer (phase 2) and maps the triangle to its face's `EntityId`, within contract 13.3's 16 ms native and 33 ms browser rows. A hit from a coarse cluster or within a pixel of an edge is confirmed by a CPU ray cast in under 2 ms (target). G3 picks by CPU ray cast, avoiding WebGL2 readback stalls. Edges and vertices use a pick buffer widened to 4 px for mouse and 12 px for touch; clicking again cycles stacked entities, and box selection follows CAD's enclosed and crossing convention.

Every selection becomes a `Query` before an edit uses it. `api` Inspect returns ranked candidates such as `base.face(role: end_cap)`, each with a robustness rating; fragile ones carry `ING-L-FragileSelector` and a "Name this selection" fix.

**Decision D-UIX-10:** Picking reads an id target or the visibility buffer and confirms ambiguous hits against level-0 geometry; selections enter edits only as `Query` values chosen from ranked suggestions. *Why:* a fast pick that is never wrong about identity, and selections that survive rebuilds. *Rejected:* CPU-only ray casting (slow at assembly scale); raw `EntityId`s in source (unreadable). (revised in round 2)

### Edges, transparency and sections

Model edges come from the package, drawn as screen-space quads 1.25 px wide with analytic antialiasing; tangent joins draw thinner. Silhouettes of curved faces come from id, depth and normal discontinuities, and hidden lines dash in screen space so dashes never crawl. Drawings use Anvil's exact silhouette curves instead, following Bénard and Hertzmann's survey of the trade-offs.

**Decision D-UIX-11:** Phase 1 uses weighted blended order-independent transparency (McGuire and Bavoil) on every tier. From phase 2, G1 and G2 resolve the nearest k layers exactly with a k-buffer of 32-bit keys (24 bits of quantized reversed-Z depth, 8 bits hashing Instance and face) and blend deeper layers. The resolve breaks remaining ties by `EntityId` order, and k follows the adapter's `maxStorageBufferBindingSize` and the render resolution each frame. *Why:* X-ray views of nested housings need exact front layers, and depth-only keys flicker on coincident mating faces (R6-27). *Rejected:* depth peeling (a geometry pass per layer); linked lists (unbounded memory); a fixed k (exceeds WebGPU's default 128 MiB binding above about 3.3 MP). (revised in round 2)

Display opacities clamp to 0.2 to 0.9, where weighted blending is tuned, and the graphics popover counts pixels whose layers exceeded k. Sections take up to six planes or one box, each optionally locked to a face by `Query`. Caps draw where the nearest surface behind the plane is a back face of a closed Body, hatched per Material class, and show the active Field in Simulate. When the view settles, Anvil's exact section replaces the display caps and supplies area, centroid and second moments.

### Styles, appearance and color

Display styles are Shaded with edges (the Design default), Shaded, Wireframe, Hidden line, Realistic, X-ray and Field view. Engineering styles use a headlight with hemisphere ambient, so shading never hides geometry.

- **Appearance.** OpenPBR Surface 1.1.1 in a reduced real-time form with documented deviation, checked against MaterialX references. A `Neutral` appearance drops imported textures and is the default for agent renders (R5-17).
- **Ambient occlusion.** Ground-truth AO (Jimenez et al. 2016, ported from XeGTAO) at half resolution in motion; XeGTAO reports about 2.39 ms at 1080p on an Intel i7-1195G7 integrated GPU.
- **Color.** Rendering is linear Rec.709 in 16-bit float targets, output as sRGB, Display P3 where supported, or extended range for Realistic views on HDR displays. Khronos PBR Neutral tone-maps only the Realistic style; lighting scales Field colors only within [0.8, 1.0].
- **Ray tracing.** A path-traced Realistic preview arrives in phase 5, since wgpu's ray queries are experimental.

### Anti-aliasing, render scale and implicits

In motion, edges and overlays use analytic antialiasing and surfaces a one-frame morphological filter on id and depth. When the camera stops, the renderer accumulates 16 jittered frames over about 270 ms at 60 Hz, then stops.

**Decision D-UIX-12:** No temporal anti-aliasing during interaction; progressive supersampling when the view is still. *Why:* engineers judge edges and small features during orbit, and temporal reprojection smears thin lines. *Rejected:* TAA (ghosting, history-dependent images); MSAA on the visibility buffer (four times the memory).

**Decision D-UIX-25:** During camera motion the 3D view renders at most 2.1 MP and upsamples, while edges, overlays and text draw at native resolution; still frames accumulate at native resolution. *Why:* pixel-proportional stages cost about 2.8 times more on a 5.9 MP panel, so 60 fps would fail before geometry is counted (R6-10). *Rejected:* native resolution in motion (misses 60 fps on mid-band laptops); downscaled edges and text (blurs what people judge).

BRep and Mesh Bodies draw from clusters; SubD Bodies show Anvil's limit surface, with the control cage while editing. Implicit Bodies draw from Anvil meshes at display tolerance, or on G1 and G2 by direct evaluation per screen tile with interval pruning, following Keeter's massively parallel method. During edits this runs Anvil's WGSL tape interpreter, which takes tapes as data, so no pipeline compiles inside a drag; a specialized shader compiles only for still views (R6-42).

### Frame budgets

## Field views

Fields are painted on the true geometry, never exported to a separate post-processor. A `FieldView` in `ViewState` names a study result and how to show it.

```rust
pub struct FieldView {
    pub source: OpSite,                  // the study call whose result is shown
    pub output: Symbol,                  // which result Field, such as von_mises
    pub quantity: DerivedQuantity,       // magnitude, x, y, z, von Mises, principal 1..3, ...
    pub spec: VisualizationSpec,
}

pub enum VisualizationSpec {
    Color { map: Colormap, range: Range, bands: Option<u8>, isolines: Option<u8> },
    Vectors { density_px: f32, scale: VectorScale },
    Streamlines { seeds: SeedRake, max_length: Length, tolerance: f32 },
    Isosurfaces { values: Vec<f64>, opacity: f32 },
    Deformation { exaggeration: Exaggeration, show_undeformed: bool },
    Volume { map: Colormap, opacity_ramp: Ramp },
    Chart { kind: ChartKind },           // line probe, waveform, Bode, Smith, eye
}
```

**Decision D-UIX-13:** Field colors come from per-pixel evaluation of Flux's WGSL evaluators, run on the UI process's device from coefficient buffers, where the tier allows; elsewhere from adaptively refined vertex samples with a stated interpolation error. Probes always use Flux's exact sampler, and display data never feed checks (D-FLX-22). *Why:* linear interpolation of high-order solutions misplaces peaks, and the UI's device avoids a host round trip on DX12 and Metal (R6-16). *Rejected:* fixed per-vertex sampling (silent error near stress concentrations); a separate post-processor. (revised in round 2)

Vertex samples refine until interpolation error is under 1% of the color range (target). During a geometric drag, physics results show as `Proxy` until the full update arrives; from phase 3 Flux's reduced models answer parametric drags (D-FLX-37).

Crameri, Shephard and Heron show that rainbow maps distort data and fail readers with color-vision deficiency. Crucible ships the Scientific colour maps (v8.0.1): batlow for sequential data, vik for diverging data and a cyclic map for phase. Paul Tol's palette serves categories, and a value-suppressing palette (Correll, Moritz and Heer) shows uncertainty.

**Decision D-UIX-14:** Rainbow and jet colormaps are not offered, not even as an option; imported legacy presets map to batlow with a one-time notice. *Why:* evidence of distortion and accessibility harm, and defaults decide most users' choices. *Rejected:* offering jet "for familiarity" (familiarity is why the harm persists).

## Direct manipulation and code

Direct manipulation edits the same Ingot program the code panel shows. Sketch-n-Sketch showed that output edits can map back to small program changes; Crucible applies the idea to typed CAD programs through provenance and Ingot's derivatives.

### From gesture to Ingot edit

Every manipulation produces an `EditPlan`: the intent plus ranked candidate edits that would realize it.

```rust
pub enum ManipulationIntent {
    MoveEntity    { target: Query, delta: Transform },
    SetMeasure    { target: Query, measure: Measure, to: Quantity<Dyn> },
    PlaceInstance { instance: InstancePath, to: Transform },
    CreateFeature { call: FeatureCall },
}

pub enum EditCandidate {
    SetLiteral    { site: LiteralSite, to: Value },                  // change one literal
    SolveLiteral  { site: LiteralSite, through: OpSite, to: Value }, // invert an expression
    SetParameter  { symbol: Symbol, to: Value, uses: u32 },          // a shared parameter
    InsertFeature { after: OpSite, source: IngotSnippet },           // a direct-edit feature
    SetPlacement  { instance: InstancePath, to: Transform },
}

pub struct EditPlan { pub intent: ManipulationIntent, pub candidates: Vec<EditCandidate>, pub chosen: usize }
```

1. **Prefer the driving literal.** In phase 1 the first candidate is the literal of the call whose `OpSite` and role created the dragged entity, such as an extrude distance for an end cap. Other literals follow by IIR dependence distance. From phase 2, derivatives through `anvil::shape_velocity` refine the order.
2. **Solve through Ingot expressions.** For `width / 2`, ING's forward-mode derivatives solve for the free literal from phase 1. When several literals contribute, the plan lists each and never edits more than one silently.
3. **Warn on shared parameters.** "Used by 3 features" appears, and "change only here" introduces a new literal that the diff shows.
4. **Fall back to a direct-edit feature** over Anvil operations, with no privileged path.

During a drag, a chip states the candidate ("thickness 4 → 6.2 mm" or "adds `offset_faces` after `fillet`"). Tab cycles candidates, and the code panel shows a ghost diff.

**Decision D-UIX-15:** Direct manipulation edits source through ranked edit plans: change the driving literal when one exists, otherwise append a direct-edit feature, always showing which before release. During a drag Kiln evaluates literal overrides `{ LiteralSite => Value }`, so a gesture writes exactly one Change, on release. Phase 1 ranks by provenance and dependence, and derivatives refine the ranking from phase 2. *Why:* one model with three editors; intent survives where parameters exist, and history-free editing stays possible where they do not, as in Plasticity and Shapr3D. *Rejected:* edits that rewrite history invisibly; refusing direct edits on unparameterized geometry; derivative ranking in phase 1, which needs `shape_velocity` (R2-44). (revised in round 2)

### Handles, push-pull and sketching

Features declare linear, angular, radial, point, planar and count handles in their metadata, so std and user packages get the same treatment. The transform gizmo draws arrows, rings and plane squares at a constant 96 px, with axis letters and distinct arrowheads. Typing during a drag enters an exact value, and `=` starts an expression.

Drags step by zoom-adaptive 1, 2, 5 increments; Alt (Option) moves freely, Shift locks the direction or inference, and Ctrl or Cmd gives one-tenth speed. Control-vertex drags on surfaces use Anvil's `Preview` re-evaluation with zebra and curvature Fields within 16 ms (target).

- **Push-pull** on an end cap changes the extrude distance. On other faces, phase 1 plans `anvil::offset_faces`, which rebuilds adjacent blends with the same parameters and ids; `move_faces` joins in phase 2. A blend that cannot regrow fails with `BlendRegrowFailed`, offering "remove blend" and "reduce radius".
- **Boolean choice.** A chip cycles New Body, Join, Cut and Intersect, defaulting to Cut when the drag enters material.
- **Sketches** start on a plane, datum or planar face referenced by `Query`, with the usual drawing and editing tools and construction geometry.

```
let profile = sketch(base.face(role: end_cap)) {
    let a = line(p0, p1)
    let b = arc(tangent_to: a, end: p2)
    horizontal(a)
    dim(a.length, 40mm)
    coincident(b.end, origin.y_axis)
}
```

Anvil's `solve_constraints` runs every frame while under-constrained geometry moves, within MEC's solve targets, and release writes the solved seeds as one Change. The status bar states the remaining degrees of freedom, and MEC's `SolveReport` draws free motions as arrows. Under-, fully and over-constrained geometry differ in color and stroke, each conflict member offers its `Fix` (delete, reference or replace), and "Constrain fully" asks an agent for an `EditPlan` preview.

Inference follows SketchUp. Endpoints, midpoints, centers and intersections become `coincident`, and on-edge points `on(entity)`. Horizontal, vertical, parallel, perpendicular and tangent become the matching constraint, and equal lengths, named values and 15° steps an `equal`, an expression or a dimension. In 3D the same inferences become `Query` references and deltas. Candidates lie within 8 px for mouse and 16 px for touch, a 3 px hysteresis prevents flicker, and every accepted inference becomes an explicit constraint call.

Selecting a feature shows its driving dimensions at a constant 12 px. Clicking one opens an inline editor for values, units, expressions and tolerances (`4mm ± 0.1mm`), bound through the same `EditPlan`. In assemblies (phase 2), mates draw as glyphs, Instances drag within their degrees of freedom through MEC's solver, and "Test motion" moves a mechanism without writing, highlighting interference.

Undo reverts the current principal's own Changes by writing inverse Changes; redo writes them again. It never reverts another person's or an agent's work, which is undone by rejecting or reverting a Proposal. A later edit to the same statement offers keep, revert or diff; a drag, dialog or command is one step, and typing groups by word or a 500 ms pause.

### Agents

The command palette (Ctrl+K or Cmd+K) ranks commands, features, entities, files, branches, Proposals and settings by match, recent use and preset, with shortcuts and inline argument forms. A query that matches nothing, or starts with `>`, goes to the default agent, and the palette says so first. Palette, menus, toolbars, keymaps and context menus derive from one command registry.

The agent panel holds a request input, a scope chip (permissions, cost cap, time limit), the plan expanding to `api` calls, an activity timeline and a budget meter. Its controls are Pause, Steer, Fork and Take over. Attachments (selection as `Query`, views, comments, files, sketches) enter the agent's context as `ExternalText` with their origin, never as goal text.

**Decision D-UIX-18:** Agent activity is shown at the level of `api` calls and Changes, always on the agent's own branch, and any agent action can be inspected, replayed or reverted like a person's. *Why:* trust comes from seeing real actions, not narrated summaries, and the contract confines agents to branches. *Rejected:* chat-only output (no evidence); agents editing the user's working branch (unreviewable).

- **Who steers.** Only the delegating human steers, pauses, forks or takes over; anyone else's steer or @mention becomes a request in that human's inbox (R5-43).
- **Steer, pause, rewind.** Steer and Pause use AGT's `session.control`, which arrives with the hosted crew in phase 2. A steer arrives at the next step boundary, marked on the timeline. Pause stops after the current `api` call, and Kiln cancels in-flight Evaluations, so no half-applied edit exists. "Continue from here" forks a branch at a timeline Change.
- **Pins and questions.** Pins ("do not change mounting holes") become `require` checks on the branch. Agents ask through typed question cards whose answers return as typed data.
- **Verdicts.** Reject needs a reason, given to the agent. Cherry-picked features form a new Proposal, which runs checks before approval.

Variant sets (phase 2) show up to 16 linked viewports with one camera, beside a sortable table, a Pareto scatter plot and parallel coordinates; "Promote" turns a variant into a Proposal.

### Collaboration

Live documents, presence and follow mode arrive in phase 2 (contract section 13.2). The UI draws KLN's presence as avatars, labelled 3D pointers, remote selections and drag ghosts, interpolated over 100 ms; clicking an avatar follows that person or agent.

**Decision D-UIX-19:** Presence colors come from a six-color categorical set per theme, chosen to stay distinct under protan, deutan and tritan simulation (Machado, Oliveira and Fernandes 2009), and every color pairs with initials and a name. *Why:* WCAG 1.4.1; a preliminary screen kept six colors at least about 0.07 apart in Oklab under all three simulations, against about 0.03 for the best eight; it is repeated with the paper's Table 1 before release [unverified]. *Rejected:* hashed hues (collisions); eight or more colors.

## Simulation, manufacturing, drawings and electronics

### Studies and results

A study is Ingot source; Flux owns its semantics, and the UI builds it by selection: a study template, then faces or Bodies with a condition (fixed, force, pressure, bolt preload, temperature, convection). Each becomes a statement with a `Query` and typed quantities, such as `pressure(web.face(role: end_cap), 2.5MPa)`, drawn as scaled glyphs. Unassigned Materials are flagged, detected contacts wait for confirmation, and Flux's pre-flight lists rigid-body modes, unit errors and envelope warnings with fixes.

Each study Evaluation names its fidelity in its header. `Interactive` studies re-run after edits within contract 13.3's row: 1 s up to 100,000 DOFs on G1, 2 s in browsers with WebGPU, 6 s on CPU alone, remote above that. `SignOff` Evaluations queue locally or on team and cloud workers through `api`, showing queue position, time and cost.

The results panel lists each check's verdict, value, limit, margin and bound. For the canonical bracket it reads "`stress < 0.6 × yield` beyond 8 mm from the clamp: `Pass`, margin 18% (`Estimated`, ±4%)", linked to its region and Field. A region that meets a singular set gives `Undecided { SingularPoint }` with the fix "exclude a stated distance". A bound wider than the margin gives `Undecided` with the accuracy needed and offers refinement or `SignOff`. Two Evaluations compare as a difference Field on matched geometry.

## Performance, privacy and extension

Contract section 13.3 owns the shared performance rows. PLT owns browser startup and memory: warm start 2.5 s, a first visit 8 s at 50 Mbit/s, and at most 25 MiB of compressed initial Wasm, with other packages loaded on demand. UIX adds targets of its own: 8.3 ms interface-only frames, palette results in 30 ms over 100,000 items, and keystroke-to-paint in 8 ms on 50,000 lines. Arrived results display within 50 ms, and no UI-thread stall exceeds 50 ms.

**Decision D-UIX-28:** For labels above `internal`, nothing the UI sends outside the organization carries content. Notifications, emails and push payloads carry ids and generic text, never snapshots or names; crash reports upload only the signature and module list; reproduction bundles go only to the organization's own server. Copies of labelled content are excluded from clipboard history and cloud clipboards where the OS allows, and a policy can forbid copying. PLT keeps the CAS, journal and caches out of cloud-synced folders and OS backup. *Why:* labels stop at `api` unless egress channels consult them, and ITAR's end-to-end condition fails once a third party holds plaintext (R5-16). *Rejected:* content-rich notifications for every label; per-feature opt-outs instead of one auditable rule.

**Decision D-UIX-22:** UIX's telemetry is part of PLT's one pipeline and public schema: opt-in per install, an install id rotated every 90 days and never joined to accounts, aggregates under 50 installs dropped, raw data kept 90 days and aggregates 13 months, and EU data collected in an EU region. Organizations turn it off with the signed policy `telemetry.performance = off` plus an egress allowlist. *Why:* engineering data is confidential, and two pipelines with different payloads and retention cannot both be honest (R5-29). *Rejected:* opt-out telemetry; a separate UI pipeline; compile-time exclusion, which contradicts PLT's single binary. (revised in round 2)

UIX contributes frame-time histograms per tier, interaction latencies, command counts, typed failure codes and settings, never source, geometry, names, paths, values or prompts; an inspector shows each payload first. PLT's minidumps hold thread stacks, which can hold design data, so uploads ask first and show their content, as do reproduction bundles (branch, `api` call log, `ViewState`). After a crash the workspace restores the last `ViewState`, panels and comment drafts, and every finished gesture is already a Change.

### Extending the interface

Principle 1 applies to the interface: domain views from other tabs, such as the electronics editors or the sheet-metal flat pattern, use the extension points open to any package. Feature dialogs and handles come from `Feature` metadata; commands are registry entries mapping to `api` calls; study templates are Ingot packages; visualizations are Fields with a `VisualizationSpec`; themes, keymaps, templates and tutorials are data. Code-driven views are Wasm components:

```wit
package crucible:ui@0.1.0;

interface view {
    use types.{element, ui-event, command-call};
    render: func() -> element;                              // element tree from data read through api
    handle: func(event: ui-event) -> list<command-call>;    // calls go through the registry and api
}

interface canvas-host {
    use types.{primitive-batch, layer-id};
    submit: func(layer: layer-id, batch: primitive-batch);  // imported; retained until replaced
}

interface canvas {
    use types.{hit, command-call};
    on-hit: func(hit: hit) -> list<command-call>;           // hits resolved from the same buffers
}

world panel    { import crucible:api/read; import crucible:api/edit; export view; }
world canvas2d { import crucible:api/read; import crucible:api/edit; import canvas-host; export view; export canvas; }
```

- **Sandbox.** Panel and canvas Wasm components get no files, network or clock and reach data only through `api`; `crucible:api/edit` needs the user's grant per package. Third-party ones run in PLT's sandboxed worker process (contract section 7.4).
- **Budget.** Panel UI logic gets 2 ms of CPU per frame, and three over-budget frames pause it with a notice.
- **Chrome.** Every panel shows its package identity and may not use modal or system-styled elements, so it cannot imitate Crucible's dialogs. Panel edits record the package in `ChangeProvenance` (R5-42).
- **Host services.** The toolkit supplies accessibility, theming, localization and keyboard access, and selection is one shared set of `EntityId`s.

**Decision D-UIX-23:** The interface is extended only through declarative data, Wasm component panels that return toolkit elements, and Wasm component canvases that submit retained 2D primitives. Built-in domain views use the same mechanisms, and no extension ships shaders or reaches the GPU. *Why:* no privileged code, plus accessibility, theming, localization and parity for every panel, with canvases for dense 2D editors (D-UIX-27). *Rejected:* native shared libraries (unsafe, per-OS, impossible on the web); webview panels (second runtime); custom shaders (portability and review cost). (revised in round 2)

- **Windows 11.** DX12 by default, Vulkan as an alternative; G1 needs Shader Model 6.6. On Windows ARM64, Chrome keeps WebGPU behind a flag, so browser users run G3.
- **macOS.** Metal has 64-bit texture atomics only from MSL 3.1, and some older Apple GPUs may lack 64-bit atomic min and max [unverified], so they run G1 without compute rasterization. Indirect-count draws exist only on DX12 and Vulkan, so every tier uses single indirect draws. Display P3 is the default and ProMotion gets 120 Hz interface frames.
- **Linux.** Vulkan; Wayland and X11 with fractional scaling; AT-SPI; IME through IBus and Fcitx [unverified].
- **Browsers.** WebGPU is on by default in Chrome and Edge on Windows, macOS and ChromeOS (since 113) and in Safari 26. Firefox has it on Windows (since 141) and Apple silicon (since 147, or 145 on macOS 26). On Linux, Chrome enables it only for Intel Gen12+ and NVIDIA on Wayland, so many Linux users run G3. Compatibility-mode adapters also run G3, and G2 page pools split into 128 MiB bindings.
- **Browser services.** The CAS and replica live in OPFS, a service worker caches the shell, and threads need cross-origin isolation [unverified: current requirements]. EditContext and WebHID are not Baseline and have fallbacks; Noto CJK downloads on first use.
- **Tablets.** On iPadOS the web build runs in a thin WKWebView shell with WebKit's WebGPU (contract section 7.4), with no package browser: packages appear only as dependencies of an opened design. Android Chrome has WebGPU from Android 12, and device-loss recovery is tested on Tier 2 hardware every release.
- **Everywhere.** Engineering styles stay SDR, so colors match across displays. Tier 3 builds use Vulkan and AT-SPI without a support commitment. Only the shortcut modifier, text chords, menu bar location and native dialogs differ by OS, listed in one conventions table owned with PLT.

## Open questions

1. **Toolkit.** The month-3 bake-off decides between the own toolkit and Masonry (D-UIX-3).
2. **Mesh shaders.** Do they beat compute culling by 15% on CAD scenes? A phase 2 benchmark decides.
3. **Field evaluators.** Can Flux emit WGSL evaluators for every discretization? The answer sets how often vertex samples apply.
4. **Web 64-bit atomics.** When `atomic-vec2u-min-max` reaches stable browsers, G2 may rasterize in compute.
5. **3D mouse SDK.** Licensing of the vendor SDK and the Linux and browser paths need legal review.
6. **Presets.** Default bindings of every imitated product need confirmation by daily users, and preset names need trade-dress review.
7. **Usability thresholds.** Are 90% task success and a System Usability Scale of 75 the right gates for professionals with strong habits?
8. **visionOS.** A native shell, or WebXR in Safari?
9. **Saved view location.** In the design repository, or in a store that creates no Changes? `repo` decides.
10. **Findings declined in part.**
    - R4-12: toolpath playback and the NC code panel stay in phase 2, because contract 13.2 defers CAM and posts and GP1 uses the shop's own CAM; the cost panel moves to phase 1.
    - R4-06: the setup-sheet preview arrives with MFG's CAM in phase 2, for the same reason.
    - R3-41: ten design sections rather than eight, so each capability table covers one coherent area.
